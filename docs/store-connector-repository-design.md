# Store Connector Repository Design

> Language: English | [简体中文](../zh-cn/docs/store-connector-repository-design.md)

> Status: design candidate. Production implementation remains blocked until an
> independent review returns `GO` for this exact document commit.

## Scope

This wave migrates the eight Connector-owned Store methods, all three backends,
and every production caller. It also closes the restart gap deliberately left
by the accepted [CredentialRepository design](store-credential-repository-design.md):
a binding identity becomes durable before provider work or credential sealing,
and durable non-active states authorize credential cleanup after cancellation,
an ambiguous Store outcome, or process restart.

The wave does not migrate another Store repository, remove broad `Store`
dependencies, supervise unrelated runtimes, split large Store files, or change
ASR/PostgreSQL CI topology. Those remain S4-S6 and the later CI stage.

## Repository Contract

```go
type ConnectorRepository interface {
    GetConnectorSetting(context.Context, string, string) (app.ConnectorSetting, bool, error)
    ListConnectorSettings(context.Context, string) ([]app.ConnectorSetting, error)
    ListAllConnectorSettings(context.Context) ([]app.ConnectorSetting, error)
    UpdateConnectorSetting(context.Context, app.ConnectorSetting, int64) (app.ConnectorSetting, error)

    CreateNotificationBinding(context.Context, app.NotificationBinding) (app.NotificationBinding, error)
    GetNotificationBinding(context.Context, string) (app.NotificationBinding, bool, error)
    ListNotificationBindings(context.Context, string, string) ([]app.NotificationBinding, error)
    UpdateNotificationBinding(context.Context, NotificationBindingUpdateCommand) (app.NotificationBinding, error)
}
```

`Store` embeds this interface exactly once. Memory, File, and PostgreSQL each
assert it directly. The eight legacy signatures are removed together; there is
no compatibility interface, dynamic type assertion, or error-discarding
wrapper. `RevokeNotificationBinding` disappears because revocation is a
multi-step durable lifecycle, not one repository mutation.

`ListNotificationBindings` keeps the existing `(channel, status)` filter so
shared channel workers can enumerate all owners. An empty filter means all.
Owner authorization remains in the owning Gateway/connector layer and is
covered by tests; repository failures never become an empty successful list.

### Binding Data

`app.NotificationBinding` adds:

```go
Version        int64  `json:"version"`
CredentialKind string `json:"credential_kind,omitempty"`
```

`Version` starts at one and increases on every committed binding mutation,
including automatic default demotion. `CredentialKind` is non-secret. New
sealed credentials require it; legacy active/ref-bearing rows may leave it
blank because deletion by exact ref does not need the kind. A non-empty ref
whose prefix is not `config:` is Vault-owned. A Vault-owned ref may appear on
exactly one retained binding ID across every state, including terminal records;
`config:` refs are operator-owned and may be shared. Public projections do not
expose the kind.

Binding IDs are generated by the caller before create, are at most 256 bytes,
and are never reused. Owner, actor, channel, ID, creation time, and a non-empty
provider become immutable after create. Scopes and pointer fields are cloned at
every input/output/snapshot boundary.

### Opaque Conditional Update

The only update factory is:

```go
func NewNotificationBindingUpdate(
    previous app.NotificationBinding,
    replacement app.NotificationBinding,
) NotificationBindingUpdateCommand
```

The command fields are private. The factory validates the complete prior
record, freezes a domain-separated length-delimited SHA-256 digest of every
persisted field, and carries a normalized replacement. It is invalid if IDs or
immutable identity fields differ. Callers cannot set the next version or
repository timestamps; the repository assigns `previous.Version + 1` and a
fresh UTC PostgreSQL-microsecond `UpdatedAt` strictly above its per-binding
high-water mark.

Under the command lock, the backend validates the persisted row before business
checks and requires exact equality with the frozen prior candidate. Absence is
`not_found`; another valid version/value is `conflict`; malformed persisted
state is `corrupt`. There is no unlocked get/update sequence.

## Stable Semantics

Every method composes the caller context with the registered read or
transaction timeout. Context is checked before and under the backend command
lock. Cancellation, timeout, transport, durability, unknown-outcome, scan, and
row-iteration failures remain typed Store errors.

Connector settings preserve their current normalization and CAS behavior:

- blank owner becomes `app.DefaultOwnerID`; channel is trimmed and lowercased;
- reads with a blank channel are ordinary absence;
- lists return non-nil empty slices and order by channel, or owner then channel;
- update requires a non-negative expected version, creates only at expected
  version zero, and otherwise requires the exact current version;
- the repository assigns version/time and atomically persists the setting,
  its existing typed audit, and its event;
- a concurrent create/update is `conflict`, never last-writer-wins.

Binding create requires a complete caller-generated identity, status
`starting`, version zero, no lifecycle timestamps, no credential ref, no
provider session/external identity/cursor/QR material, and no error. The
repository assigns version one and creation/update time, then atomically writes
`notification_binding.starting` audit and event. Any existing ID, including a
terminal record, is `conflict`.

Reads with a blank/missing binding ID are ordinary absence. Binding lists order
by `UpdatedAt DESC`, then `ID ASC`. Empty success is non-nil. Every scanned row
is validated before filtering or state decisions.

### State Machine

The repository accepts only these transitions:

```text
starting
  -> waiting_scan | waiting_confirm | active | failed | revoking
waiting_scan
  -> waiting_scan | waiting_confirm | credential_pending | active | expired | failed | revoking
waiting_confirm
  -> waiting_scan | waiting_confirm | credential_pending | active | expired | failed | revoking
credential_pending
  -> active | failed | revoking
active
  -> active | revoking
revoking
  -> revoked
failed | expired | revoked
  -> no transitions
```

Same-state waiting updates may change only provider polling metadata and safe
display/error fields. Same-state active updates may change delivery identity,
context, cursor, default selection, scopes, and stable error fields, but cannot
change credential ref/kind or immutable identity.

Only a transition into `active` may install a credential ref. A `cred_` ref on
a new record requires a non-empty credential kind; configuration-owned refs may
use a blank kind and are never passed to Vault deletion. A transition out of
active retains the ref/kind through `revoking`. `revoked` clears default
selection and records a repository-assigned `RevokedAt`, but retains the
non-secret ref/kind as terminal evidence. `failed` and `expired` cannot become
pollable or active again.

Installing or retaining a Vault-owned ref is valid only when no other binding
ID, including a failed/expired/revoked record, carries that ref. Memory/File
check this under their global command lock. PostgreSQL enforces it with a
partial unique index and the credential-ref advisory barrier in the same
transaction. A duplicate is `conflict`; a duplicate already present at startup
is `corrupt`. Terminal retention therefore also reserves legacy refs forever,
matching the binding-ID non-reuse rule. This invariant is the cross-binding
ownership proof that authorizes a later exact `revoking` record to call
`Delete(ref)`; envelope equality alone is not treated as ownership.

If an active candidate becomes the default, every other active default for the
same owner/channel is demoted in the same command. Each demoted record receives
a new version/time and its own redacted audit/event. PostgreSQL adds a partial
unique constraint for one active default per owner/channel after readiness
validation rejects ambiguous legacy duplicates.

## Operations And Outcomes

| Operation | Mode | Timeout | Unknown reconciliation |
|---|---|---|---|
| `connector_setting.get` | read | read | self/barrier |
| `connector_setting.list` | read | read | none |
| `connector_setting.list_all` | read | read | none |
| `connector_setting.update` | write | transaction | exact candidate |
| `notification_binding.create` | write | transaction | exact candidate |
| `notification_binding.get` | read | read | self/barrier |
| `notification_binding.list` | read | read | none |
| `notification_binding.update` | write | transaction | exact candidate |

After candidate formation an unknown write returns the normalized candidate
with the typed error. Definite failures return zero. Reconciliation executes a
new context-bound read behind the same record barrier. Exact candidate equality
proves success; exact prior proves rollback and permits a newly constructed
conditional retry; absence or another record remains unresolved. Lifecycle
callers apply the stricter credential rules below before cleanup.

## Backend Rules

### Memory

Memory applies each command and its audit/events under one lock, clones all
slices/pointers, uses per-setting/per-binding non-rollback timestamp high-water
marks, and emits no partial result. Context is checked both before lock wait and
after lock acquisition.

### File

Connector methods use migrated admission and `runFileCommand`; no connector
field uses legacy `persist()`. A definite pre-submit failure restores settings,
bindings, audit, and events. A submitted ambiguous rename/directory-sync
installs the standard File fence; all later migrated reads/writes reconcile or
fail behind that fence. Timestamp high-water marks remain outside rollback.

Startup accepts only these explicit compatibility normalizations:

- blank legacy setting owner becomes the default owner and blank binding actor
  becomes its owner;
- legacy setting/binding version zero becomes one;
- legacy active/ref-bearing bindings may have a blank credential kind, but
  every non-`config:` ref must still have exactly one binding owner;
- legacy binding statuses already shipped (`waiting_scan`, `waiting_confirm`,
  `active`, `expired`, `failed`, `revoked`) remain valid.

Keys must equal embedded IDs; identities, creation/update times, present
pointer times, versions, status relations, non-empty scopes, global Vault-ref
ownership, and the single active-default invariant are validated. New recovery
states require their specified fields. No other malformed value is normalized;
startup fails `corrupt` before the Store is served.

### PostgreSQL

The schema adds/backfills binding `version`, adds `credential_kind`, and after
validation adds both the active-default constraint and a partial unique index
covering every non-empty, non-`config:` credential ref. CI services, workflow
topology, and `SPARKCLAW_TEST_POSTGRES_DSN` skip behavior do not change.

Commands acquire owned connections and explicit transactions. Setting writes
use a domain-separated owner/channel advisory barrier. Binding writes acquire
the owner/channel barrier, binding-ID barrier, and when present the Vault-ref
barrier in one documented order.
Resolution reads use `READ COMMITTED`, acquire the matching advisory barrier in
one statement, then select in a separate statement. Mutation, automatic
demotion, audit, and event rows commit atomically.

An unsafe statement, context, transport, or commit failure after connection
acquisition is `unknown_outcome`; the session is terminated and never released.
Safe server rejections and business conflicts roll back. A rollback failure
terminates the session and preserves the original, rollback, and termination
causes. Rows-affected counts and `rows.Err()` are mandatory.

Before readiness, every setting/binding row passes the same compatibility
validator as File, including active-default uniqueness. Runtime scans use that
validator too; corrupt rows never become absence or empty lists.

## Credential Lifecycle Integration

The Connector wave introduces the public recovery surface and its first
production caller together:

```go
type CredentialLifecycleRecovery interface {
    Delete(context.Context, string) error
    AbortSeal(context.Context, string, string) error
}
```

`Delete` accepts deterministic `cred_` refs and the exact shipped legacy Weixin
QR namespace `provider:openclaw-weixin-qr:<bindingID>`. New refs require an
authenticated envelope. Only that legacy namespace may contain either the
legacy Weixin kind's raw pre-migration value or its authenticated rewrapped
envelope, and Connector may conditionally delete it only while holding the exact
`revoking` record, a ref suffix equal to that record's binding ID, plus the
repository's global unique-ref invariant. Every other provider or raw ref fails
closed.
`AbortSeal` derives the deterministic ref from binding ID, requires the
expected kind, and conditionally deletes only that envelope.
Absence is idempotent success. Conflict, replacement, malformed envelope, or
unresolved Store outcome is stable credential unavailable. Neither method
returns repository candidates or secret material.

Connector Registry owns the binding lifecycle coordinator. It receives an
explicit `ConnectorRepository` plus `CredentialLifecycleRecovery`; it never
discovers either by type assertion. All lifecycle changes for one binding are
serialized in-process. The repository CAS remains the durable authority.

### Start

1. Resolve the registered adapter, generate the immutable ID, and durably
   create `starting` before adapter/provider work or Seal. The registered
   adapter supplies its provider and non-secret credential kind before create;
   adapters that never Seal use a blank kind.
2. A definite or unresolved create failure returns unavailable and does not
   call the adapter.
3. Telegram provider verification and Seal operate only from the exact created
   `starting` candidate. Conditional active update installs the returned ref.
4. Weixin start conditionally records `waiting_scan`/`waiting_confirm`. A poll
   that returns plaintext first conditionally records non-pollable
   `credential_pending` with provider metadata and kind, then calls Seal, then
   conditionally records active with the ref.
5. A provider/Seal failure is projected stably. Cleanup runs only after a
   barrier proves the exact pre-active state; otherwise the durable state is
   retained for startup recovery.

For an ambiguous active transition, exact active proves success. Exact
`starting` or `credential_pending` proves `AbortSeal` is authorized; after
successful abort it conditionally becomes `failed`. Any different or unresolved
state remains unavailable and is never cleaned up.

### Poll API

`GET /api/notification-bindings/{id}` becomes read-only. Provider polling and
state advancement move to `POST /api/notification-bindings/{id}/poll`; WebChat
uses that command while setup is pending. This removes the current GET side
effect without changing the visible setup workflow.

### Revoke

Revocation first conditionally records `revoking`, retaining credential proof,
then cancels local/provider work. A Vault ref uses `Delete`; a pre-active record
with a credential kind uses `AbortSeal`; configuration-owned/no-credential
records need no Vault call. Only successful cleanup conditionally records
`revoked`. A failure leaves `revoking` and returns stable unavailable.

Terminal records remain stored and their IDs cannot be recreated. Repeating
revoke on `revoked` is idempotent; `failed`/`expired` remain terminal results.

### Startup Recovery

Connector Registry recovery runs after settings preload but before any connector
worker starts and before Gateway listens. It lists and resolves all:

- `starting`: `AbortSeal(bindingID, kind)` when kind is non-empty, otherwise
  no credential cleanup, then conditional `failed`;
- `credential_pending`: the same abort, then conditional `failed`;
- `revoking`: `Delete(ref)`, `AbortSeal`, or no-op according to retained proof,
  then conditional `revoked`.

A recovery Store/Vault failure retains the non-pollable record and fails
connector readiness. Waiting records remain explicitly pollable; active records
remain worker-visible; terminal records are retained. Audit is never treated as
a lifecycle receipt.

## Caller Migration

Gateway, Connector Registry, binding setup, Telegram, Weixin, Notification,
Message Control, Reminder Target, Delivery, schedules, and ToolHub callers pass
their owned contexts and handle typed errors. No migrated production caller
uses `context.Background()` or discards a Connector result/error.

Operational active-binding updates (claim, context token, cursor, and stable
last error) use exact CAS. Monotonic cursor writers reload and retry a bounded
conflict only after re-evaluating monotonicity; they never replay a stale whole
record. Lifecycle transitions are not generically retried.

Broad `store.Store` constructor dependencies may remain until S4, but callers
use only the embedded ConnectorRepository methods. Tests use real repository
fixtures or a shared create/transition helper; the removed upsert API is not
retained for test convenience.

## Verification Gate

The design implementation is `GO` only when all of the following are green:

- exact interface/signature/operation/source guards, one Store embedding, and
  direct assertions for all three backends;
- Memory/File/PostgreSQL parity for context, absence, ordering, CAS, state
  transitions, terminal ID retention, default demotion, audit/event atomicity,
  global Vault-ref ownership/conflict, corruption, aliasing, and timestamp
  high-water;
- File failure injection at every pre-submit and submitted stage, restart
  compatibility, fence reconciliation, and no remaining connector `persist()`;
- PostgreSQL fault matrix for acquisition, barriers, every statement, commit,
  rollback/termination ownership, rows affected, row iteration, and startup
  validation;
- DSN-skipping real PostgreSQL concurrent create/update/default/ref-ownership
  tests without CI topology changes;
- Telegram and Weixin crash-window tests for create-before-provider,
  pre-Seal state, ambiguous active update, safe abort, revoking/delete, and
  startup recovery before workers;
- real File restart tests retaining nonterminal cleanup ownership and terminal
  IDs, rejecting duplicate legacy Vault refs, and never deleting a credential
  on unresolved or shared ownership proof;
- read-only GET plus explicit POST poll Gateway/WebChat tests and stable public
  error/redaction assertions;
- `go test ./...`, `go build ./...`, `go vet ./...`, and focused race tests.

After Connector implementation `GO`, one final integrated Credential/Connector
review removes the temporary foundation allowances and is the only gate that
declares the credential lifecycle complete. Only then may the next S3
repository start.
