# Workflow Capability Matrix

> Language: English | [简体中文](../zh-cn/docs/workflow-capabilities.md)

This document is the user-visible capability inventory for the Workflow runtime.
It describes only registered Workflow Profiles that can currently be selected
and completed. A ToolHub tool being registered does not by itself make a feature
available.

## Shared Execution Contract

- Every natural-language owner question enters the same semantic graph through
  asymmetric channels. Embedding receives only that question. Fast/Tree receives
  the same question plus bounded typed context and scores candidates without
  rewriting the request or selecting resources. Candidate-neutral grounding,
  weighted fusion, and the final Top-2 decision select at most one
  Catalog-validated leaf.
- Each Workflow profile selects its execution lane. Document read/edit model
  calls currently use Fast; other profiles retain the Deep default.
- Conversation context, attachments, ToolResult messages, observation ordering,
  compaction, grounding, and channel delivery continue to use the shared runtime
  pipeline.
- Workflow plans contain no Skill IDs and Workflow execution loads no Skill text.
  The versioned profile, active capability scope, argument bindings, ToolHub
  metadata, and Policy are the complete execution boundary.
- Model-tool nodes freeze `observation.read` as a generic support requirement.
  It uses normal directory selection and scope validation, is limited to two
  executions per stage, and cannot advance the business workflow. Existing
  persisted revisions resume without gaining this support capability.
- Bound queries, URLs, workspace paths, locations, output paths, and outcome refs
  are materialized from persisted state. A model cannot replace them during a
  later stage.
- A matched Workflow failure is explicit. It never falls back to a generic
  executor or a different capability. Internal diagnostics remain in audit;
  public results expose only stable safe messages and typed failure codes.
- An `unmatched` route terminates as `router.blocked`; it does not expose
  tools or a fallback executor.
- A browser, weather, or document request outside the current profile revision
  is changed from `unmatched` to `blocked`; there is no legacy fallback to
  recover through.

## Current Profiles

| Capability / profile | What it can do | Fixed execution path | Current boundary |
|---|---|---|---|
| `conversation.answer` r3 | The `answer` variant answers greetings, stable common knowledge, and simple explanations. The `publish` variant returns ordinary ordered image, audio, and file parts. An inbound MCP conversation can identify existing workspace media by relative path, exact basename, or an incomplete filename description. | `detect_response_media` first freezes the unverified locator and pauses for owner approval before any workspace lookup. After approval it resolves and freezes `none`, `selected`, `clarify`, or `blocked`; then `answer` either performs one no-tool model answer or deterministically publishes the frozen content. Exact basename lookup is case-sensitive; a miss or incomplete name uses the shared bounded filename-only search and selects its stable Top-1. The result can combine answer text with the frozen media. | The external MCP surface exposes only `sparkclaw.conversation.send`, not `files.search` or Catalog leaves. One workspace-data approval binds the MCP identity, owner authorization, locator, Workflow, output class, and return route; delivery adds no second approval. Inbound MCP runs do not inherit prior session context or cached derivatives. Pre-approval processing performs no file/index lookup and accepts no absolute path. The answer node cannot search or substitute a resource, and hash/size changes block the whole multipart result. Human-explicit text or media sends gain no destination-only approval. |
| `browser.internet_search` r2 | Search public, current Internet information from a frozen query. Weather warnings, news, official-source discovery, comparison, and air-quality research also use this general search path. | One `web.search` call, currently backed by Infinimesh Info when enabled, followed by deterministic rendering of the validated aggregate. Info-returned fact, conflict, viewpoint, and source order is preserved; no second ranker, synthesis pass, page read, or model finalizer runs after the result. | It does not open result pages, read a known URL, operate a signed-in browser, or turn a direct weather request into a card. Every rendered claim keeps its own valid source-ID edges. Freshness, uncertainty, linkless citations, and projection omissions remain explicit; upstream next-action advice cannot control the Workflow or answer. |
| `browser.weather` r2 | Produce one weather PNG for an explicit location. The card uses normalized current conditions and temperature, the matching daily low/high range, and up to five available future hourly entries. | `weather.lookup` -> `media.render_weather_card`. The frozen route location is bound to a typed `POST /v1/info/weather` request; the render stage receives only the completed lookup ref. | Infinimesh Info is the only weather source and fixed metric units are mandatory. Malformed, incomplete, unsupported-unit, or unauthorized responses fail without generic query/search or parsing fallback. Coordinates, AQI, and alerts are not projected into the card payload. Text-only weather, missing location, warnings/news/source comparison, and air-quality research are outside this profile. |
| `browser.automation` r3 | Acquire exactly one explicit HTTP(S) URL, runtime-registered destination, or named public website in a Bridge-allowlisted task tab, prove it with background and handed-off snapshots, and leave the verified handed-off result open. The existing destination registry remains the first lookup path; a named registry miss uses the first safety-valid URL in Info's ordered structured results. | Optional background `web.search` -> `browser.identify_public_target` for a named miss, then passive `browser.status` -> `browser.list_tabs` -> navigate/open -> settle -> background snapshot and route validation -> optional owner-requested visual inspection -> explicit owner handoff -> settle -> handed-off snapshot and route validation. | Info relevance ordering is trusted, but every selected URL and redirect must remain public HTTPS. Owner and unrelated tabs are never reused. Background work does not change browser focus; only explicit handoff may foreground the task tab. The run cannot succeed before handed-off validation, and production never closes the result tab. Clicks, typing, forms, arbitrary page reads, and multi-URL work remain outside this profile. Browser r1 is retired. |
| `browser.page_read` r1 | Read, summarize, or extract bounded content from exactly one explicit URL or named public page in a background Browser Bridge task tab. | Optional Info target identification -> `browser.status` -> background `browser.open` for the frozen URL -> background `browser.read` with `require_browser_session=true` and active task-page reuse -> final URL and content validation. | The fixed health/open/read chain cannot skip browser acquisition, focus an owner tab, or fall back to direct HTTP. Login or human verification pauses in the shared owner handoff. Open-ended research remains `browser.internet_search`; page mutation and multi-URL work are outside this profile. If final model generation is unavailable after a successful read, Runtime returns bounded extracted page content as untrusted evidence. |
| `browser.interaction` r3 | Inspect one managed task tab, explicit HTTP(S) URL, registered destination, or Info-identified public site with a page subgoal, then perform up to three independently verified, ref-bound clicks and leave the verified handed-off result open. | Target identification when needed -> automation r3 acquisition -> background `browser.assess_goal` -> bounded `browser.click` -> settle -> fresh snapshot -> `browser.validate_transition` -> `browser.assess_goal`; progress may repeat the action loop. Completion may add one owner-requested visual inspection, then explicitly hands off the task tab -> settle -> fresh snapshot -> a second `browser.assess_goal`. | Every argument is bound to persisted controller/session/page generations and fresh refs. Stale evidence, repeated state, route divergence, transition failure, or a third progress verdict fails closed. Login and human verification use a durable owner handoff. Type, select, upload/download, credentials, captcha/2FA, payment/purchase, form submission, arbitrary scripts, and unsafe consequential actions remain outside r3. |
| `browser.form_draft` r2 | Type or select up to five exact owner-supplied values in ordinary reversible fields without committing the form. It can use the current managed task tab, an explicit URL, a registered destination, or an Info-identified public site. | Background interaction-style acquisition -> fresh structured snapshot -> initial `browser.assess_goal` -> explicit owner handoff -> settle -> fresh handed-off snapshot and assessment -> one independently approved `browser.type` or `browser.select` -> settle -> fresh higher page-generation snapshot -> draft verification; repeat in the same handed-off session within the five-action bound and verify the final draft in place without reopening the target. | The draft stage exposes no click or submit-capable tool. Each approval binds one field, operation, exact value, snapshot digest, page ID, and controller/session/page generation; freshness and field safety are checked before approval and again at execution. Password, passkey, token, OTP, captcha, payment, purchase, delete, upload, submit, send, and publish controls are rejected. Values are redacted in approval summaries and persisted browser projections. |
| `browser.email` r1 | Send one new plain-text email to one recipient through a configured QQ Mail, Outlook, or Gmail browser account. | Semantic send route -> deterministic explicit/default provider selection -> fresh configuration-owned read-only login probe in a background task tab before Workflow creation -> one `email_send` node. The model supplies only recipient, optional single-line subject, and body; Runtime restores provider, account, setting version, Browser control credential generation, probe/send handler revisions, validation time, and invocation ID before exact-content approval and one `email.send` call. | Provider setting and credential generation are checked again after approval. Fixed Playwright handlers create and use only Bridge-allowlisted task tabs, verify the composed fields and Send control, and attempt Send at most once. Unknown outcomes are terminal and non-retryable. Manual login uses explicit owner handoff. Reading, replies, drafts, attachments, multiple recipients/accounts, generic browser tools, container Chromium, and browser fallback are unavailable. |
| `document.read` r4 | Read, summarize, or extract verbatim in-image text from one exact governed workspace file resolved from the current request or recent document records. Supported detection covers text, DOCX, XLSX, PPTX, PDF, and images. | Recent-document resolution and deterministic path/type preflight -> persisted `confirm_document_target` evidence -> one Runtime-invoked `files.read`, `pdf.extract_text`, or `images.inspect` call according to the frozen format -> Fast finalization over completed evidence. For an external MCP invocation, only its current explicit relative path is lexically classified first; one workspace-data approval precedes recent-record lookup, path preflight, symlink checks, format detection, and reading. | The single format-qualified reader is `direct_once`; the model does not decide whether to call it. The approved external-MCP contract covers only the exact bound reader and frozen return route, so another path cannot reuse it. OCR remains untrusted evidence, not a model lane or separate Workflow. PDF partial reads name exact missing pages and cannot claim complete coverage. A unique recent document may satisfy a human follow-up without another attachment, but is not disclosed to an external MCP caller before approval. The path must resolve inside the workspace to one regular non-symlink file. File search, multiple-file comparison, mutation, and arbitrary external paths are outside this profile. |
| `document.edit` r7 | Apply one supported bounded edit to one governed text, DOCX, XLSX, PPTX, or PDF file and write one or more traceable output copies. XLSX supports typed cell/row evidence, prefix-only row updates, and verified OOXML package preservation; PPTX supports exact text, one-slide, bounded whole-deck, and structural scopes. | Deterministic path/type and format-specific scope preflight -> `confirm_document_target` -> one Runtime-invoked format-qualified read in `document_locate_evidence` -> explicit retry-bounded `select_edit_operation` decision -> `document_edit` with only the persisted format/operation entry materialized. XLSX selection and execution share bounded `xlsx_sheet_evidence_v1`; Runtime binds workbook and target hashes before approval. PPTX binds current-read slide, shape, layout, and template evidence. PDF transforms receive a strict schema containing only the selected operation's fields. The default output is `<name>-2.<ext>` and subsequent copies advance to `-3`, `-4`, and so on. | All model-driven document stages use Fast. Localization never asks a model whether to call the reader or repeats the read. Missing, invalid, unsupported, stale, or ambiguous operation/target evidence blocks before mutation. XLSX packages with unverified features block before approval and undeclared part drift deletes the output. PPTX ambiguous scopes clarify; SmartArt, animation, chart-data, master, and macro targets block. PDF page arrays are unique positive one-based integers, rotation is a six-value enum, and `merge` is unavailable. Reversible writes require approval, every output is linked to its parent and activity, and unrelated turns do not inherit the latest document. |
| `localmind.read` r1 | Explicitly delegate the current text as a non-mutating answer, reading, research, comparison, or summary task. | One `localmind.task.delegate_read` call -> internal `query_current_task` long polls with the newest state version until terminal. | LocalMind must be named explicitly. Only current-message text is sent; history, media, files, tool output, and `documentIds` are excluded. No approval is required. Only `completed` is success; polling is bounded to 10 minutes. |
| `localmind.write` r1 | Explicitly delegate current-text work that creates, updates, renames, converts, exports, deletes, or otherwise mutates LocalMind workspace content. | Approval -> one `localmind.task.delegate` call -> the same bounded internal `query_current_task` path. | It uses the same remote delegation operation as read but has an approval-gated SparkClaw route. Endpoint and contract snapshot, task ID, return route, and evolving state version remain frozen. |
| `localmind.query` r1 | Read one exact or same-session recent LocalMind task's current state or result. | One immediate `localmind.task.get` call with `wait_ms=0`. | It does not poll, mutate, resume, or discover tasks. A missing or ambiguous task reference clarifies before MCP invocation. No approval is required. |
| `localmind.cancel` r1 | Request cancellation of one exact or same-session recent LocalMind task. | Approval -> one `localmind.task.cancel` call. | It does not query first or poll afterward. The validated cancellation-request state is returned as reported by LocalMind. |
| `schedule.manage` r3 | Create, list, update, or cancel scheduled tasks from conversation or typed WebChat toolbar actions. | Create/read are single-stage. Edit/delete run `reminders.list` -> unique pending target + frozen version -> `reminders.update` or `reminders.cancel`; all writes use `ScheduleRegistry` compare-and-swap. | Toolbar IDs are hints that must be found in a fresh owner-scoped list. Due content re-enters ordinary Message Runtime; the Timer does not select capabilities or send directly. The reminder endpoint is preserved during edit. |
| `coding.agent_manage` r2 | Read and manage coding-agent tasks and sessions through configured Happy Team and personal bridge MCP endpoints. | One active stage exposes only discovered `mcp.external` tools. Read requests can call task/session listing, detail, plan, machine, and transcript tools; create, spawn, message, stop, and cancel tools use the normal approval path. | MCP observations are untrusted and summarized before use. The personal bridge may be offline without disabling Team task tools. Plan approval/rejection is excluded from chat and belongs only to the human approval inbox. |

## Document Edit Operations

| Format | Supported edit operations |
|---|---|
| Text | `replace_text` |
| DOCX | `replace_text`, `replace_paragraph`, `insert_paragraph`, `delete_paragraph`, `set_text_style` |
| XLSX | `replace_text`, `update_cell`, `insert_row`, `delete_row`, `update_row`, `append_row` |
| PPTX | `replace_text`, `add_slide`, `update_slide`, `update_deck`, `duplicate_slide`, `delete_slide` |
| PDF | `extract_pages`, `delete_pages`, `rotate_pages`, `split` |

PPTX text edits preserve supported paragraph, run, bullet, and hyperlink
structure and fail on field-bearing targets. Whole-deck updates are atomic and
bounded to 12 slides, 64 shapes, and 32 KiB of replacement text. Slide insertion
uses a current-read layout or template-slide reference and an evidence-bound
position; note-bearing clone sources are rejected. Every PPTX edit shares a
125,000 ms end-to-end deadline and returns `document_operation_timeout` after
cleaning a partial output. Exact shared-Pipeline `reread`/`preserve` timeout
stage classification is not yet available.

## Unmigrated Features

Code/command assistance, image inspection, memory, and other domains without a
registered Workflow terminate as `unmatched`. The legacy generic loop has been
removed; resuming a persisted pre-workflow run now terminates with an explicit
retired-runtime message. Registered tools outside the
current Workflow matrix remain in ToolHub for later migration but are not
advertised as available features.
