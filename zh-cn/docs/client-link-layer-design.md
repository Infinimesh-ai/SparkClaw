# 三端连接层设计

> 语言：简体中文 | [English](../../docs/client-link-layer-design.md)

日期：2026-11-19。状态：目标设计，未实现。代码调查基于 `dfc49969`。

本文只讲电脑、手机、手表三端与后端之间怎么通信。域、设备绑定和接入凭据的签发在[自建官网设计](self-hosted-console-design.md)里，两份文档分开维护。

本文取代[客户端与后端架构 R3](client-backend-architecture-design.md) 第 1、2 节里"会话归各客户端本地所有"的边界。

## 0. 前提

以下前提由用户在 2026-11-19 确认。

1. **正式环境只有一种连接方式**。官网里有"域"，域是设备和信任关系的隔离边界。三端凭官网签发的 SparkClaw 接入凭据（扫码或粘贴）绑定到域里，后端也加入同一个域，之后各端经连接层与后端通信。接入方式只有这一种。
2. **官网只负责设备绑定、配对和签发凭据**。消息传递、会话同步、审批等一切业务都走连接层（局域网或 ISCP Relay），不经官网转交。
3. **自建环境是同一种连接方式的开发环境**，不是另一种连接方式。自建的官网和 Relay 只是把官网的角色放在自己的主机上。凡是只在自建环境下才成立的行为，都算缺陷。
4. **自建官网只要求表现形式与官网一致，不要求接口逐一相同**。与真实官网接口的适配留到接入官网链路时再做。因此客户端和后端访问官网的代码必须集中在一个适配器里（3.11）。三端暂时不用 ITES 登录。
5. **功能默认全部开放，只受设备自身条件限制**。例如手机没有内置浏览器，就不开放浏览器自动化的入口（3.9）。
6. **后端保存全部会话记录，包括附件**。
7. **旧会话记录不迁移，可以删除**。电脑端和手机端现有的本地会话在切换时直接清除；后端数据库里现有的宿主 WebChat 会话也可以删除。
8. **后端离线时三端都不能工作**。后端连不上时，任何一端发起的操作都立即明确报错，不在本地排队，也不由客户端代为执行（3.12）。
9. **一台后端只给一个人用**。暂不考虑多人场景。
10. **SparkX 内置浏览器的控制方式保持不变**。它是电脑端自身的设备能力，不在这次重构的修改范围内（3.12）。

## 1. 结论

1. 被弃用的不是 ISCP Bridge 的架构，而是它当时的凭证来源。Bridge 的代码仍在仓库里并持续维护。手机弃用它的原因是参考 Trust Root 只能签一小时 `text` 授权、不能续期、每台手机要手工写进 `peers[]`，这三点都属于凭证问题。
2. Bridge 的进程边界正是现在缺少的东西：ISCP 在独立进程里终止，Gateway 只认一个与传输无关的窄接口。node issuer 路径把 ISCP 搬进了 Gateway 进程，耦合由此而来。
3. 方案是：**用 Bridge 的进程边界，用官网域模型的凭证**。设备和后端都加入同一个域，由官网签发授权并续期。在这之上加一层后端权威的会话同步。
4. 官网的授权有效期是天级并支持自动续期。当初"一小时、不能续期"是参考实现的限制，不是官网模型的限制。node issuer 是为绕开那个限制自建的另一套签发方式，与官网模型不同，最终退役。

## 2. 现状的问题

| 问题 | 位置 | 后果 |
|---|---|---|
| ISCP 在 Gateway 进程内终止 | `cmd/sparkclaw/workbench_iscp.go`、`internal/gateway/workbench_iscp_lifecycle.go` | Gateway 升级会中断所有远程连接；ISCP 故障和业务故障互相牵连 |
| 操作表按 HTTP 形状设计 | `iscpworkbench/operations.json`：159 个操作，92 个带 `http` 字段 | Gateway 收到 ISCP 请求后再合成 `http.Request` 调原处理函数，等于两套接口叠在一起 |
| 业务适配直接写在传输类型上 | `internal/gateway/workbench_iscp_*.go`，约 1.1 万行 | 每加一个功能都要改操作表、协商、适配三处 |
| 传输协商结果被当成业务授权 | `execution_authorization.go`，用 `NegotiatedOperations` 决定工具和文件权限 | 权限取决于客户端版本协商到了什么 |
| 操作表精确比较 | `negotiation.go` 的 `compatibleV2Operations` | 新增操作会让旧客户端连不上，只能靠逐个扩展开关绕开 |
| 客户端到处分支 | 桌面主进程 `main.mjs`、`desktop-auth.mjs`，webchat `LocalWorkbench.tsx` 约 15 处 `iscp` 分支 | 局域网和远程是两套代码路径，行为不一致 |
| 两套会话模型并存 | 宿主 WebChat 的会话存在 Gateway 的 `sessions`/`messages` 表；桌面和手机的会话存在本机，每轮用 `execution.submit` 把历史带上去 | 三端无法共享会话；远程接口没有"列出会话""读消息"的操作 |
| 手机客户端库依赖后端业务代码 | `mobile/sparkclawmobile` 会编译到 `internal/toolhub` | 库编不出 32 位，手表用不了（3.8） |

## 3. 目标结构

```
 电脑端           手机端           手表端
 LinkClient      LinkClient      LinkClient        ← 同一套接口，路径选择在内部
    │  │            │  │            │  │
    │  └── 局域网 ──┼──┼────────────┼──┼──→ 局域网连接器（Gateway 内的薄监听）
    │               │               │
    └── ISCP ───────┴───────────────┴─→ Relay ─→ ISCP 连接器（独立进程）
                                                        │ Unix 套接字，双向帧
                                                        ▼
                                              ┌──────────────────┐
                                              │ Gateway 连接层入口 │  只认 Principal + 帧
                                              ├──────────────────┤
                                              │ 会话同步 │ 执行 │ 审批 │ 各业务域 │
                                              └──────────────────┘
```

三个概念：

- **连接层契约**（暂名 `sparkclaw.link.v1`）：一份与传输无关的消息定义。客户端、连接器、Gateway 都只依赖它。
- **连接器**：负责终止一种传输、验证设备身份、把帧转给 Gateway。有两个：局域网连接器和 ISCP 连接器。
- **Principal**：连接器验证完身份后交给 Gateway 的结果，内容是所有者、设备 ID、设备类别。业务代码只看到它，看不到授权、会话、Relay 这些传输概念。

### 3.1 连接层契约

以现有 Bridge 的 `agent.*.v1` 为起点（`iscpbridge/contract.go`）。它已经具备会话列表、发消息、取消、带游标的事件与续传、审批、操作状态、幂等键、能力清单。需要补的是分页读历史、变更游标、设备投影和双向帧。

帧只有五种：`hello`、`request`、`response`、`event`、`cancel`。每帧带 `id` 和 `type`。

握手时双方交换协议版本和能力集合，取交集。收到不认识的 `type` 返回 `unsupported_capability`，连接不断开。不再做操作表精确比较。

操作分三组：

| 组 | 内容 | 说明 |
|---|---|---|
| 核心 | 同步、会话、消息、运行状态、审批 | 三端都用，见第 4 节 |
| 业务域 | 邮件、药箱、设置、语音等 | 统一成 `domain.call`，带域名和方法名；Gateway 侧直接调业务函数，不再合成 `http.Request` |
| 设备能力 | 内嵌浏览器控制、麦当劳结算等现在的 11 个反向操作 | 行为保持不变：有内置浏览器的电脑端在握手时声明，后端通过同一条连接反向调用，见 3.12 |

大对象（附件、生成的文件）走单独的分块操作，不混在信号帧里。

客户端至少有三种实现语言（Go、Java/Kotlin、Swift）。契约必须先写成规范并附一套一致性测试样例。

### 3.2 Gateway 侧

新增一个包（暂名 `internal/link`），对外只有两个入口：

- `Dispatch(ctx, principal, request) → response`
- `Open(ctx, principal) → 双向帧流`（事件推送和反向调用用）

规则：

- `internal/gateway` 的业务代码不再导入任何 `iscp*` 包。
- 功能是否可用按 3.9 的规则在入口统一判断，不来自传输协商。
- 设备被撤销时，Gateway 通知连接器断开该设备的连接。

### 3.3 ISCP 连接器

独立进程，是 Bridge 的继任者：

- 复用现有的多对端应答器和授权续期代码（`iscpworkbench/node_*.go`、`grant_lifecycle.go`）以及 Bridge 的 Relay 收发代码。
- 凭证走官网的域模型（3.11）：后端作为域里的一台设备，持有与各端之间的授权，到期前自动续期。Bridge 已有这套代码的雏形（`enroll_ticket.go`、`managed_lifecycle.go`、`grant_lifecycle_client.go`）。
- 现有的 node issuer 路径在迁移期间原样保留给已装客户端，P4 时退役。
- 与 Gateway 之间用 Unix 套接字上的双向帧流。旧 Bridge 用的是一次一个 HTTP 请求（`/api/bridge/v1/dispatch`），做不了事件推送和反向调用。
- 连接器只能声明 Gateway 设备目录里存在且有效的设备，Gateway 每次都核对。

Gateway 升级时连接器不重启，远程连接只表现为短暂的请求重试。连接器或 Relay 出问题也不会拖垮 Gateway。

### 3.4 局域网连接器

留在 Gateway 进程内，是 `Dispatch`/`Open` 上的一层薄监听：TLS 证书固定（沿用 `pinned-https.mjs` 的做法）加 WebSocket。

设备身份和 ISCP 路径是同一个设备密钥、同一条设备记录。局域网握手由 Gateway 直接用本地保存的设备目录验证，不经过官网，所以断网时局域网仍可用。

### 3.5 信任配置

客户端只需要保存一个官网地址和它的信任根。开发期填自建官网，正式期填官网。域、绑定的后端及其公钥、授权、Relay 节点列表，都在加入域时由官网给出。

切换环境只换这个地址和官网适配器（3.11），连接层契约和其余客户端代码不变。

### 3.6 客户端

三端各有一个 `LinkClient`，接口相同：连接、请求、订阅、取大对象。路径选择在它内部完成：局域网和 ISCP 同时探测，局域网优先，失败退回 ISCP，切换后按游标续传。

- **电脑端**：主进程里用 `LinkClient` 取代 `DesktopAuth` 和 `ISCPTransport` 的分支逻辑。界面保持不变，只在原组件下换数据来源。
- **手机端**：gomobile 库从"透传原始操作名"升级为带类型的同步接口。
- **手表端**：同样走连接层（局域网和 ISCP Relay），用拉取档，见 3.7 和 3.8。

**宿主 WebChat 保留。** 后端主机上的网页版继续直接使用 Gateway 的本地接口，界面不变。它读写的是同一套会话表，所以跟随第 4 节的数据模型改动，并与三端看到同一批会话。

`LinkClient` 的 Go 实现是一个独立模块，只依赖 ISCP 包和连接层契约，不引用 Gateway 的内部包。

### 3.7 两种接入档

三端的运行条件差别很大，所以契约规定两种接入档，核心操作在两种档下都必须可用：

| 档 | 连接方式 | 实时性 | 适用 |
|---|---|---|---|
| 双向档 | 一条长连接，支持事件推送和反向调用 | 流式输出逐字到达 | 电脑、手机前台 |
| 拉取档 | 只有一问一答，没有长连接 | 靠 `run.status` 轮询拿当前快照 | 手表；手机后台短暂唤醒时 |

约束：**事件只是加速手段，游标才是事实**。任何靠事件能得到的状态，用 `sync.changes`、`session.messages`、`run.status` 也必须能拉到。

### 3.8 三端现状

2026-11-19 调查本机仓库和实机的结果。

| 端 | 平台 | 现在怎么连 SparkClaw | 本地存储 | 对方案的影响 |
|---|---|---|---|---|
| 电脑 SparkX | Electron 加 Go 辅助进程 | 局域网 HTTPS，或经辅助进程走 ISCP | SQLite，会话的事实源在本机 | 改成缓存角色，工作量最大 |
| 手机 JingSi Android | Java 11，最低 Android 9 | 两条：gomobile 库走 node issuer；局域网模式是明文 HTTP、无认证、手输 IP、只有一个隐含会话 | 远程路径存 `chat.json`，每轮最多带 31 条历史；局域网路径只存一个游标 | 局域网模式换成带认证的局域网连接器；本地会话退为缓存 |
| 手表 JingSi Watch | OPPO Watch，Kotlin，最低 Android 8.1，纯 JVM | 只有演示模式可用。代码里定义的官网接口没有调用方，真实配对未实现 | Room：离线事件队列、审批、状态。没有会话缓存 | 新写配对和连接层模块，用拉取档 |
| iOS JingSi | Swift | 有 ISCP 连接代码和官网接口客户端，未深入确认 | 未查 | 第四种客户端实现 |

手表是 32 位设备。实机（OPPO OWW261）的处理器架构是 `armeabi-v7a`，系统只有 32 位运行环境，Android 11，内存约 1.8 GB。

现有 gomobile 库只有 64 位构建。按 32 位编译时只有一处失败：`internal/toolhub/mcd_purchase.go` 里的一个常量溢出。ISCP 仓库的 `pkg/...` 在 32 位 ARM 下可以编译通过。所以独立的 `LinkClient` 模块（3.6）可以同时出 64 位和 32 位构建，手表和手机共用一份实现。

未验证：只做了 `linux/arm` 的编译检查，没有做 gomobile 的 `android/arm` 构建，也没有在手表上运行。

### 3.9 功能开放规则

功能默认对三端全部开放。只有设备自身做不到的才不开放。不做按设备的权限表，官网也不管理功能开放。

- **设备声明自身条件**：握手时客户端报告自己具备什么，例如有没有内置浏览器界面、能不能显示和选取附件、有没有麦克风、屏幕类别。
- **功能声明所需条件**：契约里每个操作标明它需要的设备条件。多数操作不需要任何条件。
- **后端在入口统一判断**：设备条件不满足时返回 `unsupported_capability`。局域网和 ISCP 两条路径结果相同。
- **界面**：握手应答里带上本设备可用的功能集合。有对应界面的端保留原入口并禁用不可用的操作；本来就没有该界面的端不新增入口。

| 功能 | 电脑 | 手机 | 手表 | 限制原因 |
|---|---|---|---|---|
| 会话、消息、审批 | 有 | 有 | 有 | 无 |
| 附件上传和下载 | 有 | 有 | 无，只显示文件名 | 屏幕和存储 |
| 邮件、药箱等业务域 | 有 | 有 | 有，内容按屏幕裁剪 | 无 |
| 设置 | 有 | 有 | 有 | 无 |
| 浏览器自动化的操作界面 | 有 | 无 | 无 | 没有内置浏览器 |

### 3.10 附件

附件和生成的文件随会话保存在后端，是消息的一部分，消息里只存引用。

- 客户端按需下载并在本地缓存。列表和消息页里只带文件名、大小、类型。
- 上传走分块，带内容摘要，可断点续传。消息发送时引用已上传完成的附件。
- 需要配额和保留策略：单文件上限、总量、删除会话时一并删除。具体数值在实现时定。

### 3.11 与官网的接口

官网一侧的设计见[自建官网设计](self-hosted-console-design.md)。连接层只依赖下面这些。

| 从官网得到的东西 | 谁用 | 用来做什么 |
|---|---|---|
| 域内身份：域 ID、本设备 ID | 设备、后端 | 握手时表明自己是谁 |
| 后端的设备 ID 和公钥 | 设备 | 确认对端是自己绑定的后端，局域网和 ISCP 都用它 |
| 设备与后端之间的短期授权 | 设备、后端 | ISCP 路径上建立会话；到期前自动续期 |
| Relay 节点列表 | 设备、后端 | ISCP 路径走哪里 |
| 域内设备目录和撤销状态 | 后端 | 后端保存一份副本，据此接受或拒绝设备 |

**官网适配器。** 客户端和后端各有一个模块集中访问官网，对外只暴露四个操作：加入域、取授权并续期、同步设备目录（仅后端）、退出域。连接层的其余代码不知道官网的地址和接口。开发期适配器对接自建官网，接入真实官网时只换这个模块。

**连接层不依赖官网在线。** 设备加入域之后，日常通信只需要授权没有过期。官网短暂不可用只影响新设备加入和授权续期，不影响已建立的连接。局域网路径完全不需要官网。

### 3.12 后端离线与设备能力

**后端离线时三端都不能工作。**

- 后端连不上时，发消息、审批、业务域操作都立即返回明确的错误，界面提示后端不在线。
- 不做离线发送队列。只有"请求已发出但没收到应答"的情况才用幂等键重试，用来确认结果。
- 已缓存的会话仍可以打开查看。
- 客户端不代替后端执行任何业务。

**SparkX 内置浏览器的控制保持不变。** 现在由电脑端提供的 11 个反向操作（`browser.controller.*`、麦当劳结算等）照旧：电脑端在握手时声明自己有内置浏览器，后端通过连接层反向调用。重构只改它们的承载方式，从 ISCP 操作表搬到连接层的反向调用帧，不改行为和界面。手机和手表不声明这项能力。

## 4. 会话同步

后端是唯一事实源，三端都是缓存。做法是把宿主 WebChat 已有的会话接口提升为唯一接口，再补上分页和变更游标。桌面和手机现有的"历史随每次请求上传"模型退役。

### 4.1 数据模型改动

| 表 | 新增 | 用途 |
|---|---|---|
| `sessions` | `revision`（单调递增）、`last_seq`、`preview`、`archived`、`deleted_at` | 变更游标、列表显示、归档跨端同步、删除墓碑 |
| `messages` | `seq`（会话内单调递增）、`client_message_id` | 按序号分页、发送幂等 |

不单独建变更日志表。"自游标以来的变化"就是 `revision` 大于游标的会话，按 `revision` 排序。状态大小只和会话数有关，不随时间增长。

### 4.2 核心操作

| 操作 | 作用 |
|---|---|
| `sync.changes(cursor, limit)` | 返回变化过的会话头：标题、`last_seq`、预览、归档和删除标记。重连后第一件事 |
| `session.messages(session, before_seq, limit)` | 向前分页读历史。打开会话取最近一页，上滑再取 |
| `message.send(session, client_message_id, content)` | 发消息。幂等键相同则返回原结果 |
| `run.subscribe(session)` | 订阅进行中的输出。先给当前快照，再给增量 |
| `run.status` / `run.cancel` | 查询和取消 |
| `approval.list` / `approval.resolve` | 审批 |

### 4.3 行为

- **缓存**：客户端本地保存会话头和已读过的消息页。启动先显示缓存，再用 `sync.changes` 对齐。
- **慢加载**：只有打开会话才拉消息，只拉最近一页。
- **流式输出**：进行中的预览只在内存里，不进 `seq`。完成后落成一条定稿消息。断线后重新订阅即可拿到当前快照。
- **多端同时在线**：同一会话的订阅者都收到同样的事件。同一会话同一时刻只允许一条消息在运行，第二台设备发送会得到冲突提示。
- **后端连不上时**：发送立即报错，不排队（3.12）。
- **设备投影**：设备记录里有设备类别。手表请求时后端返回裁剪后的纯文本和更少的条数，附件只给文件名。

## 5. 现有 159 个操作的去向

| 现有操作 | 去向 |
|---|---|
| `execution.*`、`events.*`、`approvals.*`、`phone.*` | 并入核心组。`phone.snapshot.get` 和 `phone.activity.list` 作为投影保留 |

## 6. 分阶段

| 阶段 | 内容 | 对已装客户端的影响 |
|---|---|---|
| P0 | 契约定稿；Gateway 的 `link` 包；会话表迁移和分页、游标；局域网连接器；官网适配器 | 无。旧路径原样保留 |
| P1 | 独立的 `LinkClient` Go 模块（64 位和 32 位构建）；ISCP 连接器进程，后端经它加入域，和现有 Gateway 内应答器并行运行 | 无 |
| P2a | 手机端切到新连接层。先用手机验证同步模型 | 手机需要新版本；本机旧会话被清除 |
| P2b | 手表补上真实配对，加入连接层模块（拉取档）。先接局域网，再接远程 | 手表需要新版本 |
| P3 | 电脑端：`LinkClient`、缓存与同步引擎，界面不变 | 电脑需要新版本；本机旧会话被清除 |
| P4 | 业务域逐个迁移；删除 Gateway 内 ISCP 应答器、操作表和 `workbench_iscp_*`；node issuer 退役 | 旧版本客户端不再可用 |

自建官网的排期见配套文档。它的 C1 阶段完成后，P1 就可以开始联调。

旧 Bridge 的 `agent.*.v1` 入口目前还被 JingSi 和 LocalMind 的 MCP 接入使用。本方案不动它们；新连接器是另一个二进制，只共用 Relay 收发代码。

## 7. 风险与代价

- **多一个进程**：需要单独监管和部署。
- **连接器是信任点**：攻破连接器等于能冒充任意有效设备。它和 Gateway 同机同信任域，用套接字权限和设备目录核对来收窄。
- **工作量集中在 P3 和 P4**：桌面端现有的本地存储要改成缓存角色，约 1.1 万行适配代码要迁移。
- **切换会删除各端本机的旧会话**：不可恢复，发布说明里要写明。
- **后端存储增长**：会话正文和附件长期保存在后端，需要配额和保留策略。
