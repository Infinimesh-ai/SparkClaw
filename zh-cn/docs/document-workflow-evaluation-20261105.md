# 文档处理编排评估 — 2026-11-05

语言：简体中文 | [English](../../docs/document-workflow-evaluation-20261105.md)

本轮从 `codex/document-system` 的 `db2e1841` 开始，将实际失败反馈到
文档读取 revision 7。仍然使用一个 workflow，节点内部可以检索、游标续读、
分批处理原文。目标是找到当前 Fast 模型能执行的编排契约。

## 输入与证据

将 `test-files` 中三个用户文档复制到隔离工作区：包含模拟访谈附件的
58 段 DOCX、含十个表格的 649 段学习手册 DOCX，以及 19 页 PPTX。
没有修改原件。补充的固定样例覆盖 Markdown 一般规则与例外、长风险台账、
纯文本比较、原生 PDF、扫描 PDF，以及含单位、取消项、过期公式缓存、
空白样式尾部的工作簿。另一个台账改变命中位置、编号和负责人。

全部任务执行生产 Runtime、路由、ToolHub、策略与 file store。Fast 使用当前
配置的 Qwen/Qwen3.6-35B-A3B-FP8 端点，OCR 使用配置的 OCR 端点。
真实验收没有 mock，也没有调用评审模型。仅在隔离的内部配置开启采集。
每次尝试均保留终态、模型与工具调用及封存导出，失败记录不会被成功重跑替换。
另用 16,000 字节证据预算检验小上下文链路，物理模型没有切换。

原始快照、维护副本、配置与 ZIP 保存在仓库外的
`test-files/document-evaluation-20261105`。仓库内保留可复现资产：

- `eval/document-workflow/generate_fixtures.py`：生成补充样例。
- 同目录 `cases.json`：十三项主要任务，含两项编辑。
- `variant-cases.json`：改变台账及改写计算、访谈核实问题。
- `analyze.py`：检查导出哈希、采集完整性、路由和事实项。
- `verify_maintenance.py`：检查原件哈希与精确的修改、格式保留范围。
- `TestRealDocumentWorkflowEvaluation`：显式开启的生产链路测试入口。

关键词与负向检查只是回归检查，不是语义评分。覆盖结论、限定条件、计算与
定位必须对照原文人工复核，不能以“关键词都出现了”直接判定回答正确。

## 缺陷与改动

| 实测缺陷 | 链路原因 | revision 7 的处理 |
| --- | --- | --- |
| 访谈材料的限制说明被漏掉 | 只读标题，没有读取声明为模拟的正文 | 定位限定条件、例外后读取正文证据 |
| 末尾七项检查只返回一项 | 把搜索命中当成完整章节 | 选择标题时展开同一来源的后代正文，保留兄弟章节边界 |
| 全文学习路线总结失败 | 误选逐项穷举并复制 185 个节点 ID，超过 64 个上限 | 区分全文总结与记录穷举；使用分节总结或运行时全文遍历 |
| 风险台账从标题编造负责人 | 把分页目录当成完整内容 | 声明全文或选定范围；全文由运行时设置 `all=true` 并续读 |
| PPT 只返回笼统失败 | 未解析图形压住了已读取的文字 | 在保留 blocked/partial 状态和限制的同时回答已有文字 |
| 小预算下耗尽工具次数 | 原文采集批次直接受模型证据预算限制 | 至少以 64 KiB 有界批次采集并归档，模型呈现单独受预算约束 |
| XLSX 明明总量能放下却丢掉主要批次 | 两个大小不同的批次被均分最终预算 | 按实际结构化证据大小分配，数值与依赖保持原子性 |
| 大台账读完仍无法进入最终模型 | 混淆原文采集完成与模型实际可见范围 | 任务模型逐批判断本地别名的相关性，程序保留选中的原文、定位和依赖闭包 |
| 分批筛选出现重复别名 | 复制两个长分类列表不稳定 | 严格布尔 schema、逐项校验、按原文顺序还原，最多 24 批 |
| 工作表选择器出现被截短的 ID | 长 ID 精确复制不稳定 | 优先选工作表容器；冻结范围前最多允许两次纠正 |
| 要求保留的最后一项自检丢失并被编造内容替换 | 通用分节压缩没有接收用户的保留要求 | 使用任务感知的总结契约 3 和按任务隔离的缓存，冻结旧契约 |
| 新节点 ID 与旧章节选择器冲突 | 新搜索输出原生 ID，旧 section 字段要求另一套 ID | revision 7 隐藏并去除旧章节选择器；历史计划保持不变 |
| 提取正确却声称抽样，并编造可能遗漏的编号 | 初始目录覆盖率、最终原文可见率与已完成分批处理相互混淆 | 分别记录历史目录发现、原文遍历、批次处理和最终选中证据的呈现范围 |

搜索范围不等于任务读取范围：全文搜索某章节，不代表用户要求全文读取。
源哈希、结构代次、已选范围和游标仍由运行时控制。初次选择失败可纠正，
但沿用源版本绑定；已经冻结的范围或续读失败不能重新选取范围。
历史 revision 4、5、6 冷恢复保留旧契约。

分批筛选属于任务执行，不是评估。每个非空文本或类型化数值片段必须收到
一个相关性判断，输出非法时放弃缩减并保留限制。模型不能生成原文、值或定位
来替换来源。依赖按传递闭包保留。采集明确区分“已完整遍历来源”和
“模型判断相关性”，不将后者认证为语义完整。

## 结果与文档维护反馈

revision 6 基线十三项中八项通过事实检查，五项失败分别是访谈性质核实、
尾部清单、PPT 比较、学习手册全文总结和风险全文提取。首轮五项重跑修复了
主要事实，但人工复核仍发现风险解释中编造了编号范围。随后的小预算测试
继续暴露上表的采集、投影、选择器输出与覆盖表述问题。所有中间失败均保留。

常规预算复测最初通过十三项粗粒度检查，但人工复核发现一个尚未解决的总结错误：
分节摘要漏掉了“开始写代码后先实现哪一层”的最后一项自检，最终回答又将其替换为
原文没有的 A/B 实验检查。加强样例检查后，保留的结果是 **12/13**，其中包含一项
明确部分完成的 PPT 回答。这不是 13/13 语义成功。同一七项清单的定点提取可以成功，
损失发生在中间通用摘要与最终重构，不在解析器。

总结契约 3 已将持久化、经过治理的原始任务传入每次分节和合并调用，要求保留用户
明确指定清单中的各项、原始定位与限定条件，优先压缩其他细节。任务内容也进入摘要
缓存身份；revision 6 保留契约 2 及原缓存行为。这是在修复信息交接缺口，而非让
最终模型猜回上游丢弃的细节。失败输出与加强后的检查仍保留。

变换台账的重复测试还暴露了过度筛选：32 片段批次保留了 32 个片段，依赖组合超出
最终呈现预算，导致前部一条真实命中无法进入回答。每批上限已降为 16 个片段，
并明确纯导航标题通过依赖保留，不作为匹配记录。代价是更多任务调用，收益是减小
单次分类负担；它仍然是模型判断，不是正确性证明。

首轮任务感知总结已在工具输出中保留七项原文，但最终回答仍选错另一份自检清单。
Revision 7 因而在长证据之后再次对照原始任务，优先保留指定清单而非可选展开内容。
随后的两项总结复测保留了七项自检与访谈限制说明。

模型调用。较小批次以更多调用换取较低的单次判断负担。

DOCX 维护任务只修改第 43 段标题，明确标注访谈为模拟且尚未真实开展。

独立检查器对全部 DOCX 包内容进行 XML 命名空间归一化比较，包括段落、
字体样式和其他正文，只有指定标题改变；Markdown 必须精确匹配指定替换。
用户原件与工作区源副本的 SHA-256 一致。这证明结构保留，不代表已验证

## 仍然存在的能力边界

- 即使清单内容完整保留，总结仍可能编造章节关系或相对位置，来源定位需要复核。
- 全文读完不等于语义提取正确。相关性、范围选择和最终措辞仍由模型判断，
  仍可能出错。本轮没有加入独立评审模型，也没有自动语义合格结论。
- 大提取最多 24 个任务批次，每批不超过 16 个片段并受证据预算限制。
  不可拆分的大片段或依赖、批次数超限、空选择、非法分类都保留限制。
  本轮没有增加跨进程恢复的分批缩减执行计划。
- 缩减只用于定点、穷举和比较任务。大工作簿汇总仍需要适配的计算策略；
  最终回答不会伪造公式重算，公式缓存继续作为观测值呈现。
- PPT 非文字对象、复杂布局和 OCR 不确定性仍保留 partial。
  返回可用文字，不意味着整份文档已被理解。
- 任务要求传入后，总结忠实度仍依赖模型。保留的失败说明全文覆盖标记不能认证
  摘要事实。全文总结的分节上限、大文档编辑限制仍存在。两项维护覆盖现有的小型编辑，
  不代表任意文档重构。
- 本轮覆盖支持格式及代表性任务，不等于 A01–A24 全部用户验收、统计准确率
  或原生 UI 验收。页面组件、传输与数据库 schema 未改动。

## 复现

使用 Node 26，先执行 `npm run setup:document-tools`。用项目 Python 环境
将样例生成到新的私有目录：

```sh
.tools/document-python/bin/python eval/document-workflow/generate_fixtures.py /private/new-workspace --owner-files /private/test-files
```

显式配置真实模型端点、绝对工作区与存储路径，并设置
`storage.execution_evidence.enabled=true`。本地隔离样例配置可允许在生产容器
沙箱外执行受支持的编辑；测试入口只批准该隔离工作区内的文档编辑 workflow。
不要指向用户原件或生产状态库。

```sh
SPARKCLAW_RUN_REAL_DOCUMENT_EVAL=1 \
SPARKCLAW_DOCUMENT_EVAL_CONFIG=/private/eval-config.json \
SPARKCLAW_DOCUMENT_EVAL_CASES="$PWD/eval/document-workflow/cases.json" \
SPARKCLAW_DOCUMENT_EVAL_OUTPUT=/private/new-results \
go test ./services/gateway/internal/agent -run '^TestRealDocumentWorkflowEvaluation$' -count=1 -timeout=40m -v

python3 eval/document-workflow/analyze.py --runs /private/new-results --output /private/new-analysis.json
python3 eval/document-workflow/verify_maintenance.py --workspace /private/new-workspace --owner-files /private/test-files --runs /private/new-results --output /private/new-maintenance.json
```

`SPARKCLAW_DOCUMENT_EVAL_FILTER` 接受逗号分隔的用例 ID。每次使用新的输出
目录。压力配置设置 `runtime.workflow_stage_evidence_max_bytes=16000`，
运行尾部清单、台账、工作簿，再运行 `variant-cases.json`。自动检查通过后，
仍需复核回答正文与冻结证据。
