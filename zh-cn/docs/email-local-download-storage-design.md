# 邮件本地下载、处理与窗口展示设计

> Language: [English](../../docs/email-local-download-storage-design.md) | 简体中文

状态：设计稿，创建于 2026-09-15，修订于 2026-09-16。本文把邮件获取后的本地文件落盘、解析入库和窗口展示收敛为一条链路；本次修订增加每个非空来源批次一份有界恢复日志、同一稳定 ID 的不可变原件冲突处理、有界信头探测后仅执行一次完整异步 MIME 解析，以及不进入调度索引、但可只确认视觉提醒的终态告警。普通网络轮询、失败分类、仅一次随轮补齐、溢出缺口和刷新遵循[邮件时间线增量同步、失败随轮补齐、刷新与留痕设计](email-timeline-incremental-sync-design.md)，该文专门细化此前的[邮件网络读取契约](email-pipeline-optimization-design.md)；不新增 DOM、菜单导出或 native 回退。

## 目标

用户在专用浏览器邮箱窗口中触发或等待同步。Reader 继续从已登录页面观察并重放真实网络请求，取得原始邮件字节；SparkClaw 先把原件保存到专属邮件目录，再解析、去重、分类和生成摘要，最后将可展示数据写入现有 Store 数据库。邮件卡片保留原件入口，用户需要核对原文时可预览或下载本地原件。

## 端到端流程

```text
专用浏览器网络 Reader
  → Controller 下载回执
  → Gateway 校验（owner/邮箱/稳定ID/大小/哈希/MIME）
  → 专属目录原子落盘
  → EML/MIME 解析与附件索引
  → Store 事务写入邮件元数据、正文表示、状态
  → 异步分类/事件归属/摘要
  → 邮件窗口读取数据库投影
```

每一步使用 owner、邮箱绑定代次、服务商稳定邮件 ID 与原件哈希组成的规范身份幂等。下载临时文件写入同一文件系统后原子重命名；普通轮询不为可重新获取的来源字节支付逐文件 `fsync` 屏障，每个非空来源批次改为在任何 rename 前持久一份有界恢复日志，空轮询不写日志。非正常关机自动检测并留痕，下一次定时轮询携带定向修复并同时发现新邮件，刷新则可提前触发同一有界轮次。检测本身属于运维失败，不消耗邮件级阈值；若同一稳定邮件 ID 随后在共享前置条件健康时连续两次来源同步失败，则进入 `sync_suppressed`，以后定时轮询和刷新对它都不再产生工作，并持续提醒 owner。校验失败的文件进入隔离目录并保留错误记录，不得进入窗口。

## 专属目录

根目录使用当前工作区数据目录下的专属邮件目录 `email/`，不接受模型或浏览器脚本传入任意路径。原件按接收日期和 owner、邮箱、邮件、确定性采集身份分层，规范化为十段路径；`capture-id` 只标识唯一获准的落盘实例，不是收件内容修订版本号：

```text
email/<YYYY>/<MM>/<DD>/<owner-scope>/<mailbox-id>/<mail-id>/source/<capture-id>/
  message.eml               # 不可变原件
  capture.json              # MIME、字节数、SHA-256、来源、日期证据和采集时间
  body.txt / body.html      # 解析出的正文表示
  headers.json              # 规范化信头
  parts/<part-id>/<name>    # 可选，按 MIME part 校验保存
```

`capture.json` 不含 Cookie、SID 或临时令牌。文件权限仅授予 SparkClaw 服务账号；下载接口只接受数据库中已提交的 source pointer，并再次检查 owner。

日期目录取自**原件 `Date:` 信头**，在字节落到 staging 后、唯一一次完整异步 MIME 解析前，由有界信头探测计算，再原子 rename 进日期目录。该探测只读取日期、身份依据和粗粒度信封合法性所需的有限信头，不解码正文 part 或附件。信头是字节派生的、带时区的、每次重放一致的证据；列表行显示文本在部分提供方是相对时间（如「今天 14:32」），无法可靠解析，因此只作为次选。回退链按序为：

| 序 | 来源 | `received_source` |
|---|---|---|
| 1 | 原件 `Date:` 信头 | `eml_date` |
| 2 | 列表行显示时间 | `list_row` |
| 3 | 本次采集时间（每次 attempt 只取一次，保证 attempt 内路径稳定） | `captured_at` |

`capture.json` 同时记录 `date_path`、`received_at`（RFC3339 UTC）、`received_source` 和 `received_display_text`（列表行原始文本，作时区证据）。Gateway 两处校验按段解析该路径而非重新拼接——日期无法在服务端预测，但其余每一段仍是对已持有值的精确等值比较，篡改面不变。

删除邮件记录时先写墓碑，再删除字节，避免数据库出现悬空链接。

## 数据库投影

沿用现有 EmailRepository 和三层模型，不再增加第二套邮件数据库或队列。`PublishEmailCapture` 事务同时写入原件 pointer、邮件身份、解析任务和来源状态；解析结果作为不可变 representation version；分类、事件和摘要只引用 representation version。

邮件窗口默认查询轻量投影：主题、参与者、接收时间、远端读状态、分类/事件、摘要状态和原件可用性。正文和附件仅在用户点击时按 pointer 读取。

原件入口鉴权使用 Bearer token 加四层 owner 校验（邮件归属、capture 归属、路径 owner scope 前缀、manifest 与邮箱身份三元组），不使用一次性签名 URL——凭证不进入 URL 和 Referer，实际更强。投影返回 `original_available` 布尔值而非 `original_url`，URL 由前端按固定路由拼接，避免数据库中出现第二个事实来源。

`original_available` 除了检查数据库 pointer，还对工作区做一次只读 stat：数据库里有指针不等于字节还在。文件被外部删除后窗口不再提供下载入口。原件被用户手动清理时另有 `original_purged` 标记，与「文件意外丢失」区分开。

## 去重与失败处理

- 同一 owner、邮箱绑定代次、邮箱与服务商稳定邮件 ID 只保留一份权威收件原件；重复列表项、标签和分页只增加观察记录，同哈希字节是幂等重放。
- 收件邮件不隐式产生内容更新版本。同一稳定 ID 后续返回不同字节且没有另行验收的服务商 revision token 时，保留第一份已验证原件、隔离后来的字节并记录 `source_conflict`。共享前置条件健康时，只有隔离到该 ID 的冲突才算邮件级；同组冲突算服务商运维失败。第一次合格冲突只精确重读一次，第二次连续合格冲突进入 `sync_suppressed`。未来若要支持服务商已证明的 revision，必须另行设计。
- 下载成功但解析失败：邮件仍可在窗口显示主题、时间和原件入口，解析状态为 failed，等待重试；解析／模型重试属于下游工作，不消耗来源同步抑制阈值。
- 解析成功但模型失败：保留正文和原件，摘要/分类显示 pending 或 failed；不阻塞采集边界。
- 普通服务商列表／范围结果不完整时，`poll_through` 不推进，下一轮从同一下界扩展到新上界；overflow 则冻结一个区间只确认一次，随后留下终态可见缺口并继续实时尾部轮询。只有原件或采集回执失败时，稳定 ID 记录第一次合格失败，发现水位可推进；下一轮或更早刷新只给该精确目标一次剩余尝试。第二次连续合格邮件级失败后标记 `sync_suppressed`；新邮件轮询继续，但该稳定 ID 永不再请求。不可变告警保留在分页历史中，owner 确认只消除角标／横幅打扰。

不可变来源按下表确定性决策：

| 同一稳定 ID 的观测 | 决策 |
|---|---|
| 尚无已接纳原件 | 校验后把该字节接纳为唯一权威原件 |
| 已有原件且 SHA-256 相同 | 视为幂等重放；不新建文件、解析作业或失败 |
| SHA-256 不同且没有已验收服务商 revision token | 保留第一份原件、隔离新字节、记录第一次合格 `source_conflict`，只安排一次精确重读 |
| 精确重读返回第一份已接纳哈希 | 解决冲突 attempt，丢弃隔离候选，原件不变 |
| 精确重读确认另一哈希或重复该隔离冲突 | 记为第二次合格邮件级失败并置 `sync_suppressed`；绝不原地覆盖任一来源 |
| 同轮两个以上 ID 出现相同冲突签名 | 整组提升为 `provider_operational`；不消耗任何邮件的两次阈值 |
| 服务商以后暴露已验收 revision token | 不自行推断版本；在独立修订设计被接受前，该更新路径保持未验收 |

## 删除的冗余路径

删除以下重复职责：DOM 读取和页面点击导出；脚本向任意 localhost 上传；Gateway 再复制一份原件；以未读为独立发现通道；正文默认进入列表投影；摘要反向触发分类或事件循环；多个定时器重复扫描同一邮箱。保留网络 Reader、Controller→Gateway→Store 单一路径、采集时一次有界信头探测、来源提交后恰好一次完整 MIME 解析、独立分析任务和按需正文读取。

“只解析一次”不等于采集阶段完全不读字节。网络采集流必然写完整 EML，并在线计算大小与 SHA-256，但只检查有界信头块；提交后，异步解析器才执行唯一一次完整语义读取，在同一遍中解析 MIME 结构、正文与附件，并在线计算所需复核哈希，不另开纯哈希重读。因此普通同步不存在提交前完整 MIME 解析、提交后再次完整解析，也不存在独立的全文件哈希遍历。以后用户下载、备份恢复或显式损坏检查属于按需校验，不是每轮轮询成本。

## 历史文件与附件

切换时直接删除旧接收链路及其历史，不做迁移，也不保留运行期兼容分支。先停止接收，再删除除邮箱绑定外的全部邮件管理记录，并清空专属 `email/` 目录内容。仅保留邮箱地址、提供方、连接状态和接收开关；激活边界与同步边界统一重置到固定部署锚点。新链路中的附件现阶段不进入正文查看或模型分析，但必须与所属邮件保持关联；原始 EML 始终保存，解析出的附件按 MIME part 保存并记录名称、MIME、大小、哈希和 pointer。

## 安全、容量与运维

原件和附件受单文件大小上限、单次采集总量上限和 owner 隔离保护；超限进入明确失败状态。`capture.json`、数据库 pointer 和实际文件在每次读取时按大小与 SHA-256 完整校验。备份必须同时覆盖数据库与 `email/`，恢复后先校验哈希再开放窗口。日志只记录 source ID、版本、大小、哈希和错误码，不记录正文内容。

原件默认永久保留，不自动过期；用户可手动清理单封邮件、日期目录、单个邮箱或全部原件，清理后保留「原件已手动清理」状态。系统对工作区容量做告警：已用达 85% 或剩余低于 2 GiB 为 warning，已用达 95% 或剩余低于 512 MiB 为 critical。告警只提示用户并提供手动清理入口，**绝不自动删除任何文件**。

## 实施顺序与验收

1. 打通日期目录：Controller 按 `Date:` 信头分目录、staging 移出日期树、写入 `index/` 指针；Gateway 两处校验改为按段解析。
2. 采集只执行有界信头探测；解析器只消费已提交 `message.eml`，恰好一次完成 MIME／正文／附件解析并写入 representation；解析所需完整性哈希随同一次读取在线计算，不再另开重读遍历。
3. 窗口改为数据库轻量投影，加入 owner 校验的原件入口、按需正文加载和真实的可用性探测。
4. 四级手动清理、启动时有界失败检测、仅一次定时随轮修复、终态 `sync_suppressed` 与 owner 提醒、立即刷新触发和容量告警；清理旧 DOM/native/unread 分支及重复调度器，更新文档与配置迁移。

验收覆盖：同一邮件重复发现不重复落盘，同 ID 不同哈希的重放绝不覆盖第一份已验证原件；断电或进程终止后，半写入或哈希无效文件绝不对用户可见；日志发布前崩溃不发生最终目录 rename，并由有界陈旧 staging 清扫处理，日志发布后的任一崩溃都可按精确路径恢复，不扫描日期树、不产生最终目录孤儿；空轮询日志写入与 `fsync` 均为零；中断会留下由下一轮或更早刷新修复的持久失败记录；同一稳定 ID 第二次连续合格邮件级失败后产生持久提醒，后续定时轮询和刷新对它的来源请求均为零；网络、登录、服务商全局模板、磁盘容量、权限和 Store 失败绝不消耗该阈值；哈希/MIME/owner 校验拒绝伪造回执；解析或模型失败仍可查看原件；链接只能访问所属邮件；备份恢复后链接可用；零新增同步不触发下载、解析或模型调用。

本设计不改变跨项目接口或协议；若未来需要让其他项目直接读取邮件原件，应先在 InfiniCenter 建立并接受契约。

## 已确认的实现决策（2026-09-15）

- 日期目录使用邮件接收时间；解析为稳定时间后按 `YYYY/MM/DD` 存储，并保留原始显示文本和时区证据。
- `emailWorkspaceRoot` 是 Browser Controller 的宿主配置项，由 `SPARKCLAW_BROWSER_EMAIL_WORKSPACE_ROOT` 设置；默认值为项目 `data/workspaces`。邮件目录固定放在该工作区内的 `email/`，文件处理不越出工作区。相关配置入口见 `tools/browser-controller/src/main.mjs` 与 `scripts/setup-browser-controller.sh`。
- 切换新规范时，旧接收链路、旧邮件／分析／作业／检查点记录、旧文件与旧附件全部删除；仅保留邮箱绑定及启停设置，激活边界与同步边界统一重置到固定部署锚点。
- 原件提供安全解析预览和原始 `.eml` 下载两种入口。
- 手动清理分为单封邮件、日期目录、单个邮箱、全部本地邮件四级，不要求二次确认；清理后保留邮件元数据和「原件已手动清理」状态。
- 收件邮件按不可变原件身份处理，不隐式设计内容更新版本。同 ID／同哈希幂等；同 ID／不同哈希是 `source_conflict`，不能覆盖第一份已验证来源。多邮件对话通过既有事件划分和成员关系表达，不复制或覆盖原件。
- 单邮箱下载按现有共享浏览器会话串行处理，并发发生在邮箱之间；单批最多 50 封。第一次合格邮件级失败保留在 checkpoint 中但绝不暂停邮箱；下一轮携带失败一次，并同时发现新邮件。该唯一剩余合格尝试仍失败时，稳定 ID 进入 `sync_suppressed`，以后不再由定时任务或刷新重新排入，只保留 owner 提醒。调度索引排除其详情行，确认操作只改变界面未确认计数。
- 文件已落盘而数据库事务失败时，启动阶段只记录未解决 attempt；Store 失败属于运维失败，不增加邮件级计数。Store 恢复后，下一次定时轮询或更早刷新校验 manifest、大小和 SHA-256 后补登记，不重复下载。
- 保存全部可识别 MIME part，包括内嵌图片；当前界面只显示附件元数据和下载入口，不查看或分析附件内容。
- 原件永久保留，不自动清理；仅用户手动清理。系统增加工作区容量告警，达到告警阈值时提示用户，但不自动删除文件。

## 实施补充（2026-09-15）

### 日期来源与 staging

日期只有在字节已落到足以完成有界信头探测后才可知，不需要完整 MIME 解析。因此 staging 不能再位于日期树内。staging 根为 `email/<owner-scope>/staging/<mailbox-id>/<mail-id>/attempt_<invocation-hash>/`，与 `invocations/`、`pages/`、`index/` 并列，处于同一文件系统，提交仍是单次原子 rename；日期树只包含已完成的采集。

### `index/` 指针与重放

已提交的采集位于由邮件内容决定的日期目录下，重放时无法仅凭稳定身份反推该路径。因此保留一个与日期无关的普通查询加速指针：

```text
email/<owner-scope>/index/<mailbox-id>/<mail-id>/<capture-id>.json
```

该指针可重建，不承担断电恢复权威。timeline-v2 为每个非空来源批次新增一份确定性日志：

```text
email/<owner-scope>/journal/<mailbox-id>/<invocation-id>.json
```

有界日志不含凭据或正文；每项只记录稳定身份、capture ID、staging 路径、最终路径、大小、SHA-256 与预期 Store 命令键。提交顺序为：

1. 每封来源和 `capture.json` 写入 staging，再计算最终日期路径。
2. 全批条目写入临时日志；只对这一份文件执行 `fsync`，原子 rename 到 `journal/`，再对日志目录执行一次 `fsync`。
3. 写入或刷新可重建 `index/` 指针，并把各 staging 原子 rename 到日志记录的最终路径；来源文件、index 文件和单封目录都不单独执行同步屏障。
4. 执行确定性 Store 批量命令；只有 Store 确认该命令已提交后才删除日志。日志持久发布前尚未 rename 任何来源；之后断电必然留下 Store 事实或可精确对账的日志路径。Store 已提交但日志残留时，只需验证并回收。

因此每个非空批次固定支付两次持久化屏障，而不是每个文件或每封邮件两次；空轮询零屏障。它封闭了“最终日期树保留下来，但 Store 记录和可重建 index 指针同时丢失”的窗口。来源字节仍可重新获取：若有效 staging 与最终目录都未保留，恢复按稳定 ID 定向重读。最终 manifest 不存在的指针绝不视为完整采集；已完全落盘且校验通过的 capture 免下载收养。检测属于运维失败，不消耗两次邮件阈值；只有共享前置条件健康后的服务商单封重读失败才计数。

来源批次崩溃矩阵如下：

| 崩溃点 | 持久证据 | 恢复方式 |
|---|---|---|
| 写 staging 期间、日志发布前 | 没有最终来源，也没有已发布日志 | 后续有界陈旧 staging 清扫删除遗留 attempt；任何内容都不能展示或收养 |
| 日志文件 `fsync` 后、日志目录 `fsync` 前 | 断电后日志可能未发布；来源 rename 尚未开始 | 与日志发布前 staging 相同处理；最终目录仍未触碰 |
| 日志持久发布后、任何来源 rename 前 | 精确 staging／最终路径、哈希、身份与 Store 键 | 校验 staging 后完成安全 rename，或只留下一个精确定向重读目标 |
| 部分或全部来源 rename 后、Store 提交前 | 同一日志加已经落到最终目录的树 | 校验并收养已落盘 capture，完成其余有效移动；绝不扫描日期树 |
| Store 提交结果未知 | 日志和确定性 Store 命令键 | 先查询／重放命令键；不得生成第二份 capture 或重复推进 checkpoint |
| Store 已提交、日志尚未删除 | Store 事实和陈旧日志 | 校验已提交结果并回收日志；不请求服务商重读 |

因此唯一可能没有日志的残留只会是发布前 staging；它不对用户可见，也不在日期树内，并由有界陈旧 staging 趟删除。一旦任何来源可以进入最终目录，持久日志已经成为恢复权威。

### purge 用字段而非第四个状态

`PurgedAt *time.Time` 是「这些字节必须不存在」的唯一权威，而不是给 `CaptureState` 增加第四个取值。`CaptureState` 被采集跳过判断、页批次短路、解析与标记已读触发、计数与投影多处消费；新增状态会把已清理邮件踢出 `complete`，采集任务随即把用户刚删的字节重新下载回来。可空时间戳恰好保住需要的语义：这封采集过，字节按用户要求已删除。

purge 后的存活情况：

| 数据 | 结果 |
|---|---|
| representation 正文 | 存活——清理后预览照常工作 |
| 附件 `Path` | 存活（审计用） |
| 附件 `State` | 置为 `purged` |
| `CaptureID` / `CaptureState` | 存活，保持防重采守卫 |
| `ManifestPath` / `OriginalPath` / 两个哈希 | 存活，是删除目标与恢复任务的墓碑证据 |

### 清理顺序与崩溃矩阵

序列为：① 数据库写墓碑 → ② 逐条删除 `dir(ManifestPath)` → ③ 非递归上溯剪枝空祖先目录（遇 `ENOTEMPTY` 即停，绝不触碰 `email/`）→ ④ 按游标续批。

| 崩溃点 | 磁盘 | 数据库 | 修复者 |
|---|---|---|---|
| 步骤 ① 提交前 | 文件在 | 未盖墓碑 | 无需修复，用户重试 |
| ① 后 ② 前 | 文件在 | 已盖墓碑 | 恢复任务第一趟 |
| ② 中途 | 部分已删 | 已盖墓碑 | 恢复任务第一趟（删除幂等） |
| ② 后 ③ 前 | 空祖先目录 | 已盖墓碑 | 恢复任务第一趟剪枝 |

**不存在「数据库宣称有字节而字节已消失」的窗口**——这正是墓碑优先的意义。反向窗口是安全的：下载接口在碰文件系统之前就因墓碑拒绝。

枚举一律走数据库查询而非文件系统遍历：owner scope 是哈希，遍历无法映射回 owner；授权必须由数据库派生；数据库是墓碑权威；且各 scope 都是索引化游标查询，全树遍历对单封清理是 O(全部采集)。

### 由定时同步与刷新复用的本地恢复 worker

既有 owner 级 `source_recovery` 机制继续作为实现原语，但 timeline-v2 改变它的触发方式：启动只检测并记录未解决运维失败，下一次定时复合同步或更早的用户刷新调用对账；检测和本地收养不消耗邮件级阈值。墓碑清理由显式清理操作继续触发。该 worker 与解析 worker 共用槽位，不带邮箱，也不占用模型 worker。四趟有界处理：

1. **未完成日志对账**（每次最多 16 份日志、50 个邮件条目）。先确认 Store 命令结果，再校验精确最终路径或 staging 路径；收养完整来源、完成安全 staging rename，或留下一个精确定向重读目标，绝不遍历日期树。
2. **墓碑 → 删除**（上限 200）。按 `purged` 状态索引查找，删除后标记为已回收，避免索引无限增长。
3. **已有 index 的落盘来源 → 免下载补登记**（上限 50 封）。由仍未提交 capture 的已接纳邮件定界；有效 `index/` 指针只作为次级加速，按记录大小和 SHA-256 重哈希并核对身份三元组后登记。补登记走独立 adopt 路径且仅可填补空缺：邮件已有采集则不动，采集 ID 已存在则冲突，竞争中实时采集恒胜。
4. **陈旧 staging 清扫**（上限 200）。删除 mtime 早于两倍作业超时、且没有被未完成日志引用的 `attempt_*`；更年轻的一律跳过。
三个抗竞争守卫：跳过租约未过期的运行中采集作业；补登记使用确定性命令键，与实时发布在既有重放/冲突逻辑中正面相遇；staging 按 attempt 新建因而在途者天然年轻。

### 部署锚点验证

本轮接收验证将部署锚点固定为 `2026-09-11T00:00:00Z`，文件为 `data/workspaces/.sparkclaw-deployment.json`。服务启动后应调用 `GET /api/email/sync-status` 检查 `coverage_start` 是否从该锚点开始。timeline-v2 中，调度器只把仍可重试的首次邮件失败携带到下一次普通增量轮询；owner 可使用 `POST /api/email/sync/refresh` 立即运行同一复合轮次。已抑制 ID 只保留告警：两条路径都不会重新排入或扫描其详情行，状态接口只读取事务维护的汇总计数。服务未运行时不产生接收效果，连接失败必须留痕，不能误判为零邮件。
