## 1. 目标与现状

窗口语言跟随设置；主要区分“信息通知”和“需确认／交互”的邮件。分类依据是当前事项是否需要
确认、答复、决策或继续沟通，不判断由谁负责处理，也不以官方／个人、机器／人工发件为主分类标准。
用户自行决定如何处理；系统负责分类、组织完整对话，并提供主动写信和回复功能。
保留顶层“对话／待归属邮件”，对话板块中设置“信息通知／需确认与交互”。
验证码、广告、常规账号登录提醒属于信息通知；通知内部可用验证码、广告、账号安全、一般通知标签筛选，
不把这些标签扩展为更多主分类。
验证码展示用途、来源时间及有证据的有效期；收件及时性优化按用户确认留待后续，不属于本次设计或验收范围。

方案提出时的代码基线：

- `App.tsx` 已向邮件弹窗传递 `text` 和 `language`，常规按钮使用中英字典，日期使用当前语言。
- `emailPopup.tsx` 直接显示后端标题、摘要、疑点依据和 `Error.message`，仍可能出现英文内容。
- `emailmanagement/model.go` 的模型输入没有目标语言，也没有通知分类输出；所有可归属邮件进入同一对话模型。
- 语言偏好目前保存在当前浏览器的 `sparkclaw.language`，不是后台已持久化的 owner 设置。

因此本次同时设计界面文案本地化、生成内容的语言投影及邮件分类，不能仅补几个按钮翻译。

## 2. 信息架构与窗口交互

```text
邮件
├─ 对话
│  ├─ 信息通知（验证码、广告、账号安全、一般通知）
│  └─ 需确认与交互
└─ 待归属邮件
```

顶层保留现有结构；默认打开“对话／需确认与交互”，之后记住当前设备最后选择。
来源邮箱筛选、搜索和未查看计数覆盖对应子类的完整已接纳数据，不是只筛选已加载页。
切换分类重置分页游标，保存各子类选择；刷新与语言切换不丢失当前详情。

| 视图 | 列表与详情 |
|---|---|
| 需确认与交互 | 参与者、事项标题、需要确认／回复的内容、对话摘要及完整时间线；包括官方和个人发送的邮件 |
| 信息通知（非验证码） | 默认逐封通知卡片：服务名称、事项、来源时间、摘要；详情保留正文、附件、原件 |
| 验证码通知 | 默认逐封：服务名称、用途、时间、有效期状态；详情可显示并主动复制可靠提取的验证码 |
| 待归属邮件 | 尚未取得可展示邮件资料等接纳／解析异常；保留恢复入口。分类不确定和对话未归属邮件直接在交互入口显示 |

信息通知包括验证码、广告、常规登录提醒、已支付账单回执、订单状态及订阅资讯。
要求核对账单、确认交期、补交材料或答复问题的邮件进入交互类，即使来自官方自动发送地址。
一般通知首版不按同一发件地址自动聚合，避免订单和事务互相覆盖。验证码不合并成永久对话，旧码保留可追溯。
验证码列表默认遮盖码值；进入详情主动显示/复制，复制不等于已使用。
不自动回复通知、不提交验证码、不点验证链接、不自动删除过期邮件。
本地查看继续按实际呈现的 mail_id 记录；计数、分类、过期、远端已读和处理失败相互独立。

## 3. 分类边界与分析流程

主分类采用互斥的 `notification / interaction / unknown`；unknown 表示暂未判定，不是第三类业务邮件。
通知子类型为 `verification / promotion / account_security / general`，仅用于筛选和卡片呈现。
非通知的 subtype 必须为空；验证码提取字段只对 verification 生效。
`unknown` 是分析结论而非入口：没有人工规则时有效入口一律为 interaction，显示“分类待判断”。
分类待分析、模型失败或交互对话未归属也在交互入口以独立邮件卡片展示，不等待建对话才可见。
卡片后续归属成功替换为对话成员投影，按 mail_id 去重，不留下重复入口。
处理状态另存 `queued / running / ready / failed / stale`。

1. 原件和正文已提交后先查询人工发件地址规则，再进行正文分类；使用规范化正文、可信来源字段及已解析邮件头，不重复启动浏览器。
   本阶段所有邮件模型任务（分类、归属、摘要、关系检查和语言投影）均不读取附件或附件提取结果；附件保留供用户下载查看。
2. 确定性收集 `Auto-Submitted`、`List-Id`、群发信息、发件地址模式、模板结构、验证码用途片段及回复证据。
   缺失头字段记录为未知；`no-reply`、数字串或发件地址都不能单独决定类别。
3. 复用现有 Fast 分析通道生成严格结构化分类及证据，Runtime 校验类别、来源引用与输入版本。
   无法判断、模型失败或证据冲突且无人工规则时进入交互入口，记录原因，由用户判断。
4. 有效入口为 `interaction` 的邮件进入现有候选检索及 append/new/pending 归属流程。
   分类兜底不代表关系已确认：证据不足时保留独立卡片，不强行追加或为每封创建永久对话。
   `notification` 发布逐封通知投影，不新建交互对话，不进入常规对话候选池。
5. 单封摘要与显示语言投影异步生成；分类成功但摘要暂不可用时，卡片仍可查看。
   验证码不等待历史补齐或对话摘要才能展示；正文不足时走交互兜底。
6. 新证据触发有界重分析；所有任务复用原件，以输入指纹去重并持久化重试。

分类边界与例子：

| 邮件内容 | 主分类 | 判断依据 |
|---|---|---|
| 登录验证码、注册验证链接、常规登录成功提醒 | 信息通知 | 提供账号流程信息；输入验证码／点击验证链接本身不算邮件事项交互 |
| 优惠广告、“立即购买／回复领取优惠” | 信息通知 | 泛化营销号召不等于需要用户回应的具体事项 |
| 发货状态、已付款回执、工单已收到 | 信息通知 | 只告知既成事实，没有当前待确认事项 |
| 请确认合同版本／交期、核对账单、补交账号资料 | 需确认与交互 | 明确存在需要用户处理的具体请求，官方、no-reply 或平台发件也适用 |
| 询价、会议邀请需确认、客服追问、同事讨论 | 需确认与交互 | 需要答复、决策或后续沟通 |
| 普通登录告知附带“若非本人请处理” | 信息通知 | 条件式通用安全提示不直接证明当前需要处置 |
| 已检测异常且要求核实／申诉／恢复账号 | 需确认与交互 | 明确异常事项和待处置请求，不能仅因官方通知模板而漏掉 |
| 既有事项中的“已确认／已完成，谢谢” | 需确认与交互 | 属于交互事项的延续或收尾；此封无待办也保留上下文 |
| 证据不足，或正文仅为“详见附件” | 需确认与交互 | unknown + 交互兜底，标明未分析附件／分类待判断，让用户处理 |

一封邮件兼有通知和明确事项请求时，交互类优先；验证码及泛化营销号召按上述例外判断。
“需确认与交互”表示事项类型，不等于每封都有尚未完成的任务；本次不新增待办状态机，
不因读过、已回复、事项收尾而自动改成通知。可在摘要中说明所需回应，不能据此自动执行。
个人发送的纯信息转发也可以是通知；发件身份、自动发送头和原生线程仅作辅助证据。
自动回执可与相关交互对话链接，但不因同一 provider thread 强行归并。
验证码只提取明确属于本封当前验证动作的证据，排除引用旧码；账单编号、订单号、手机号均不是验证码。
人工转述或多用途歧义不自动开放验证码快捷复制。

建议模型分类输出：`category`、`notification_subtype`、`purpose`、`service_label`、`evidence_refs`、`reason_code`、
`uncertainty`、`missing_context`、`requested_response`（仅陈述原文请求，不分配责任人）及可选 `verification`。验证码包含候选码值、用途与有效期的具体证据引用。
Runtime 从引用的正文片段核验码值原样存在；多码/多用途不明确则不提供一键复制，仍可查看正文。
邮件中的指令属于分析资料，不能改变模型契约、执行动作或指定任意来源 ID。


## 3.1 人工修改与发件地址规则

每封邮件提供“改为信息通知／改为需确认与交互”。操作文案明确说明：修改当前邮件，并记住该发件地址，
以后同地址邮件进入所选入口。保存前展示实际发件地址，不根据显示名称建立规则。
规则范围为同一 owner 下的已解析 From 完整邮箱地址，跨其收件邮箱生效；不扩大到整个域名、联系人别名或 Reply-To。
地址按既有邮件地址规范规范化；域名不区分大小写，本地部分不擅自去点、删除加号后缀或合并大小写变体。
地址缺失／多义时只允许修改当前邮件，并明确不能建立地址规则。

优先级：当前邮件人工选择 > 有效发件地址规则 > 模型分类 > 不确定时交互兜底。
规则保存后即生效，未来接纳邮件在发布分类前再核验规则版本；进行中的分析也不得用旧结果覆盖规则。
修改当前邮件不批量改写该地址的历史邮件；其他已接纳邮件默认保持，用户可逐封修改。
提供规则列表、修改入口、停用／删除规则；同地址再次修改更新现有规则，最新已提交版本生效。
删除规则只让后续邮件恢复自动分类，不撤销既有逐封人工选择；并发修改用 expected_version 拒绝过时请求。

人工规则决定主入口，不会让模型捏造验证码子类；通知子类无法确认时用 general。
人工将某地址设为通知后，其后续交互内容也按用户规则进入通知，显示“按你的发件地址规则分类”，便于改回。
记录作用邮件、规则 ID／版本、修改时间和分类来源；人工修改不改变原件、查看记录或已提交对话成员。
发送给该地址的出站邮件不匹配发件地址规则；从本人邮箱发出的回复沿用显式选择的管理对话。

## 3.2 对话组织、上下文与当前状态

交互入口按事项组织，不按发件地址把所有邮件塞进一个对话。相同地址可有多个事项，多个参与者可继续同一事项。
沿用阶段 3 的有界候选与版本校验；使用本封新正文、可信回复关系、已提交历史正文和摘要。
优先当前关联对话，必要时检索有限相关候选；实际输入引用和截断范围必须记录，超出输入预算不冒充读完历史。
过滤附件内容及依赖附件的旧摘要；由纯正文重新生成所需摘要，避免通过历史摘要间接识别附件。
正文提及附件只标注“附件未分析”，不能推断附件内容；附件变化不触发本阶段的语义重分析。

区分三个信息：类别是通知／交互；本地查看是未查看／已查看；摘要中的请求是正文所陈述的确认／回复事项。
本次不维护任务完成状态、不推断谁负责，也不把已读、已回复推定为已处理。
交互收尾邮件留在原事项，时间线完整保留收发方向、来源邮箱、参与者、附件下载及原件。
已有归属固定；疑似重复／待修正可显示依据和相关对话链接，分类修改不执行合并、拆分或搬移成员。

## 3.3 写信与回复

在邮件窗口提供“写邮件”；单封邮件提供“回复／回复全部”，通知也可由用户主动回复。
这是本次拟议功能的端到端交付要求，不能以底层存在 send 能力冒充窗口已经支持。
用户选择已验证且允许发送的邮箱，编辑 To／CC／主题／正文；回复默认使用原收件邮箱，切换时明确显示。
回复目标绑定具体原邮件及其 provider 定位，按有效 Reply-To（缺失时 From）预填；回复全部展示去重后的收件人，排除已知本人地址供用户核对。
保留原生回复关系；不能用仅带 Re: 标题的新信冒充回复。无法证明回复目标时保留草稿并提示，不退化为静默发送新信。

用户点击发送才执行，不因分类、摘要或邮件内容自动发信。复用现有 owner 鉴权、发送开关及发送执行通道；
首版编辑器至少支持纯文本新信、回复、回复全部，附件下载保留，上传附件与富文本编辑留待后续。
草稿由 owner 隔离持久化，编辑版本与发送快照绑定，失败保留内容；通知类邮件发起回复时显式建立或关联交互事项，原通知归属不变。
发送请求持久化幂等键和状态，防止双击、刷新、超时重试重复发送。远端结果不确定时显示“发送结果待确认”，
先核对已发送证据，不自动再次发送；明确失败才允许用户重试。成功收据不伪装成收件人已收到。
已发送邮件通过实际发送证据及后续 Sent 来源核对进入同一管理对话；本地发送记录与采集副本关联去重，
原生头字段不足时保留待核对状态，不编造 Message-ID。不同收件账号切换遵守现有绑定隔离。
实现与实机验证状态见第 8、9 节；实现测试不发送真实邮件。

## 4. 已采集验证码的有效期展示

持久事实包括用途、来源发送/接收时间、明确有效时长或截止时间、时间依据及提取版本。
验证码值作为受 owner 文件/邮件授权保护的字段，不进入列表搜索、通用摘要、日志和通知预览。
模型分类需要正文时仍可在既有受控分析通道中处理原文，不能声称模型从未接触验证码。

状态规则：

- 有明确绝对截止时间或“自发送起 N 分钟有效”且起算时间可靠：计算 `expires_at`；仅显示“按邮件说明未过期／已过期”。
- 只有“N 分钟有效”但起点不可靠、日期/时区冲突或时间异常：`validity_unknown`，显示“有效期未知”，不制造倒计时。
- 未写有效期：同样显示未知，不统一假定 5 分钟或 10 分钟。
- 验证码是否使用、撤销或被新码替代无法从邮件确定；新码到达不擅自判旧码作废。
- 已过期卡片保留在验证码历史中，不再显示成可用码；过期本身不触发模型任务或改变查看记录。

后端返回 `server_now`、`expires_at` 与时间依据，前端依据服务器时间差刷新倒计时，恢复焦点后重新校准。
未知时效不进入“按邮件说明未过期”筛选，默认列表按时间倒序并明确状态，已过期记录仍可检索。

用户于 2026-09-09 明确：邮箱获取信息的及时性暂不考虑，后续持续优化。
本次只处理已经采集入库的邮件，不设计轮询提速、实时收件或验证码专用优先调度，
也不把这些能力作为实施依赖或验收门槛。验证码有效期展示仍以邮件证据为准。

## 5. 语言一致性

唯一 UI 语言来源沿用设置中的 `Language = zh | en`，不增加独立邮件语言开关。

| 内容 | 规则 |
|---|---|
| 按钮、分类、状态、空态、提示、无障碍文本 | 全部使用 `text.email` 等现有字典，切换即生效 |
| 日期、数字、有效期 | 按当前 language 格式化，时区沿用当前应用约定；存储时间为 UTC |
| API/脚本错误 | 稳定错误码映射本地化文案；未知错误用本地化通用提示，技术诊断留在受控详情 |
| 模型事项标题、摘要、分类说明、疑点依据 | 发布当前语言投影，记录语言和来源分析版本 |
| 原始主题、正文、地址、服务专名、附件名、原件 | 原样保留，明确标为原始内容，不伪装成已翻译 |

建议把事实分析和语言呈现分开：归属与分类基于原文和结构化事实；标题、摘要、疑点说明按
`owner + target + target_kind + analysis_revision + language + prompt_version` 缓存。
语言切换只请求缺失的语言投影，不重新分类、归属、采集或重置查看。
后台初次分析可产生带 language 标记的基础摘要；首次打开窗口用当前设置按需请求目标语言。
GET 只读取缓存；缺失投影由显式幂等 POST 排队，不通过 GET 触发模型或写库。
不新增 owner 全局语言偏好，不让同时打开的中英文设备相互覆盖。

未生成当前语言时显示本地化“正在生成中文／英文摘要”；可主动展开标注语言的旧版本，
不能默认把旧英文摘要当成中文结果。失败显示本地化状态并允许重试，原文依旧可访问。
语言版本和分析依赖一起做条件发布；切换中迟到的英文结果只能进入英文缓存，不能覆盖中文视图。
生成请求显式包含 `output_language`，要求所有面向用户的解释使用该语言，代码枚举不翻译。
旧英文标题不能简单改 language 标签；须创建真实语言投影。无需预先为全库生成双语副本。

## 6. 持久化、查询及兼容

下列均为拟议内部结构和 API，不是已上线接口。

| 结构 | 关键约束 |
|---|---|
| EmailClassification | owner/mail_id、模型 category、有效 entry、分类来源（manual/rule/model/fallback）、notification_subtype、state、input_fingerprint、analysis_revision、规则版本、证据、reason_code |
| EmailSenderRule / MailOverride | owner、规范化完整 From、目标入口、rule revision、生效时间／停用状态；逐封人工选择独立保存 |
| EmailDraft / SendIntent | owner、草稿版本、发件邮箱绑定、具体回复目标、发送快照、幂等键、结果证据和状态 |
| EmailVerification | mail_id、受保护码值、用途、期限/时间依据、证据、revision；不保存不可信的“已使用”状态 |
| EmailLocalizedPresentation | target kind/ID、分析依赖版本、language、title/summary/explanation、state、revision |
| 查询投影 | 分类/子类、摘要语言/状态、逐封未查看数、通知未归属原因、历史混合关系标记 |

分类发布、列表投影变更和后续任务意图同事务提交；比较邮件输入版本及分类 revision。
已分类通知在没有 conversation_id 时也算已分流，不能继续被旧 pending 查询当成待归属；
unknown／分类失败映射交互入口；交互尚无归属显示独立卡片。顶层 pending 仅保留未具备展示资料的接纳／解析异常，
不能把分类 unknown 当成顶层 pending。分类、未归属关系和解析状态分字段保存，列表与计数遵守同一规则。
新增/待归属邮件的分类发布与对话归属提交需协调，过时的 new/append 必须拒绝并重评。
Memory、默认 File（含快照恢复）、PostgreSQL 与迁移均须同时覆盖新增结构和索引。

拟议接口扩展：

- `GET /api/email/notifications`：`subtype=verification|promotion|account_security|general`（省略时返回全部通知），来源、搜索、时效筛选、稳定游标、language。
- 交互入口查询返回对话与未归属单封两种 item_type；需扩展现有查询或新增聚合查询，不伪造 conversation_id。pending 仅返回接纳／解析异常。
- 新增逐封分类修改命令及发件地址规则查询／更新／停用命令，owner 鉴权、幂等键和 expected_version 必须校验。
- 新增草稿保存／读取、发送提交与结果查询命令，复用实际发送执行通道，GET 不触发发送。
- 通知复用已有逐封资料/原件访问能力；补充单封详情查询时沿用 owner 鉴权，不暴露本地路径。
- 列表/详情支持 language，返回 `presentation_language`、状态和版本；游标绑定筛选条件，不跨子类复用。
- `POST /api/email/presentations/ensure`：白名单目标类型、最多 100 个目标 ID、language；owner 校验后合并排队。
- 现有 reanalyze 扩展为分类/摘要/关系复查；messages/viewed 仍按 mail_id 幂等提交。

旧数据迁移采用有游标、可恢复、限速的分类补算；无分类数据不得默认认作交互邮件或从 UI 消失。
过渡期在旧对话显示“分类待更新”，保留历史入口；新入库邮件先分类后分流。
纯通知的旧对话由通知主列表逐封呈现，同时保留原对话 ID 的只读历史入口。
混合旧对话仍保留对话入口和完整原时间线，通知卡片可链接回原归属；标明历史混合／待修正。
各入口徽标按邮件有效入口计算（含交互兜底），混合时间线中的通知不重复计入交互类未查看数；同 mail_id 的查看状态共享。
类别的显示投影可随新证据修订，但不搬移既有 conversation membership。
明确通知变成对话而无旧归属时可走新归属；已有归属始终保持，只更新疑点和展示。
回滚关闭新展示/任务分派，保留新增记录和原来源；不得用旧版 pending 条件接管已分流通知，
应先停新分析任务，再使用兼容查询或前滚修复，避免通知被旧 worker 新建对话。
