## 分析流水线

确定性解析邮件头、正文、附件和回复声明，生成标准化版本；附件提取调用现有文档能力。
模型读取这些已提交资料，生成单封摘要、事项描述及归属建议。随后 Runtime 原子提交归属，
另一个有界模型任务更新对话摘要。三者都可重试，不重复下载原件。
仅归属不明不会让整封邮件从管理界面消失。

单封摘要记录本封新增信息；保留正文引用但尽量不把整段引用当成这封新说的话。
会话摘要概括目前已取得的往来、进展与未解决问题，引用具体邮件/附件，不替代邮件时间线。
附件未提取、历史未补齐时可以产生明确标注范围的部分摘要，资料补齐后再更新。

## 候选选择与决定顺序

1. 按 mail_id 查询有效归属：重复发现或重复任务直接复用，不重新建对话。
   此处只跳过归属提交，摘要输入变化仍须刷新摘要并检查关系疑点。
2. 查询同 owner 的明确回复头关联与 provider thread 成员已有归属，优先提供对应对话。
   同一线程可能有多个事项，索引返回候选集合；RFC ID 匹配存在冲突时不能任意选中。
   跨邮箱查询只在当前 owner 已提交来源中进行，保留各自 mailbox；多个副本或冲突返回候选集合，
   不把旧来源层的同邮箱事实关系静默改成跨邮箱唯一父关系。
3. 以对方地址、参与者集合检索已有对话，再结合标题和内容获取有限的相关候选。
   不以 provider 或本地收件地址隔开；来源地址作为模型上下文和 UI 元数据保留。
4. 无已有关系且对方地址从未出现：提议新建；模型生成标题、单封摘要和初始会话摘要。
   新地址若有明确既有回复关系，则进入延续判断，不强制新建。
5. 地址已有：模型比较候选摘要、必要的具体邮件及新邮件，选择 append、new 或 pending。
   同地址不同事项新建；语义延续追加；“Re:”或同名主题不能单独决定归属。
6. 原生多邮件线程：优先定位已建管理对话，把尚未采集的成员作为独立任务同步。
   每个新成员都经过归属提交；不能在遍历每封时无条件新建一个对话。

邮件可能有多个收件人、群发地址或不明发件人。参与者集合替代单一联系人主键；
身份不足且无可靠既有关系时保留 pending，不猜测地址。候选不足时允许有界扩展一次检索，
仍不确定则待后续资料/重分析，不按最高相似度强行归并。

## 模型输入与结果契约

输入固定：mail/representation ID、单封摘要所需正文与附件提取、来源/参与者、
实际回复证据、线程观察、候选 conversation ID/成员版本/摘要版本、必要历史片段、
覆盖缺口与 owner assignment epoch。正文不是调度指令。

结构化输出：
- action：append / new / pending；
- target_conversation_id：只能来自候选，new/pending 时为空；
- proposed_title、message_summary、topic；
- evidence_refs、reason、uncertainty、missing_context；
- 本次实际输入引用及模型/提示版本由 Runtime 记录。

Runtime 校验候选 ID、owner、证据引用和版本后提交，不接受模型任意指定文件或构造 ID。
模型提出的管理归属可以按规则自动提交，不需要逐封人工审批；它不改变原件中的
From、Message-ID、In-Reply-To，也不把语义相似性写成“原始邮件声明回复”。

append/new/pending 输出仅用于新/pending 邮件归属。纯摘要任务返回摘要、证据引用和覆盖；
已归属邮件检查返回 none/suspected_duplicate/pending_correction、来自所给候选的涉及 ID、
理由与证据。Runtime 按任务类型和输入版本校验；即使模型返回归属 action，已归属检查任务
也不能调用 CommitAssignment。

## 并发、乱序与修正

模型分析可有界并发；同 owner 的归属提交以 epoch 条件更新协调。
两个任务同时看到“没有旧会话”时，第一个提交后第二个必须重新检索并判断，
不能凭过时结果提交。这不保证资料不足时不会语义误判；模型调用期间不持有 Store 事务。

先到回复 B、后到原信 A：B 可先形成对话或 pending，保留缺失引用；A 到达后补齐关系，
对新/pending 成员重评归属，对已归属成员刷新摘要并检查关系，不必然为 A 新建。
真实发生时间排序，迟到到达事件仍可通知 UI。
同一线程的话题转向可新开管理对话，原生 thread ID 仍保留；不能覆盖旧成员归属来假装原先没分类过。

原件变化、历史补齐或归属变化使相关摘要 stale。旧模型结果不得覆盖更新的成员版本。
首版保持已提交成员归属不动，只对 pending 和新成员判断；已有关系冲突增加“疑似重复／待修正”
（suspected_duplicate/pending_correction）记录。若 B、C 已分别属于 X、Y，之后补齐证据发现关联，
仍保留两个对话 ID 与原成员，记录涉及 ID、证据和输入版本，在双方展示疑点并允许跳转查看来源；
不合并、不搬移、不隐藏任一时间线。复查可按新证据版本更新疑点，但不修复归属；缺失父邮件或
RFC ID 命中本身不证明重复。历史归属修正及合并/拆分命令与 UI 留待后续。
首版不承诺任意乱序或资料不足时都不会产生重复事项对话。

## 刷新触发与恢复

以下目标分别持有期望代次与输入指纹：

| 目标 | 输入与持久触发 |
|---|---|
| 单封摘要 | 已提交正文/解析、附件提取/覆盖；版本变化即刷新，已归属邮件同样适用；选用的相关上下文也必须登记依赖 |
| 新/pending 邮件归属 | 解析、回复关系、线程观察、候选版本；新证据、缺失引用解析完成或显式重试触发重评 |
| 已归属邮件关系检查 | 相关回复/上下文/候选证据变化；可发布疑点，不能重新归属 |
| 对话摘要 | 成员集合、成员来源/提取版本、选用的单封摘要、上下文及历史覆盖；任一实际输入变化即刷新 |

持久保存具体 ID 依赖和 owner 范围内尚未解析的回复键；父邮件或线程成员到达时查询反向引用。
新可检索证据还要触发有界的 pending 归属/相关疑点扫描，让没有回复头的语义候选也能重评；
保存扫描游标，合并密集变化，跳过输入指纹未变的目标。无关 owner epoch 变化只是提交校验，
不能因此重新生成所有邮件摘要。

阶段 1 的发布同次保存失效与 RefreshIntent，分批展开时任务和继续位置一起提交。
复用归属不能完成摘要任务；单封摘要发布要触发依赖它的对话摘要更新。发布比较全部实际输入，
不能只比较成员数量。旧文案保留并标记 stale/failed 与覆盖；旧尝试完成不清除最新期望工作。
重启恢复持久任务，有限退避，重试耗尽持续可见并支持显式重试。已归属邮件的重新分析只刷新
摘要/关系检查，不搬移成员，不重新下载。

## 验收案例

| 输入 | 预期 |
|---|---|
| 新地址、无既有关系 | 一个稳定新对话，有单封摘要 |
| 同地址两件无关事项 | 两个不同对话 |
| 同地址同事项回复 | 追加原对话，不创建重复卡片 |
| 新参与者回复既有邮件 | 可追加原事项，不被新地址规则截断 |
| 已有线程首次补齐五封 | 已有邮件去重，新成员归属，保留历史排序与缺口 |
| 同一事项经两个收件邮箱到达 | 可共享管理对话，各自来源仍可追溯 |
| 两个相关新邮件并发 | 过时 epoch 决定拒绝并重评，不重放旧 new |
| B/C 已分别归属后原信 A 才到达 | 保留两个对话 ID 与原归属，按补齐证据显示疑似重复／待修正 |
| 模型超时、资料不全或候选冲突 | 已接收邮件可查看，归属/摘要状态明确，不重新采集 |
| 线程内换话题、同主题不同参与者 | 内容判断可新建，不被 thread/subject 强制合并 |

以人工确认的样本期望评估归属，另用确定性故障测试检验提交语义。
真实模型质量和 mock 状态测试分开报告，不能用后者证明理解正确。
补测不改变成员的附件提取改进、反向缺失引用解析、任务展开中崩溃恢复、旧任务完成和耗尽后显式重试。
样本数量及质量门槛沿用阶段 5，不以任意输入顺序下“零语义重复”作为验收条件。
