## 历史来源交付（已取代）

本节记录已实现的来源采集阶段。后续底座职责以“范围与归属”和“接收职责与执行边界”为准；
现有单封未读 Workflow 不是未来后台接收的必选入口；上一轮设计审查之后的实现进展另列如下。

后续实现进展：已增加独立的 `qqmail.discover` / `outlook.discover` / `gmail.discover` 与
对应的 `.capture` 固定脚本，Gateway 提供经过账号配置校验的发现调用；采集请求携带 Runtime
拥有的 `target` 时调用 `.capture`。既有 `.read` 手动入口保持兼容。
发现不打开邮件、不标已读，返回当前加载范围内最多 100 个稳定候选（候选总字节不超过 48 KiB）、
账号、观察时间、扫描行数、未支持行数和覆盖限制。非空列表只声明 `listed/limited`，
不能据此推进全邮箱完成进度；只有已有空列表证据才返回 `empty/scan_complete`。
当前尚未实现跨页完整发现，多邮件会话继续记为未支持，不能宣称接收全部未读邮件。

2026-09-08 自发样本验证：QQ、Gmail 分别给本账号发送带中文正文及中文文件名附件的测试邮件，
发现后固定目标采集均返回 `collected/read`。两份 59 字节附件与发送前文件逐字节摘要一致，
正文、From/To、主题及全部来源文件摘要通过核验。QQ 样本补齐了真实未读到已读转换和附件证据；
Gmail 样本补齐了自发单封身份及附件证据。Outlook 自发附件样本已在收件箱观察到，初始为已读，
验证期间仅将该测试会话标为未读；列表响应显示本地 1 封、全局 2 封，发现返回 1 个未支持行而非 empty。
该样本验证了多邮件会话的拒绝边界，未完成 Outlook 附件采集或新未读到已读闭环；
下一步须补齐会话内按 ItemId 定位及导出，不能仅放宽全局计数校验。
私有证据及可重复运行的离线校验位于 `data/qualifications/email-intake-20260908/report.mjs`。
宿主 Controller 已刷新，三家正式 Gateway→Controller `discover` 调用均通过回执校验；
QQ/Gmail 指定采集重试也通过 Gateway 来源与目标核验。Controller 166 项测试、Go 全量
build/test/vet、63 份双语文档检查通过。临时 Go 凭据桥接与启动脚本已移除；验证结束后
浏览器保留 7 个既有标签，无 Bridge 任务标签或文件选择对话框。以上不代表常驻 Gateway 已部署。

指定采集输入绑定实际账号地址、提供方邮件 ID 和导航 ID。首次打开邮件前持久写入目标，
列表必须同时匹配两个 ID 并核验账号；不得借相同调用 ID 替换目标，已读目标仍按身份恢复。
Gateway 校验来源清单中的实际账号及邮件 ID 与目标一致。候选字段由后台接收程序使用，
不增加模型可填写的查询或邮件目标参数。此步骤只拆分采集接口，尚未接入持久队列、定时器、
邮件 Store、标准化解析或模型分析，也未部署常驻 Gateway。

固定脚本 `qqmail.read`、`outlook.read`、`gmail.read` 每次选择并固定一封未读邮件，取得
可用正文与范围内附件、内嵌资源字节，并在配置的宿主工作区发布来源清单。每次采集一封
未读邮件，无需模型参数。没有符合条件的邮件时明确返回 empty，不创建虚构邮件。

QQ 邮箱具有单封邮件的未读标识。Gmail 将可见的单封会话标记与网页自身的列表响应
关联，要求邮件 ID、会话 ID、未读及收件箱标签一致。`thread-f/msg-f` 保留数字与十六进制一致性校验；
自发邮件的 `thread-a/msg-a` 使用列表中明确的单封记录与页面一致的 legacy 邮件 ID，不能把会话 ID 当邮件 ID。
Gmail 列表证据在任务页初始化时安装并重载任务页，避免遗漏已发出的请求。QQ 邮件 ID 允许实际观察到的 `~`。
Outlook 要求本地/全局邮件数均为 1、
ItemIds 与 GlobalItemIds 一致、未读计数一致；会话 ID 只用于导航，ItemId 才是邮件身份。
被动观察仅发生于任务自有页面，不重放服务商私有请求；未知响应结构不能作为证据。
Gmail/Outlook 仅从已加载列表选择能够证明为单封的会话；非空且没有可证明的候选时，在打开前
返回错误，不能返回 empty。目前不支持多封邮件组成的会话。
重试时重新检查收件箱列表中的同一单封身份，包括已读行；目标缺失或变化时明确失败，
不能改选其他邮件。

来源 ID 和引用不可变。每份清单用受治理相对路径、字节数与 SHA-256 描述实际文件，并绑定
精确服务商邮件；会话 ID 不得冒充邮件 ID。成功脚本结果返回采集数量、状态和来源清单
相对引用，不将所有来源字节塞入工具回执，也不声称已经理解附件内容。

服务商提供原始邮件下载时，脚本将其原字节保存为 `message.eml`，用 `mailparser` 解码
邮件头、文本/HTML 与 MIME 资源，采集方式为 `rfc822`。共享采集器接受明确标记为
`browser_dom` 的实际 DOM 观察，不拼装 EML 或补造缺失邮件头；但当前服务商适配器
要求经过验证的原文导出，导出不可用时失败。MIME 解码已实现；
附件文档内容提取、独立标准化数据解析层与模型分析尚未实现。

结构化来源记录使用 `schema_version: 1` 作为解析标识。
可选字段具有明确缺省语义，读取方容忍兼容的可选字段增加。已有字段含义和不可变来源 ID
不得用于不同内容；传输脚本 Revision 是独立契约。

宿主 `SPARKCLAW_BROWSER_EMAIL_WORKSPACE_ROOT` 指向与 Gateway 工作区共享的已有目录。
宿主与容器绝对路径可以不同，但相同相对路径须对应相同字节。它设置 Controller 的
`emailWorkspaceRoot`，不是模型参数。须校验配置根目录、
调用专属路径与最终引用，不能发布任意宿主路径、凭据或带签名下载地址。来源文件持久写入
并校验后才能发布清单。不支持的材料、缺失来源字段、未完成枚举与下载失败应明确记录，
不能用空内容或 complete 掩盖。

| 采集限制 | 边界 |
|---|---|
| 原始 EML 下载 | 110 MiB |
| 正文 | 2 MiB |
| 二进制资源 | 最多 20 个附件或内嵌资源 |
| 单个二进制资源 | 25 MiB |
| 二进制资源合计 | 100 MiB |

这些是采集边界，不允许静默截断来源。个别附件下载失败或超限可以产生明确资源状态的
`partial` 采集。资源超过 20 个时采集前 20 个，在 `coverage.skipped_parts` 记录
未取得的数量，并返回部分采集；正文超限会使采集失败。不获取远程图片或云盘链接。

所有者范围内的 `email/<owner-scope>/invocations/<invocation-hash>.json` 日志，在打开
邮件前持久保存所选账户与单封邮件身份；当前服务商适配器均要求打开前取得此身份。
重试仍固定同一选择，切换账户或邮件会被拒绝。
完成后的 `capture.json` 与来源文件不可变；`read-state.json` 独立记录可变的标已读意图
与观察，不属于不可变内容清单。文件及清单完成持久写入后才原子发布；显式操作服务商前
先持久保存已读意图。

回执区分 `empty`、`collected` 和 `partial`，附件计数只包含成功取得的文件。已有日志
回执重放时校验清单摘要及各文件字节数和摘要，拒绝缺失、被修改或经过符号链接的来源，
不会重复已确认的标已读操作。来源已发布但最终日志回执丢失时复用该采集；已读操作结果
未知时仍针对同一封邮件核对状态，重复操作前重新持久保存意图。
已确认采集的回执丢失时，校验文件并恢复回执，无需再次打开邮箱；已读结果未知时复用
原件，不再打开导出菜单或重复下载。失败暂存会清理；崩溃恢复只清理同一次调用未完成的
暂存目录。

`script_capture` 仅描述脚本层文件与清单的持久采集结果。本轮不实现 Gateway Store 提交、
稳定邮箱及邮件记录、关系解析、标准化表示、文档登记或独立模型分析节点。不能将一份文件
清单报告为 Store 已提交邮件记录。三层设计要求在 Store 接纳前校验不可变引用，其实现
不属于本任务。

完整采集已持久保存后，记录标已读意图、操作已固定邮件并验证结果。partial/failed 不授权
新的标已读操作。服务商打开即自动标已读时独立记录观察，不能用它证明采集成功。标已读
失败或结果未知不删除已有持久文件；恢复仍须针对同一封邮件，即使已经变为已读，也不能
转而消费下一封。

历史来源阶段验证（已由下文读取闭环验证补充）：Controller 全部 144 项测试通过，包含使用合成邮件和临时文件的来源采集、服务商
契约及真实 CLI 子进程传输测试；Go 专项测试和 vet、47 项 Golden 及扩展检查、8 项
资格验证辅助脚本测试通过。QQ/Outlook 的真实空结果路径通过；Outlook 最后一次已固定的
已读邮件返回 `collected`、附件 0、`read_state=read`，文件校验通过。这证明原文采集成功，
不代表新的未读选择通过。Gmail 最后一次固定邮件重试返回 `email_capture_unavailable`，
不宣称已有真实附件下载成功。宿主 Controller 已更新，Gateway 未部署。以下章节定义
数据归属与接入要求，其中 Store/分析组件
不属于本轮交付。

## 原件原生下载

2026-09-08 决策：通过 Playwright 获取服务商提供的原始 EML。QQ 和 Gmail 的原生下载
验证成功后，取消下文的网页信息替代方案。下文仅保留历史验证证据，不再作为现行备选
或后续三层数据结构工作的前置条件。当前服务商脚本要求原件校验通过；导出不可用时
明确失败，不会静默将重建邮件当作原件发布。

脚本在激活导出控件前注册 `page.waitForEvent('download')`，再对取得的 `Download`
调用 `saveAs()`。导出弹窗和指定目标的链接临时转为当前任务页导航，由 Chromium
处理响应、跳转和原生下载。Bridge 将任务页的原生 GUID/帧事件转交 Playwright，
宿主校验并交付文件字节，不修改浏览器全局下载目录。宿主在任务时间范围内关联唯一的
最终 URL 下载记录；并发同 URL 导致歧义时拒绝匹配，保留这些无法确认归属的文件。私有暂存副本成功后才删除原临时
下载文件；取消、大小限制、目标重名及任务断开均有对应清理。

QQ 的固定已读样本取得 38,146 字节，Gmail 取得 45,731 字节，Outlook 取得 58,069 字节，
均与独立获取的原件逐字节一致，并通过 MIME/邮件头校验。Gmail 跳转到已允许附件域名的
路径现已通过。三封均无附件。单次导出的 Blob 测试另验证了 1,435,412 字节 EML 及其中
1,048,613 字节二进制附件的逐字节完整性；普通链接和任务页内弹窗导出也已通过。这与
每次处理一封邮件的范围一致，同一页面批量下载未验收，仍受 Chromium 自动下载限制。
Controller 149 项、Bridge 39 项及制品 9 项测试通过。这证明原件下载能力可用，不等于
真实服务商附件清单、新未读选择或标记已读效果已验收。私有原件与脱敏回执保存于
`data/qualifications/native-download-20260908/`。宿主 Bridge/Controller 已更新；本任务
不部署 Gateway，也不实现 Store 或模型分析节点。

## 已取消候选方案：采集网页信息

决策状态：原件原生下载成功后，于 2026-09-08 取消。用户于 2026-09-07 提出此替代方案，要求先验证信息获取是否
准确、方便，再决定是否使用。以下保留的是当时的试验设计与记录，不代表现行实现决策。

候选方案从服务商网页中精确定位一封邮件，采集信息并生成统一的本地记录。原始 EML
导出作为可选证据，不再是候选路径的必要前提。“统一”指存储格式一致、忠实保留观察，
不表示重建与原件字节完全相同的邮件。

沿用三层结构：来源层可以保存仅属于该邮件的 `mail.json` 观察记录、实际正文文本/HTML、
逐个取得的附件，以及 `capture.json` 的覆盖情况和来源信息；标准化事实与模型分析仍各自
负责原有内容。不能把整个邮箱页面当作一封邮件，也不能补造缺失的邮件头、时间、收件人
或回复关系。未取得字段与确认没有该字段必须区分。附件仍需独立取得真实字节；此方案
本身不解决附件下载、单封未读身份或打开即自动已读的问题。

### 先验证，再决定

初步信息验证使用已有定位的已读邮件，不发送测试邮件，也不新增打开其他未读邮件。
验证脚本和私有观察资料独立于生产脚本及正式邮件记录。有现存 EML 时以其作为独立对照；
没有时与展开后的邮件界面核对，并明确对照依据较弱。仅重复采集同一份 DOM 只能证明
结果可重复，不能单独证明准确。

| 检查项 | 所需证据 |
|---|---|
| 账户与邮件 | 身份稳定且对应目标单封邮件，不能仅确认会话 |
| 邮件头信息 | 主题、发件人、收件人、抄送、显示时间与对照一致，缺失项明确 |
| 正文 | 展开后比较文本、段落顺序与引用历史，区分渲染差异和内容遗漏 |
| 附件 | 清单及逐个文件字节与对照一致；无附件样本不证明附件下载可用 |
| 便利性 | 记录耗时、浏览器操作数、展开操作、重试与服务商特定处理，不能预设更快 |
| 状态 | 本次仅观察既有已读样本；新未读选择与标已读效果仍需独立证据 |

对支持的服务商和样本范围取得足够证据后，才建议采用。复杂 HTML、引用会话、同名附件、
内嵌资源及不同收件人/时间呈现方式需要相应覆盖。有限样本成功只能证明可行性，不能等同
完整可用。先记录实际验证结果，再与用户讨论是否采用。

## 范围与归属

邮件功能通过可弹出的统一管理窗口呈现；事项对话、跨收件邮箱归属及遇到线程的历史补齐，
由[整体管理设计](email-management-design.md)与阶段文档定义。本文负责来源、标准化和分析的
数据基础。下文任务仍指后台采集和分析任务，不是用户待办事项。

管理窗口查询已提交的邮件资料及处理状态；打开、关闭或重新打开窗口不启动重复接收，
也不决定后台任务的存续。具体窗口交互和对外 API 留待管理阶段设计。

Gateway 通过现有[类型化 Store](store.md)拥有权威记录，
不可变文件内容保存在受治理的本地工作区。不新增独立 SQLite、图数据库或向量库。
文件与 PostgreSQL 后端必须具备等价持久化语义；Memory 仍是非持久化参考和测试实现。
邮件专用 Repository 方法属于设计要求，不是当前已有接口。

## 接收职责与执行边界

以下底座要求尚未形成完整后台服务；独立 discover/capture 内部入口已经存在。定时器只触发发现，不承担任务队列；
Workflow 可用于固化模型分析步骤，但不是确定性接收过程的必要依赖。

```text
定时触发发现 → 持久化邮件身份与采集任务 → 按身份采集 → 校验并提交本地资料
                                                           ↓
                                                   独立模型分析任务
                                                           ↓
                                          管理窗口查询资料、状态和分析结果
```

| 职责 | 输入与输出边界 | 执行归属 |
|---|---|---|
| 发现 | 已验证邮箱、发现范围及进度；输出有界候选、稳定单封身份、观察证据及扫描覆盖情况 | 确定性程序，由后台调度触发 |
| 采集 | 已持久化的指定邮件身份；输出原件、正文、附件、清单与独立已读结果 | 任务执行器调用服务商脚本，不自行改选下一封 |
| 标准化与分析 | 已提交且校验通过的来源版本；确定性解析后创建绑定输入版本的模型任务 | Runtime 管理解析与分析，Workflow 是可选组织方式 |
| 管理呈现 | 已提交记录、任务进度、覆盖缺口和分析结果 | 后续可弹出管理窗口，不拥有另一套邮件状态 |

单封是采集执行单元，不是批量发现的限制。当前“第一封未读”可以作为手动便捷入口保留，
但不能作为后台队列的唯一来源。当前已有独立指定邮件 capture 入口及同次调用固定目标恢复，
尚未接入持久队列与正式 Store 接纳。

未读是发现条件，不是持久任务状态。先保存候选身份与采集任务，再打开邮件；
打开即自动已读或用户改变已读状态，都不能使已有任务丢失。重复扫描按
`(owner_id, mailbox_id, provider_message_id)` 去重；已采集邮件再次变为未读不自动创建重复采集或分析。
扫描进度只能越过已可靠记录的候选。发现与采集共同改变列表时，不能按可缩短未读列表的页码
直接推进；需稳定游标或有界重复扫描与身份去重。扫描受限、身份不明与确实为空分别报告，
不能将当前可见列表结束当作全邮箱已同步。各服务商的分页机制和恢复接口在实现前单独验证。

同一邮箱的网页任务默认串行，避免导航和选中状态互相干扰；不同邮箱在浏览器会话隔离及
Controller 约束允许时并行。模型分析可以独立、有界并发，不阻塞下一封采集。
任务需要持久状态、领取租约或等价排他机制、过期执行者保护、有限重试及下次可运行时间；
单封持续失败不能阻塞其他邮件。队列容量和积压需要背压，不能无界启动浏览器或模型任务。

资料提交与待分析意图必须可靠关联：同次 Store 条件提交持久化待分析意图，
由执行器幂等领取；不能在提交后仅发送可能丢失的内存通知。解析未完成时意图等待所需版本就绪，
生成分析任务时固定实际输入版本。采集、解析、标已读与分析独立恢复，模型失败不重复下载原件。
具体 Repository 方法、任务字段和参数在编码前确定，不引入独立队列数据库。

只发现未读邮件不保证历史完整；已读历史、已发送邮件及跨邮箱管理属于以后明确的接收策略。
保留原始回复头、未解析引用与缺口即可，不为界面预造完整上下文。
当前 Gmail/Outlook 的单邮件会话限制必须解决后，才能宣称接收范围内所有未读邮件。

### 会话内逐封回复邮件采集

QQ 邮箱、Gmail、Outlook 均须支持采集归属于多邮件会话的一封回复邮件。
一次采集仍只绑定一封邮件，不要求下载整段往来，也不因目标带有回复关系而递归采集历史。
这是统一的验收要求；上文的单邮件会话限制是待消除的实现缺口，不是产品范围限制。

发现结果以服务商单封邮件 ID 为身份，会话 ID 只提供分组或导航信息。同一会话内不同未读
邮件可分别成为候选；已读历史、已发送副本和草稿不能凭会话的未读标记成为未读来信。
采集指定目标时必须核对具体邮件对应的详情与原件导出入口，不能用会话标题或“最后一封”
替代指定身份。正文中的历史引用保留为目标原件的一部分，不伪装成已独立采集的历史邮件。

原件中存在的 `Message-ID`、`In-Reply-To`、`References` 保留供后续关联；缺失字段不猜测，
引用到尚未采集的邮件不触发自动补全。标已读结果绑定目标单封邮件，必须验证打开会话是否
会连带改变其他邮件状态；不能把会话级已读状态当作逐封处理证据。

三个邮箱各自需要真实回复样本，核对目标身份、原件、正文、附件与回复头，以及重试固定目标。
同会话多封未读时还须验证候选区分与非目标邮件的状态影响。各邮箱分别记录通过范围，
一个邮箱或单封会话样本通过不能替代其他场景的验收。

#### 2026-09-08 定位验证结果（尚未实现）

用户确认改用 Outlook 当前登录账户已有的会话。该样本返回收件箱 2 封、全局 6 个项目，

## 三层结构

| 层次 | 权威内容 | 写入方 | 版本规则 |
|---|---|---|---|
| 一、来源层 | 实际获取的邮件头、可取得的原始格式、浏览器正文或 HTML 观察、内嵌图片和附件字节 | 固定服务商脚本及 Runtime 采集流程 | 已提交采集版本不可覆盖，缺失材料明确记录 |
| 二、标准化层 | 跨服务商统一邮件记录、解码正文、提取结果、身份及有依据的关联 | 确定性采集和解析器 | 来源或解析方式变化时生成新版本 |
| 三、分析层 | 总结、上下文解释、证据引用、覆盖范围和缺口 | 独立模型任务，可用 Workflow 组织，由 Runtime 校验落盘 | 每次分析绑定不可变输入清单与输出 |

来源层表示“实际取得了什么”，不保证是完整原始邮件。
只有从服务商实际取得 RFC 原文时才保存 `message.eml`；网页采集标记为 `browser_dom`，
不能拼装伪原始 EML，也不能声称看到了缺失的邮件头。
凭据、Cookie、带签名下载地址和包含其他邮件的整页快照不属于邮件资料，不能混入来源文件。

标准化层保留缺失和歧义，不用模型猜测发件人、时区、原始邮件 ID 或附件状态。
分析层可以解释和推断，但须标明推断，不能改写事实字段、邮件身份、权威关联或服务商状态。
正文和附件始终属于不可信的分析输入，其中的指令不能改变 Workflow 权限、选择工具或授权外部操作。

## 身份定义

| 身份 | 定义 |
|---|---|
| `owner_id` | 现有已认证本地所有者边界 |
| `mailbox_id` | 一个已验证服务商账号的稳定本地 ID，不是可变默认账号别名或凭据代次 |
| `mail_id` | Runtime 分配的稳定本地邮件 ID，不随 Workflow 运行变化 |
| `capture_id` | 针对已固定邮件的一次来源采集版本 |
| `part_id` | 某采集版本中的一次附件或内嵌资源出现 |
| `representation_id` | 一次不可变标准化或提取版本 |
| `analysis_id` | 一次不可变模型分析结果 |

采集唯一键为 `(owner_id, mailbox_id, provider_message_id)`。
服务商 ID 按该服务商的范围和稳定性约定作为不透明值使用，会话 ID 不能替代单封邮件 ID。
无法取得可靠稳定定位符时，保留为未完成采集证据，不能接纳为可去重的完整邮件。

RFC `Message-ID` 是来源证据与查询键，不是全局唯一主键，因为可能缺失、重复或伪造。
不按主题、发件人与时间组合、正文或附件哈希合并邮件。
不同账号收到相同 RFC ID 的邮件仍分别保存。切换为另一个账号须创建不同邮箱绑定；
同一已验证账号轮换凭据不会改变邮件身份。

重复采集同一唯一键时复用 `mail_id`。相同内容摘要可复用已提交来源内容；
内容变化或补齐材料时追加采集版本，不覆盖历史。身份依据矛盾时记录冲突，不静默合并。
`run_id` 仅记录执行来源，不能成为邮件身份。

## 物理存储与权威边界

在已配置工作区内，以不透明 ID 组织目录：

```text
email/<owner-scope>/<mailbox_id>/<mail_id>/
  source/<capture_id>/
    capture.json
    message.eml                 # 仅在实际取得时存在
    headers.json
    body.html                   # 仅在实际采集时存在
    body.txt                    # 实际观察到的文本
    parts/<part_id>/<safe-name>
  normalized/<representation_id>/
    message.json
    body.txt
    parts/<part_id>/content.json
  analysis/<analysis_id>/
    inputs.json
    result.json
  staging/<attempt_id>/          # 不属于已完成来源
```

文本及 JSON 使用 UTF-8，原始二进制保留原字节。
每个不可变内容引用包含结构版本、受治理相对路径、字节数与 SHA-256。
文件名清理后用于展示，不作为身份；相同附件名不能相互覆盖。
哈希用于校验，也可支持以后在同一所有者范围内复用相同字节，但不能合并附件或邮件身份。
不要求物理去重。

工作区文件拥有不可变内容；Store 独占邮件身份、已提交版本指针、关联及可变生命周期状态。
磁盘上存在 JSON 但没有已提交 Store 引用，不代表该邮件已接纳。
查询索引是由已提交记录和内容重建的派生投影，不能成为另一套事实来源。
不能通过目录扫描或可编辑 `latest.json` 推断权威状态。

目录由 Runtime 分配。Controller 下载到调用专属暂存目录，Gateway 验证宿主机与容器共享映射，
或通过有界受控通道传入工作区。模型收到限定范围的文档或文件引用，不能使用任意宿主下载路径。
适用时通过现有[文档记录](document-workflows.md)登记下载文件；
文档记录描述文件，不重复拥有邮件生命周期。

邮件资料是持久来源，不是运行临时制品，不能随普通运行日志清理而消失。
本设计不定义删除或保留期产品。外部修改或丢失文件是完整性错误，不能自动当成新来源版本。

## 最小逻辑记录

| 记录 | 必须表达的信息 |
|---|---|
| 邮箱 | 所有者、服务商、稳定账号绑定及绑定版本 |
| 发现进度与候选 | 邮箱与扫描范围、进度和覆盖限制、单封稳定身份及观察证据、持久入队结果 |
| 后台任务 | 采集或分析目标、去重依据、状态、尝试与领取凭据、重试时间、失败原因；分析绑定不可变输入版本 |
| 邮件身份 | 本地 ID、服务商邮件及会话 ID、实际观察到的 RFC ID、首次取得时间 |
| 来源采集 | 采集、尝试及运行 ID，脚本版本，采集方式和时间，文件清单，邮件头、正文及附件枚举覆盖情况 |
| 标准化邮件 | 来源版本及哈希、解析器版本、主题、From/To/CC、可取得的 Reply-To/BCC、时间依据、正文及附件引用、原始回复头、缺失字段 |
| 附件资源 | 所属邮件与采集版本、出现 ID、可取得的服务商定位符、原始文件名、附件或内嵌类型、Content-ID、声明及检测类型、字节数、哈希、引用和取得结果 |
| 提取结果 | 附件或正文输入哈希、提取器版本、文本或版面引用、原始页码/段落/幻灯片/工作表定位、解析结果和限制 |
| 关联 | 有范围的起点、目标 ID 或待解析外部键、类型、来源证据、解析状态及版本 |
| 分析 | 模型和提示版本、不可变输入清单、结构化总结和上下文说明、证据引用、推断标记及覆盖缺口 |
| 运行状态 | 采集尝试、预期记录版本、已读观察、标已读意图及结果、分析尝试 |

显示时间原文保留，标准化时间戳和时区可为空，记录解析依据。
空正文与缺失或截断正文不同；只有附件枚举完成，空附件数组才表示确实无附件。
引用历史作为正文片段保留，没有独立来源采集时不能变成独立邮件事实。

所有结构化记录带 `schema_version`，Store 可变记录另外带条件更新用的 `record_version`。
Runtime 观察时间采用 UTC，来源时区未知则继续保留未知。
记录版本、内容哈希及解析器或模型版本含义不同，不能相互替代。

普通附件和内嵌图片都作为资源明确记录，HTML `cid:` 按同次采集的 Content-ID 关联。
远程图片、正文 URL 和云盘分享链接仅记录为外部引用，不自动获取。
限制和不可用材料明确记录，不能为适配模型上下文静默截断来源，也不能假定不支持的附件已被分析。

## 关联规则

权威关系图由 Store 中的带类型关联记录组成，不需要图数据库。

| 类型 | 依据 | 含义 |
|---|---|---|
| `replies_to` | 明确解析到的 `In-Reply-To` | 本邮件声明回复该目标 |
| `references` | 按顺序解析的 `References` | 声明的祖先或上下文引用，并非每个目标都是直接父邮件 |
| `provider_thread_member` | 同一邮箱内的服务商会话 ID | 服务商分组，不代表回复方向 |
| `has_part` / `inline_part` | 经核验的采集清单及 MIME/DOM 证据 | 这次资源出现属于这封邮件 |
| `derived_from` | 精确输入引用与摘要 | 标准化和分析的来源追踪 |

引用正文、主题相似、参与人相同或语义接近不能自动生成权威回复关系。
模型建议的相关性只保存在分析层，带建议标记及依据，不合并身份、不改写权威关系图。
RFC 关联表示观察到了这种声明，不代表验证了发件人身份。

只在同一所有者、同一邮箱内解析目标。
目标尚未取得时保留 `unresolved` 外部键；后来采集到对应邮件时，按精确依据补齐，
但不因此自动下载历史。多个目标匹配时记为 `ambiguous`，不能任意选择。
非法、自引用或成环回复依据保留为 `invalid`，不用于上下文遍历。
服务商分组与父子关系可以同时存在，不强制伪造唯一父邮件。本设计不做跨邮箱关联。

上下文遍历必须有数量限制与已访问 ID 检查。
分析输入清单记录实际使用的本地邮件和版本，以及缺失引用；
“已分析可用上下文”不能表示完整历史已经全部取得。

例如先取得回复 B、尚未取得原邮件 A 时，保留 B 指向 A 的待解析引用。
后来取得 A 后补齐关联，不改写两封邮件的来源；如果 A 进入 B 已声明的上下文选择范围，
B 的旧分析变为 stale。

## 状态边界

远端未读、发现进度、后台任务、本地采集、模型理解是不同事实，不能合成一个状态字段。
发现与任务状态由 Store 持久拥有，执行器推进；管理窗口只展示这些状态。
任务等待、执行、重试等待和终止结果须分别表达；任务完成不替代来源覆盖或分析新鲜度。

| 状态归属 | 取值及边界 |
|---|---|
| 采集尝试 | `pending -> running -> complete / partial / failed`；重试针对同一已固定邮件创建新尝试 |
| 来源覆盖 | 邮件头、正文可用性，附件枚举完整性，各资源取得结果，明确缺失或受限字段 |
| 资源取得 | `pending / downloading / available / failed / skipped_limit`；available 要求字节已持久保存并校验 |
| 解析尝试 | `pending / running / succeeded / partial / unsupported / encrypted / failed`；下载成功不表示可解析 |
| 分析尝试 | `pending / running / succeeded / failed`；成功结果另外记录 `complete_for_inputs` 或 `partial` 覆盖情况 |
| 分析新鲜度 | `current / stale`，由输入版本和上下文选择推导，与分析成功与否分开 |
| 邮箱已读观察 | `unknown / unread / read`，包含观察时间与依据 |
| 标已读效果 | `not_requested / pending / confirmed / failed / unknown`，绑定实际单封邮件 |

采集完成要求：邮件身份核验通过、正文和必需元信息已落盘、普通附件及内嵌资源枚举完整，
所有范围内二进制资源均可用。可选 RFC 头或原始 EML 不可取得，不妨碍合法 DOM 采集完成；
身份、正文或附件枚举有缺口则不能 complete。解析不支持不会把成功下载改为失败。

采集 complete 后先持久记录标已读意图，再操作服务商并核验，模型分析不必先完成。
partial 可以进行明确标注的不完整分析，但不触发新的标已读操作。
标已读和分析分别报告结果，标已读失败不能否定已持久保存的邮件资料。

部分服务商打开时就自动标已读。记录实际观察以及 `provider_auto` 原因，
不能声称仍是未读，也不能因此将后来失败的采集视为成功。
完整采集发现已读时核验即可，不再切换状态。本设计不默认自动恢复未读。
标已读超时记为 unknown，必须核对同一封，不能假定成功。
用户后来重新标未读，只更新观察，不改变本地采集状态。

模型失败保留已采集资料和邮箱实际状态。重做分析复用文件；
重试采集仍使用固定邮件，即使它现在已读，也不能换下一封。
`empty` 是调用结果，不创建虚构的邮件或状态记录。
这些状态均不表示“用户已处理完这封邮件”，本设计不引入这样的管理状态。

## 发布、恢复与分析版本

1. 打开或下载前把调用绑定到单封身份，用每封邮件的活动尝试令牌及 Store 条件版本拒绝过期执行者写入。
2. 暂存写入、原子完成文件、校验字节与摘要并保证持久落盘后，才在 Store 发布清单和版本指针。
3. 一次邮件发布通过条件更新写入已提交采集版本、覆盖情况、需要的标已读意图与待分析意图。
   不声称数据库与文件系统具备分布式事务。发布前崩溃留下未接纳文件，恢复须核对同次尝试，不能换另一封。
4. Store 回执丢失时，先按尝试 ID、预期版本、清单摘要对账，再执行外部动作。
   已提交引用对应文件缺失或摘要错误时，阻止使用和标已读。
5. 重试不能以 partial 覆盖已有完整采集；来源和解析改进追加不可变版本。
   关联解析结果独立版本化，不重写来源字节。

分析 `inputs.json` 固定邮件、采集及标准化版本，实际读取的正文、附件与提取结果哈希，
相关邮件的具体输入、关系快照和上下文选择规则版本，以及模型和提示版本。
证据引用应定位正文片段或文档页、段落，不能只有文件名。
引用旧总结时必须标明它是可追溯的派生资料，不能提升为来源事实。

新内容、改进的提取结果或新补齐上下文可让分析 stale。
读取分析时比较保存的输入与上下文指纹；仅在明确重新运行时追加分析，保留旧结果。
已读状态、轮询时间、单纯凭据轮换不使内容分析过期。
本设计不加入自动重分析或上下文获取后台任务。

## 设计验收

验证账号隔离与去重、来源和派生版本不可变、重名附件、来源保真与缺失语义、
未解析、歧义和成环关系、证据追踪、独立状态转换、崩溃恢复、
已读效果不确定、分析过期，以及宿主和容器的文件真实可见性。
文件及 PostgreSQL 实现须遵守相同约定。

底座接入还须验证重复发现去重、发现进度与入队一致、未读列表变化不漏掉已发现候选、
已读后采集恢复、资料提交与待分析意图一致、租约过期拒绝旧执行者、失败邮件不阻塞队列、
模型并发不干扰采集，以及窗口关闭和后台重启后的任务恢复。这些是设计验收要求，尚未实现或验收。

本轮验收覆盖来源脚本、清单与文件校验、采集限制、部分覆盖与标已读顺序。
脚本测试不能验证尚未实现的三层 Store 或模型分析节点；这些组件不在本轮实现范围内。
无跨项目契约变更，其他簇项目无需跟进。
