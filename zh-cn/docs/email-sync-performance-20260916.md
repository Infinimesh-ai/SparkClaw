# 邮件同步性能优化实测 — 2026-09-16

语言：简体中文 | [English](../../docs/email-sync-performance-20260916.md)

## 范围和计时口径

优化前后使用同一个已登录的专用浏览器、固定邮件身份和时间区间。每个新下载用例使用新的隔离 owner／工作目录，确实重新获取原件。负载是一次原生空时间区间查询，加 0、1 或 N 个精确的缺失原件目标，执行正常采集及本地保存链路；不是自然到达 N 封新邮件的突发测试。不发送、不标记已读、不更改生产接收开关。

总耗时覆盖 Go runner 内的浏览器任务、页面准备、采集、本地发布与清理；独立原件／哈希复核在计时之外。不含后续完整 MIME 解析、数据库接收、分类和模型分析。之前的 16.5／26.8／29.8 秒诊断测量含额外浏览器观察，不作为此次比较基线。这些是单次观察，不是 P95 或吞吐承诺。

## 已实现的优化

1. 仅对受信任且明确等待实际结果的 QQ／Gmail 读取操作，取消无关页面流量等待及额外 500 毫秒 settle。必须同时满足任务级环境开关和 Controller 生成的代码标记；Outlook 原生 UI 读取、发送和未标记操作保留上游完成规则。
2. 在同一次浏览器调用中核对执行前后的真实页面 URL，同时保留独立的任务所有权、标签页拓扑、来源与账号检查，去掉一次重复 renderer 往返。
3. QQ／Gmail 将本地 Reader／账号就绪检查与唯一一次时间范围请求合并。只允许请求前的本地就绪检查重试，不在调用内重复失败的供应商请求。
4. 仅当确实需要新原件时创建 staging；哈希、持久日志、原子发布和精确 ID 重放保留。
5. 修复合法折叠 Message-ID 的空白、GB2312 正文及中文编码发件人解析，不改动原始 EML 字节，也不剔除此前失败的两封 QQ 样本。

本次测量时只有同批复用任务页面，尚未实现跨轮页面／会话缓存；后续[跨轮复用优化](email-cross-round-reuse.md)已接续解决这一限制。原件仍未并行下载。原件准备包含供应商响应传输和浏览器到宿主的传输；单独的本地写入计时不能冒充完整网络下载耗时。

## 独立的模型处理阶段

只读核查上一轮生产 QQ 事件，四项模型操作计时合计 5.032 秒（主题分类 0.937 秒、正文确认 0.838 秒、事件归属 1.350 秒、事件摘要 1.907 秒）。从原件提交到最终摘要为 6.736 秒，包含排队和本地处理。模型操作计时包含容量等待及结果校验，并非纯推理。本记录来自另一轮生产观察，不是优化后完整链路压测，本次未优化模型耗时。

## 证据及限制

初版优化的 Outlook 矩阵未通过：空区间用例及重跑的两封用例各出现一次区间发现超时，均未进入原件下载。另测五次空查询，三次成功、两次失败。仅在失败后收集的安全证据显示：搜索框仍连接但为空，未发出搜索资源请求；失败发生在原生搜索提交之前，不是原件下载慢。更深层 UI 时序原因未确定。已撤回 Outlook 的快速完成优化，保留原有 500 毫秒 settle 和上游完成检查，同时保留减少一次重复来源检查的改动。撤回前的成功／失败单独留痕，不混入最终数据。

最终三家共 18 项新下载／重放用例全部通过。Outlook 最终兼容策略另有五次连续新任务空查询通过，分别为 11.904／11.950／11.963／11.955／11.968 秒；这是有限稳定性证据，不是长期可用性承诺。最终自动验证通过：完整 Go 测试／build／vet、邮件相关 race、Controller 376 项加 1 项既有环境跳过、前端135项／build／707翻译键，以及81份双语文档检查。
