# 邮件时间线增量同步、失败随轮补齐、刷新与留痕设计

> 语言：简体中文 | [English](../../docs/email-timeline-incremental-sync-design.md)

状态：2026-09-16，已实现、已部署，受管 Reader 0.2 已真实安装。QQ、Gmail、消费者版 Outlook 均已通过不注入源码、直接使用已安装脚本的实机验收矩阵。Microsoft 365 尚未验证，当前不支持。证据和限制见第 15–16 节；部署成功不等于下列全部验收与性能目标都已达成。

用户决定保持不变：失败不停止后续新邮件轮询；同一精确邮件连续两次合格邮件级失败后，永久退出普通轮询和刷新，保留可确认或未确认的持久告警。运维失败不消耗此额度。非空批次在 rename 前发布一份恢复日志，空轮次不写；溢出只确认一次冻结区间，再成为可见终态覆盖缺口。本文替代[邮件全链路优化](email-pipeline-optimization-design.md)的普通轮询、分页与热路径持久化部分；来源目录、鉴权和保留遵循[邮件本地下载、处理与窗口展示设计](email-local-download-storage-design.md)。

## 1. 用户要求与范围

本文冻结以下产品决定：

- 普通轮询从上一次成功完成的时间线边界向新的固定上界继续，不再重复扫描邮箱页面后丢弃旧行。
- 正常业务量应在一次服务商响应内完成；普通轮询不跟随下一页，也不重读前页来证明前缀未变化。
- 断电、进程崩溃和断网属于特殊情况。热路径不在每轮支付全量审计、重复哈希或逐文件持久化屏障成本；系统持久化失败记录，下一次定时轮询只携带首次失败邮件一次，同时继续查新邮件；同一稳定 ID 第二次合格失败后终止同步并提醒用户。邮件窗口刷新键只立即运行仍有资格的有界工作。
- 原始邮件直接下载到本地邮件工作区；分类、事件归属和摘要异步运行，不阻塞同步边界。
- 9 月 11 日部署锚点保持为产品下界；已经删除的旧历史和旧接收链路不迁移、不恢复。
- QQ 邮箱、Gmail、Outlook 共用一套状态机和结果契约，但分别维护真实验收过的网络适配器；不得把一家服务商的能力推定给另一家。

核心目标是：

```text
实时尾部轮询水位 + 连续覆盖水位 + 仍可重试的精确 ID
  → 到新固定上界的一次已验收服务商变化／范围请求
  → 新稳定邮件 ID 与精确失败目标的并集
  → 只下载或收养缺失原件
  → 一次本地批量提交
  → 推进实时尾部；仅跨越已证明区间推进连续覆盖
  → 不加载终态告警明细，只更新重试积压
```

轮询不可能在零上游 I/O 的情况下知道“没有变化”。因此，零新增邮件的目标是：一次有界增量请求、零原件下载、零来源文件写入、零解析、零模型调用。

## 2. 当前实现与历史差距

Gateway 与 Reader 现对每轮普通轮询使用一个半开时间区间。旧 QQ 头页扫描及 Outlook 文件夹 offset 扫描不再属于 timeline-v2 轮询路径。

| 提供方 | 当前范围请求 | 验收边界 |
|---|---|---|
| QQ 邮箱 | 原生 `/list/search` 的已观察 `after`／`before` 条件，加精确 `totime` 校验 | 无注入已安装版本实机矩阵通过 |
| Gmail | 原生有界 `after:`／`before:` 搜索，消费已观察响应而不重复重放，再校验精确内部收件时间 | 无注入已安装版本实机矩阵通过 |
| Outlook 消费者版 | `/searchservice/api/v2/query`、`EntityType: Message`、显式收件下界 AND 上界、完整入站文件夹范围 | 已安装 Reader 实机矩阵通过，详见第 16 节 |
| Microsoft 365 | 无已接受 transport | 未验证、不支持；不继承消费者版证据 |

这些适配器是 `time_range`，不是服务商变化游标。秒级服务端查询包络可能在相邻精确区间重叠；精确收件时间校验和稳定 ID 去重避免重复下载原件。它们不能发现任意延迟可见、且旧收件时间早于保留边界的邮件。普通轮询不跟随下一页，也不复查历史前缀。

## 3. 术语与持久状态

“上次读取时间”不是最新一封邮件的时间，而是上一个已完整列取的发现区间终点。已发现但原件未完成的邮件不回拉该水位，而是进入精确失败积压。

每个 `owner/provider/mailbox/scope` 保存一份等价于 `EmailSyncCheckpoint` 的状态：

| 字段 | 含义 |
|---|---|
| `scope_version` | 固定值，例如 `timeline-v2`；阻止旧分页游标进入新状态机 |
| `deployment_anchor` | 不可变产品下界；当前干净部署为 9 月 11 日 |
| `discovered_through` | 最近连续且已完全证明的覆盖终点；遇到最早未解决覆盖缺口时停在那里 |
| `poll_through` | 下一次实时尾部查询的排他起点；正常与 `discovered_through` 相同，终态溢出缺口后可越过缺口继续，使新邮件轮询不停 |
| `inflight_until` | 当前运行 attempt 的固定排他上界；后续定时 attempt 可选择新上界，但保留同一未证明下界 |
| `provider_mode` | 类型化取值：`change_cursor`、`time_range` 或 `anchored_head` |
| `provider_cursor` | 只有语义经实机验收的服务商变化令牌才能保存；绝不保存伪造页 offset |
| `state` | `idle`、`running`、`incomplete`、`overflow_confirmation`、`coverage_gap`、`unqualified` 或 `login_required`；它报告上轮结果和覆盖事实，只有 `unqualified` 阻止普通提供方轮询 |
| `pending_failure_count` | 有且仅有一次合格失败、仍可随轮补一次的精确目标，加未闭合发现失败数 |
| `suppressed_mail_count` | 连续两次合格邮件级失败后永久排除的稳定 ID 数；它们是告警，不是重试工作 |
| `coverage_gap_count` | 一次确认后仍无法证明完整的冻结溢出区间数；它们是告警，不是普通重试工作 |
| `last_error_code` | 阻止边界推进的稳定安全原因 |
| `updated_at` | Store 提交时间，用于状态展示和陈旧工作识别 |

没有覆盖缺口时，下一权威查询区间为：

```text
[poll_through, inflight_until)
```

发现使用服务商收件／变化时间，绝不使用 RFC `Date:` 信头。稳定服务商邮件 ID 继续作为幂等身份。对于秒精度谓词，查询时只保留一秒的闭区间下界重叠，再在本地应用精确半开区间和稳定 ID 去重；该有界重叠避免同秒邮件丢失，又不重新打开旧历史。

原件下载失败不会把任一水位向后拉：其稳定服务商 ID 持久保留在 `EmailSyncFailure` 中并独立重试。列表失败时尚无可证明的候选集，因此 `poll_through` 保持不变；下一轮从同一下界查到新固定上界，一次覆盖原失败区间与后续新邮件。终态溢出缺口是唯一允许 `poll_through` 前进而 `discovered_through` 仍停在缺口起点的情况；精确冻结缺口持续可见，邮箱不得宣称连续覆盖完整。

`provider_cursor` 只是优化，不是唯一恢复权威。游标过期或被拒绝时，实时尾部从 `poll_through` 重新查询，而不是从当前时间开始；更早的终态覆盖缺口保持可见，不被静默重新打开。

任何服务商 I/O 开始前，Store 先持久化 attempt revision 与 `inflight_until`。终态失败清除当前 in-flight 标记，但在失败审计中保留本次上下界。若断电发生在普通错误记录写入之前，启动时把陈旧 `running` attempt 转换成持久 `interrupted` 失败。启动本身不请求服务商；下一次定时轮询或更早的人工刷新携带该中断工作。

## 4. 类型化提供方契约

Reader v2 在正常路径用类型化 `listChanges` 替代 `listPage`。下面只是内部概念契约，不是公开 HTTP API：

```json
{
  "account_address": "owner@example.com",
  "after": "2026-09-16T01:00:00Z",
  "before": "2026-09-16T01:20:00Z",
  "limit": 50,
  "provider_cursor": "optional-qualified-token"
}
```

结果携带：

```json
{
  "provider_mode": "time_range",
  "account_address": "owner@example.com",
  "items": [],
  "complete": true,
  "overflow": false,
  "next_provider_cursor": "optional-qualified-token",
  "provider_time": "2026-09-16T01:20:00Z",
  "unsupported_items": 0
}
```

必须满足：

- 账号、提供方、区间、范围、稳定 ID 和收件时间在候选离开已登录页面前全部校验。
- `complete=true` 表示服务商已经证明本次请求区间在单次响应内完整，绝不表示“第一页加载完成”。
- `overflow=true`、未知行、畸形响应、账号变化或请求模板不可用，都会阻止边界推进。
- Reader 对当前账号类型只声明一种已验收的 `provider_mode`；Gateway 不通过静默 type assertion 猜测可选能力。
- 凭据、SID、Cookie、Bearer、请求模板和服务商下载 URL 不得进入 checkpoint、日志或公开状态。

三种模式：

| 模式 | 语义 | 是否满足“不再询问旧邮件” |
|---|---|---|
| `change_cursor` | 服务商严格返回某个已提交不透明令牌之后的变化 | 在令牌及重置行为实机验收后满足 |
| `time_range` | 服务商执行收件／变化时间范围条件，只返回该区间 | 满足，仅允许一个本地去重的有界精度重叠 |
| `anchored_head` | 服务商不能按时间过滤，只读取一次头部响应并在持久锚点停止 | 不满足；只允许人工诊断，普通自动轮询不得启用，因为它会重复返回旧元数据 |

## 5. 普通轮询状态机

### 5.1 接纳

1. 获取既有单邮箱采集租约。不同邮箱可并行，同一邮箱不得重叠。
2. 校验已登录账号和受管 Reader 的精确部署代次。
3. 读取 checkpoint、仍可重试失败索引和至多一个待确认溢出区间；一次性固定新 `inflight_until`，优先采用已验证的服务商时间，否则使用有界 Gateway 时钟。调度器绝不读取已抑制邮件详情行。
4. 正常只调用一次 `listChanges(poll_through, inflight_until, limit=50)`。上轮列表失败后，未变下界自然包含原失败区间。若紧邻上一响应发生溢出，本轮唯一请求改为确认被冻结的原区间，绝不扩大区间。

### 5.2 候选筛选

- 账号或范围不一致立即拒绝。
- 只为确定性处理按 `(received_at, provider_message_id)` 规范化排序；不得因本地排序推断服务商覆盖完整。
- 将新返回稳定 ID 与合格邮件失败次数恰好为一的精确 ID 合并为一个去重工作集。
- 请求原件前先用该工作集查询 EmailRepository。
- 已完成采集、用户主动清理过的采集、`sync_suppressed` 稳定 ID、以及已落盘可补登记的采集全部跳过；不再次下载、解析、哈希或分析。
- 只有缺失原件进入批次。

### 5.3 本地快速路径

正常小邮件批次按以下方式处理：

1. 提供方适配器通过已经验收的原件操作取得缺失原始字节。
2. 小原件可在一次受限页面批次中返回；大原件继续使用既有有界下载回执路径。
3. 一次采集流同时计算大小和 SHA-256，只做取得 `Date:`、身份依据和粗粒度信封合法性所需的有界信头探测，不在此处完整解析正文和附件。
4. `message.eml` 与 `capture.json` 写入新的 staging 目录。任何来源 rename 前，先用一个有界批次恢复日志记录全部稳定 ID、staging 路径、最终路径、字节数和哈希。非空批次只支付一次日志文件持久化屏障和一次日志目录屏障；空轮询不写日志，也不执行 `fsync`。
5. 日志持久后，再把各 staging 原子 rename 到最终 owner-scoped 目录；来源文件和单封目录都不单独同步 `fsync`。因此断电可以丢失可重取字节，但不会丢失精确恢复目标：启动按日志直接收养已验证最终来源、完成有效 staging 移动，或排入定向重读，不扫描日期树。
6. 一次等价于 `PublishEmailSyncBatch` 的 Store 事务同时接纳观察、登记所有完整采集、为每个新来源只排入一次完整异步 MIME 解析并推进 checkpoint。只有确定性 Store 命令确认提交后才删除日志；残留日志可安全重放。Memory、File、PostgreSQL 必须语义一致。

这是有意用可重新获取来源字节的同步断电持久性换取普通轮询低延迟。系统不会静默信任缺失文件：重启后，数据库标为 complete 但文件缺失或哈希错误的采集改为 `source_missing`，创建或更新开放失败，并停止宣称原件可用。检测本身属于运维修复事件，不消耗合格邮件失败次数；该精确 ID 成为下一次定时轮询的目标，也可通过刷新提前修复，只有全部共享前置条件通过后的单封重读失败才启动该邮件的两次尝试序列。

### 5.4 提交

发现与原件实体化分开提交，但必须原子记录二者关系：

- 当 `complete=true`、`overflow=false` 且 `unsupported_items=0` 时，每个返回稳定 ID 必须先持久记录为已完成、已有意清理、新近提交、仍可重试或 `sync_suppressed`。只有之后，同一 Store 事务才可设置 `poll_through = inflight_until`；若此前没有覆盖缺口，同时设置 `discovered_through = inflight_until`、安装已验收下一游标并清空 `inflight_until`。
- 只要精确稳定 ID 和重试证据已持久，原件、落盘或校验失败不阻塞发现水位推进；它们改为更新重试积压。
- 畸形、partial、错误账号、login-required 或列表失败不推进任一水位。下一次定时轮询保留同一 `poll_through`，选择新上界，只重发一次合并区间请求。overflow 使用下文独立的“冻结并确认”转移，绝不反复请求不断扩大的区间。
- Store 未知结果必须先用确定命令键对账，后续轮次才可修改同一邮箱状态。

解析或模型失败不阻塞发现或来源提交。后续每轮仍按时运行。邮件级首次失败最多再随轮补一次：成功则解决但不删审计；第二次合格失败则原子把稳定 ID 标为 `sync_suppressed`，从重试集移除并保留终态告警。

## 6. 三家邮箱的独立设计

### 6.1 QQ 邮箱

权威收件证据是 `totime`，同步不使用发件方时间。

已实现 transport 与验收规则：

1. 原生 `/list/search` 已执行真实观察的 `after`／`before` 范围，再精确校验 `totime`。当前源码实机矩阵通过；安装路径验收和仅合成覆盖的边界仍按第 16 节分开记录。
2. 模式为 `time_range`；原件继续使用 `/read/readmail?func=5`。
3. 缺少已接受范围证据的账号仍为未验收；`anchored_head` 仅诊断，不得作为重复读取旧元数据的自动回退。

不得用 `page_now`、行 offset、总数或第一页哈希伪造增量游标；新邮件会移动这些值并造成缺口。正常 v2 不轮换文件夹，也不请求第二页。单响应超过上限时进入 `overflow` 并留下失败记录。正常业务验收要求单响应覆盖预期轮次量；溢出遵循第 7 节的有界“冻结并确认”，绝不把失败区间永久扩大。

### 6.2 Gmail

Gmail 已实现 `time_range`：受管 Reader 将原生有界搜索绑定到 `after:`／`before:` 查询，并校验内部收件时间。没有已观察 `/sync/u/<account>/i/bv` 模板时，触发原生有界搜索并直接消费该响应，不再额外重复重放。

v2 适配器必须：

- 继续以服务端查询作为首要筛选；
- 对秒精度／排他搜索语义最多保留一秒下界重叠；
- 在本地应用精确毫秒半开区间和稳定 ID 去重；
- 普通轮询只接受一个响应；出现不透明下一页令牌即为 `overflow`，不自动翻页；
- 观察到的列表请求模板或账号身份不可用时显式失败；
- 继续使用已经验收的 Gmail 原件请求，绝不退回 DOM／菜单导出。

本文不假设 Gmail History API 可用：当前产品使用已登录浏览器会话，没有单独配置 Gmail OAuth scope。未来 History API 适配器应作为单独验收的 `change_cursor` 模式。

### 6.3 Outlook

消费者版 Outlook 使用真实观察到的原生 `/searchservice/api/v2/query`，指定 `EntityType: Message`、显式 `received>=start AND received<end` 语义，以及由 `findFolders` 证明完整的入站文件夹集合。启动时 `findConversation` 文件夹证据和账号身份必须一致。partial、数量不符、未知实体、错误文件夹／账号及畸形响应均拒绝；HTTP 200 本身不是覆盖证明。

稳定提供方身份采用 `Source.ImmutableId`，按原生 URL-safe Base64 规则规范化（`_` 转 `+`、`-` 转 `/`）。普通 `Source.ItemId` 可能随文件夹移动变化，不能回退用作稳定身份；缺少 immutable 身份即不支持。文件夹是观察属性，不是第二封邮件的标识。

原件使用页面原生 webpack EML URL builder 和原生邮箱配置。路由别名及 token 留在页面内；当前 DOM 账号、已验证启动身份与原生配置必须一致。下载前校验返回 URL 的允许 origin／path、精确 immutable ID 和 EML 输出格式。旧 `ItemExport` 返回 `downloadUrl` 的假设、模板重放及任意重写返回 URL 中 ID 的逻辑已删除；原件只委托原生 resolver。

早先失败探测使用折叠 `Conversation` 结果，以及没有显式 AND 的相邻收件条件。它只说明该探测语法不合格，不能证明 Outlook 不具备范围能力。修正后的逐封 Message AND 查询及 immutable-ID 原件操作已通过实机验收（第 16 节）。

消费者版验收模式是 `time_range`，不是 Microsoft Graph delta。Microsoft 365 独立保持未验证、不支持；不继承消费者版证据，也不启用头页回退。

## 7. 定时随轮补齐与刷新

定时轮询与 owner 已认证的**刷新**键调用同一个邮箱复合命令。区别只是触发时间：调度器等到 `next_poll_at`，刷新则要求立即执行一轮。

每轮行为确定：

1. 只读取仍可重试的首次失败索引、至多一个待确认溢出区间和当前 checkpoint。worker 绝不读取或扫描已抑制邮件／终态缺口详情行；`suppressed_mail_count` 与 `coverage_gap_count` 在状态转移时事务更新，告警详情只由独立分页界面查询。
2. 只准入有一次合格邮件级失败的精确稳定 ID。先收养已完整校验的落盘来源；只有缺失或无效来源才再次下载。若这第二次合格尝试仍失败，原子标记 `sync_suppressed`，以后永不再准入。
3. 独立发出一次 `listChanges(poll_through, new_fixed_upper)` 查询新邮件，因此已知原件失败不会阻塞新发现。唯一例外是待确认的冻结溢出区间：它占用本轮唯一列表请求，但不扩大上界。
4. 如果上次普通列表失败发生在得到稳定 ID 之前，`poll_through` 就未推进；这一次新请求自然从原失败下界覆盖到新上界。
5. 在任何原件请求前，对重试 ID 和新发现 ID 去重；随后在同一提交中写入成功结果、更新失败和发现状态。
6. 第一次 `overflow` 时，精确冻结 `[poll_through, inflight_until)` 并把确认次数置为一。下一次定时轮询或更早刷新只原样重发该冻结区间一次。若仍溢出，则把缺口标为终态、增加 `coverage_gap_count`、让 `discovered_through` 停在缺口起点、把 `poll_through` 置为冻结缺口终点，并从下一轮恢复实时尾部轮询。已返回稳定 ID 仍可提交，但覆盖状态必须明确为不完整。终态缺口不再被定时或刷新重试，也不启动隐藏 continuation 循环。

溢出表示单个响应无法证明冻结区间完整。触发条件包括：服务商返回数量超过已验收上限、出现下一页／continuation 令牌、响应明确标记 partial、存在会破坏完整性证明的 unsupported 行，或 `anchored_head` 响应已填满但仍未到达请求下界。一个轮询区间内突发超过 50 封合格邮件是普通例子；同一服务商时间戳下超过 50 封是边界例子。限流、登录失败、transport 畸形和请求模板丢失属于运维失败，不是 overflow。

双水位有意把事实完整性与继续运行分开。`discovered_through` 永不越过冻结缺口，因此产品不能宣称历史连续覆盖完整；`poll_through` 只有在唯一确认仍溢出后才越过缺口，使后续新邮件继续且不再为失败区间支付每轮成本。这不会静默修复缺口；未来显式审计或更小时间片修复属于另一项功能。

概念人工命令为 `POST /api/email/sync/refresh`。客户端只提交邮箱选择和它展示的 checkpoint revision；服务端从 Store 解析仍可重试的失败、下界和服务商游标，客户端不能指定任意历史范围或提供方 ID。刷新若遇到同邮箱已排队或运行的定时轮次，则合并到该作业。按钮禁用并显示进度，直到轮次进入终态。已抑制邮件只是可读告警历史，刷新绝不将其重新排入。

登录失败保持开放，直到验证原账号。定时轮次和刷新都可验证或展示既有登录 handoff，但错误账号或再次登录失败不会清除记录，也不会禁用以后的调度。

## 8. 失败留痕与修复模型

每次特殊失败都必须持久化。`EmailSyncFailure` 是内部概念记录，包含：

- failure ID、owner、邮箱、binding generation、provider mode、Reader revision 与 checkpoint revision；
- 发现下界和上次尝试上界，以及失败阶段：`list`、`original`、`persist`、`store_commit`、`verify`、`login`、`overflow` 或 `interrupted`；
- 安全错误码、已知时的受影响稳定邮件 ID、成功／失败数量和字节数；
- 连续合格邮件级失败次数、`first_failed_at`、`last_failed_at`、`last_attempt_at`，以及 `open`、`retrying`、`resolved` 或 `suppressed` 状态；
- 解决或抑制时间、方式 `scheduled_retry`、`manual_refresh` 或 `two_failure_suppression`、操作 actor（`system` 或已认证 owner）和最终安全结果。

精确提供方 ID 仅在内部保存，以便定向重读；公开界面和日志只展示本地告警编号、邮箱标签、可用时的观测收件时间、阶段、数量、时间和安全错误，不展示主题、正文、地址、服务商 ID／游标、凭据、请求模板或下载 URL。

确定性键把重复故障合并到同一失败。精确 ID 失败按邮箱绑定和稳定 ID 建键，阶段作为 attempt 证据保留；普通列表区间失败按邮箱绑定、阶段、未变 `poll_through` 和服务商游标代次建键，每轮可扩大尝试上界而不新建活动失败；overflow 则冻结上下界且只允许一次确认。每次定时重试和人工刷新都追加审计事件，记录触发方式、actor、failure revision、invocation ID、起止时间和结果，但只有合格邮件级失败才增加抑制计数。

每个适配器结果必须携带类型化 `failure_scope`：`mail_specific`、`provider_operational` 或 `local_operational`。两次阈值只对 `mail_specific` 计数，并且所有共享前置条件必须通过：账号与服务商会话已验证、列表身份已验收、本地工作区可写且容量充足、Store 可用。网络、超时、DNS、Controller 不可用、登录／账号、限流、服务商 5xx、服务商全局请求模板、磁盘容量、权限或 Store 失败均属运维失败；它们不增加某封邮件的合格失败次数，也不得抑制该邮件。

只有精确稳定 ID 已绑定到单封原件操作，且失败证据明确属于该单封时，结果才能是 `mail_specific`。例子包括服务商逐项返回的不存在／导出拒绝、单封大小拒绝、原件畸形、重复的单封哈希／MIME 校验失败。稳定 ID／回执不匹配只有在同一 Reader revision 的其他精确操作于本轮成功，或隔离重放证明仅属于该 ID 时才计数。若一轮中两个及以上 ID 出现相同的疑似邮件级阶段和安全错误，则整组在 Store 提交前提升为 `provider_operational`，所有邮件计数均不增加。Store 事务把类型、同组证据和计数转移一起持久化，后续启发式不得追溯性地抑制邮件。

第一次合格邮件级失败保持 `open`，可由后续一次定时或人工尝试。成功则改为 `resolved` 并结束连续失败序列；审计仍保留，但以后独立发生的新故障从零计数。第二次连续合格失败原子把失败与邮件投影改为 `suppressed` / `sync_suppressed`；它从待处理集移除，重新发现时按稳定 ID 跳过，定时轮询和刷新都不再重试。因此，一次成功实体化前后的旧失败绝不会被跨接成抑制。该转移还会恰好一次增加邮箱汇总计数并生成本地告警编号，但绝不把详情行放回调度索引。

| 故障 | 下一次定时轮询 | 刷新 |
|---|---|---|
| 得到合格列表结果前断网 | 保持 `poll_through`，到新上界发出一次范围请求 | 立即运行同一个合并范围请求 |
| 某邮件第一次合格原件／同步尝试失败 | 保留成功采集；重试该精确稳定 ID 一次，同时列取新邮件 | 立即使用唯一剩余合格尝试 |
| 同一邮件第二次合格尝试失败 | 原子标记 `sync_suppressed`，永不重试并继续轮询新邮件 | 只展示终态告警，不重新排入 |
| staging 存在时进程终止 | 启动时记录 `interrupted`；下一轮先删除无效 staging 或收养完整来源，再定向重读 | 立即触发同一有界对账 |
| 文件已落盘但 Store 提交失败 | 对账确定 Store 命令，再只对有界已落盘文件重算哈希并免下载收养 | 立即触发同一对账 |
| Store 显示 complete 但文件丢失／损坏 | 隐藏原件；前置条件健康时，这成为该邮件的下一次合格尝试 | 立即使用剩余合格尝试，绝不覆盖抑制 |
| 服务商游标过期 | 从 `poll_through` 用已验收时间范围重试；保留更早终态缺口 | 立即触发同一回退 |
| 登录过期或账号变化 | 验证原账号一次；不可用则保留失败和发现下界 | 立即触发同一验证 |
| 单响应第一次溢出 | 冻结精确区间，下一轮唯一列表请求用于确认一次 | 立即执行唯一确认 |
| 冻结区间再次溢出 | 记录终态覆盖缺口，只把 `poll_through` 推到缺口终点，随后恢复尾部轮询 | 展示／确认缺口告警，不重新排入 |

不存在独立高频重试计时器、定时历史重读、每日邮箱修复、全树遍历或全量重哈希。精确邮件重试只随普通轮询搭载一次；两次合格失败后改为只告警状态。普通未知列表失败仍从唯一未闭合 `poll_through` 继续；确认后的 overflow 改为冻结终态覆盖缺口并退出热路径。一个从未进入已知失败 attempt 的旧收件时间延迟可见邮件，仍是明确限制，或由另一个用户显式触发的审计功能处理。

## 9. 调度

- 计算 `next_poll_at = completed_at + configured_interval`。
- 同一邮箱租约或未完成 attempt 活跃时不得再次启动。
- 开放失败绝不暂停邮箱调度器。下一次普通轮次只携带各首次邮件失败一次，同时查到新固定上界。
- 不存在额外失败重试调度。一封邮件总计最多消耗两次合格同步尝试；第二次失败后进入终态告警，以后轮询对它零工作。
- 已抑制邮件与终态缺口详情行全部排除在调度索引之外。普通轮询只读取 checkpoint、仍可重试失败和本次新返回稳定 ID；对新返回 ID 做一次批量仓储匹配即可跳过已抑制项，不扫描抑制集合。
- 刷新与同邮箱已排队／运行作业合并，只会提前同一调度，不制造并行重试风暴。
- 不同邮箱提供方可以并行；模型分析继续使用独立 worker。
- 轮询节奏可以按直接本地同步的实测时间重新规划。第 19 节实现了本次选定的“完成后等待 60 秒”默认值，不代表邮箱设置页已提供间隔调节控件；checkpoint 语义不绑定以前的 20 分钟假设。

## 10. 不泄露内容的可观测性

每轮只记录有界运维字段：

- provider/account binding ID、provider mode、Reader revision、checkpoint revision；
- `discovered_through`、`poll_through`、`inflight_until`、最终状态、安全错误码；
- 服务商请求数、返回条目数、新稳定 ID 数、已完成跳过数、修复数、overflow 标志；
- 原件数量和总字节数；
- `list_ms`、`download_ms`、`journal_ms`、`persist_ms`、`store_commit_ms`、`total_ms`；
- 触发方式（`scheduled` 或 `manual_refresh`）、failure revision、合格尝试次数、抑制数及修复／缺失／损坏计数。

不得记录地址、主题、正文、Cookie、SID、请求模板、服务商游标内容或下载 URL。公开同步状态可以展示模式和脱敏降级原因，但不得展示游标。

状态面必须区分：

- `incremental`：已验收的 `change_cursor` 或 `time_range`；
- `unqualified`：没有实机验收的 `change_cursor` 或 `time_range`；普通轮询保持暂停，`anchored_head` 只供诊断；
- `incomplete` / `overflow_confirmation` / `coverage_gap` / `login_required`；
- 仍可重试失败数、已抑制邮件数、终态缺口数、最早失败时间、上次尝试时间、安全阶段、下次定时尝试，以及刷新是否可用；
- owner 可见的持久提醒，例如“1 封邮件连续两次同步失败，已停止同步”；可显示本地告警编号、邮箱标签、可用时的观测收件时间、安全错误和尝试时间，日志与公开状态不展示主题、正文、地址、服务商 ID 或凭据；
- 来源采集进度与异步解析／模型进度。

告警持久性与视觉打扰分离。抑制和覆盖缺口审计记录不可变；owner 可以确认告警，系统记录 `acknowledged_at` 与 `acknowledged_by`，并将其从未确认角标／横幅计数移除，但详情仍保留在分页历史中。确认绝不重置 `sync_suppressed`、关闭覆盖缺口或让该项获得刷新资格。同步状态只读汇总计数；owner 打开告警历史时才按需读取详情行。

## 11. 迁移与旧链路删除

v2 切换不恢复已删除历史。

1. 保留 9 月 11 日部署锚点。
2. 当前邮箱边界完整且 cursor 为空时，同时复制为 `discovered_through` 与 `poll_through`。
3. 遗留区间为 partial 时，以其 start 作为两个水位，丢弃 `n1:`、`q1:`、页码、指纹和页面确认，并创建一条开放迁移失败。下一次普通轮询从该下界覆盖到新上界；刷新可提前触发同一轮。
4. 只有提供方能力与 Store checkpoint 写入均成功，才设置 `scope_version=timeline-v2`。
5. 三个已配置提供方都有明确 v2 模式后，删除正常 `collect_page` continuation 循环、前缀链复核、旧页面 checkpoint 和兼容分支；不得保留两套调度器。
6. 新 checkpoint 与批量命令必须同时实现 Memory、File snapshot 和 PostgreSQL。

没有验收增量能力的提供方必须标记 `unqualified` 并暂停普通轮询；迁移不得把头部页面适配器静默标成 `time_range`，也不得把 `anchored_head` 作为发布回退启用。

## 13. 验收门槛

### 公共确定性门槛

- 连续 100 次零新增轮询推进 100 个不同完成区间，原件请求、文件写入、解析作业和模型作业全部为零。
- 正常轮询严格只有一次服务商列表／变化请求，绝不请求 continuation 页。
- 五封新小邮件恰好产生五个逻辑缺失原件操作和一次 Store 批量提交；适配器可以用一次有界物理批量请求承载这五个操作。再次发现时为零。
- 多封邮件具有相同服务商收件秒时，跨边界不丢失、不重复。
- 没有早先缺口时，空区间推进两个水位；畸形、partial、unsupported、错误账号和 login-required 结果不推进。第一次 overflow 冻结区间，第二次 overflow 建立终态缺口且只推进 `poll_through`。
- 每次网络、原件、staging、Store、登录和 overflow 失败都创建或更新一条持久记录，但不禁用邮箱调度器。
- 如果第 N 轮一封原件失败，第 N+1 轮必须发出一次新邮件列表请求，并对该精确 ID 尝试一次；不列取旧历史，不重下载成功原件。
- 如果同一邮件的第二次合格尝试仍失败，状态转为 `sync_suppressed`；以后定时轮次和刷新对它的请求数都为零，owner 持续看到提醒。
- 网络、超时、DNS、Controller 不可用、登录／账号、限流、服务商 5xx、服务商全局模板、磁盘容量、权限和 Store 失败均被类型化为运维失败，绝不增加两次邮件失败计数。
- 一轮中两个 ID 出现相同疑似邮件级阶段／错误时，提交前整组提升为服务商运维失败，两者都不计数。稳定 ID／回执不匹配只有在同 revision 同轮有成功同伴或隔离逐 ID 重放证据时才计数。
- 如果第 N 轮列表请求失败，第 N+1 轮使用未变的 `poll_through` 和新上界，一次覆盖失败区间与后续邮件。
- 完整列表响应后，只有每个返回稳定 ID 都持久表示为已完成、已清理、仍可重试或已抑制，原件失败才可不阻塞 `poll_through` 推进；`discovered_through` 只跨越连续已证明覆盖。
- 在每个失败点点击刷新，会立即运行同一个保留区间或精确 ID 复合轮次，不产生静默缺口或重复来源。
- 同一 failure revision 的重复点击合并；成功则标记 resolved，第二次合格失败则抑制该邮件，两种转移都不删除历史。
- 非空批次在任何来源 rename 前先持久恢复日志。日志发布前进程 kill 只留下由陈旧清扫处理的有界、不可见 staging；日志发布后发生在日志／rename／Store／删除的任一边界时，均按日志精确路径恢复，不产生未索引日期树孤儿，并在任何服务商重读前先收养已验证落盘字节；空轮次日志写入和 `fsync` 均为零。
- 外部删除／损坏字节不再宣称可用，并在提供方仍有原件时成为后续一次尝试的精确目标；第二次合格失败终止后续同步。
- 登录失败跨重启和错误账号尝试继续存在；后续轮询仍按时运行，但只有验证原账号后才能解决失败。
- 解析和模型失败不推进也不回滚发现 checkpoint。
- Memory、File、真实 PostgreSQL 的 checkpoint 和重放结果一致。
- 存在 10,000 条已抑制告警且没有仍可重试失败时，一次空轮询读取已抑制详情行为零，不执行随抑制集合增长的查询；告警历史保持分页，确认只改变展示状态。
- 第一次 overflow 只原样重发冻结 `[start,end)` 一次且不扩大；第二次 overflow 生成一个终态缺口，以后轮询不再请求该缺口，实时尾部从 `end` 恢复，状态绝不宣称连续覆盖完整。

## 19. 一分钟轮询与刷新单飞

用户选择持续在线场景，默认改为**采集完成后空闲 60 秒**。这不是每个整分钟强制开始：采集耗时 10 秒再等待 60 秒，两次开始时间约相隔 70 秒。解析／模型任务继续异步执行，不占用刷新按钮锁。

要求如下：

- 同一邮箱自动轮询不重叠，不累计错过的定时触发。
- 空闲时手动刷新，让同一邮箱任务立即执行，只跳过普通轮询等待。
- 自动采集中点击刷新，最多保留一个后续轮次，当前轮结束后执行。后续轮开始时再确定其上界，避免忽略当前固定上界之后到达的新邮件。
- 手动请求排队或执行期间，重复刷新合并。前端第一次点击立即锁定，直到后端确认对应请求结束才解锁，不能仅凭 HTTP 受理成功解锁；跨标签页／组件重挂以后端状态为准。
- 手动轮结束后，下一次自动轮询等待 60 秒。提供商／运行故障的重试退避仍有效，刷新不能绕过退避或复活已抑制邮件。
- 关闭收件或邮箱绑定失效后，待执行刷新不能继续启动。改间隔不清空原件、提醒、进度或收件开关。

调度不能再使用会阻断完成后重排的时间槽幂等键；在完成事务中持久安排下一次自动期限，不新增每秒全量规划／写入循环。已有普通等待任务可协调到新间隔，但必须保留重试退避与活动租约。

缩短间隔能减少逐渐积压，不代表持续吞吐保证，也不解决瞬时超过 50 封的突发场景。既有有界溢出／终态缺口规则不变。本次不扩展离线补齐设计。此后续改动的实现与部署验收，与上方历史性能表分开记录。

### 已实现的调度与刷新契约

Gateway 默认间隔已改为一分钟。由邮箱、绑定代次和间隔限定的稳定激活命令，在既有 discover 作业上安装 `poll_interval`。Memory／File／PostgreSQL 共用的 Store 引擎在 `FinishEmailJob` 完成事务内持久安排下一期限：自动轮或手动轮成功结束后，进入完成时间加 60 秒的空闲等待；自动轮若已有待执行刷新，则立即安排这唯一一个后续轮次。完成后不需要新的规划命令代次。规划器保留原有间隔／唤醒机制；工作器既有的每秒到期检查不会引入新增的每秒全量规划或命令日志写入。

健康的空闲自动作业不计入 backlog。升级仅按旧普通排队任务记录的完成／重排时间缩短其期限，不提前活动租约或 `retry_wait`。运行故障保留有界重试期限和错误证据；某轮运行故障重试耗尽后，释放该轮手动刷新锁并安排下一次普通心跳，不会重置或重新访问任何邮件的 `sync_suppressed` 状态。

刷新契约以邮箱为单位：

- `POST /api/email/sync` 保留 `scheduled`，新增 `refresh_requests: [{mailbox_id, refresh_request_id}]`。并发请求返回同一个已有待执行 ID，不新增作业。
- `GET /api/email/sync-status` 在各邮箱投影中返回 `refresh_pending` 和最近一次 `refresh_request_id`。完成后保留 ID，让客户端能关联本次受理请求的完成状态，而不是将较早的空闲响应误认为完成。
- 自动轮期间收到刷新请求，要等后续刷新轮结束才清 pending。作业另存执行中的刷新 ID，以区分后续刷新与此前已在运行的自动轮。刷新遇到运行故障时，在 `retry_wait` 期间保持 pending；成功或终态耗尽后清除。暂停与绑定替换也会清除 pending，并阻止旧租约继续执行。
- 前端必须在发送请求前立即禁用按钮，再用持久状态确认结果；网络结果不确定不能证明已完成。多标签页和 HTTP 调用者最终由 Store 的 owner 事务串行化，不能仅依靠浏览器本地锁。

作业的安全计时字段 `round_started_at`、`round_finished_at`、`next_attempt_at` 和 `poll_interval` 支持验收实际节奏，无需记录邮箱地址、原件字节或凭据。这些是采集／作业时间，不是模型完成时间。自动化契约覆盖无需再次规划即可执行下一轮、同分钟内手动刷新重计期限、重启、并发请求合并、退避保留、旧期限升级及活动轮次中暂停。这些实现检查不代表已完成实机部署、一分钟长期运行验收或新的邮箱吞吐测量。
