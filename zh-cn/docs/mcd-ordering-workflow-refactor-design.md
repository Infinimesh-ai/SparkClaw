**对外只有一个功能：点餐。一个 Workflow 负责从解析需求到确认本单状态的完整流程；有疑问时用审批弹窗提问；下单成功返回取餐码。**

## 1. 重构前基线的问题

重构前代码（`d3c619e1`）在功能路由下注册了 5 个叶子：`dining.mcd_read`、`dining.mcd_cart`、`dining.mcd_quote`、`dining.mcd_purchase`、`dining.mcd_status`。当前 [catalog.go](../../services/gateway/internal/capability/catalog.go) 和 [workflow_registry.go](../../services/gateway/internal/agent/workflow_registry.go) 只注册 `dining.mcd_order`。以下记录促成本次 R4 重构的旧行为：

1. **流程被拆成了路由选择题。** 用户说“帮我点一份麦辣鸡腿堡套餐”，路由要猜现在处在哪个阶段，是查询、改购物车、报价还是付款。点餐本来是一个连续的任务，被拆成 5 个互相独立的功能，阶段之间的衔接只能靠用户再说一轮。
2. **Workflow 只是工具集合，没有流程。** 每个旧 profile 只有一个节点（`mcd_read` 或 `mcd_selection`），购物车和付款节点让模型在最多 8 轮里自己挑工具调用；原 `mcd_cart_workflow.go` 已删除，由 [mcd_order_workflow.go](../../services/gateway/internal/agent/mcd_order_workflow.go) 替代。阶段顺序、前置条件、何时提问、何时停止，全靠 `StageContext` 里的英文提示让模型自觉遵守，没有确定性推进，也没有依赖关系。这和通用 agent 加一层工具白名单没有区别。
3. **缺信息时没有提问通道。** 提示词要求“不得推断门店、时间、取餐方式”，但缺了信息时，模型只能用最终回答反问。执行一结束，执行级资源（临时购物车目录、报价交接、`review`）就被清理（[execution_workflow.go](../../services/gateway/internal/gateway/execution_workflow.go)）。用户回答后要重新路由、重新建立会话，前面的进度全部丢失。
4. **订单状态没有和点餐流程绑定。** 付款后的结果核对被做成独立的 `dining.mcd_status` 功能，要等用户自己再问；而且它依赖的 `mcd.purchase.status` 只有 `purchase_enabled` 打开时才出现（[mcd_purchase.go](../../services/gateway/internal/toolhub/mcd_purchase.go)）。回滚关闭付款后，结果不明的原订单就无法核对。
5. **输出交给模型自由生成。** 5 个 profile 都使用 `workflowFinalizationModel`，最终回复可能复述菜单、报价甚至凭空编造。用户实际只需要取餐码。
6. **开关关闭时仍会被路由。** 路由叶子不受 `mcd_selection` 开关控制。没有工具时，“必须先调用工具”的检查不会生效（[workflow_step_loop.go](../../services/gateway/internal/agent/workflow_step_loop.go)），模型可能直接回答菜单或价格。

## 2. 目标与非目标

目标：

- 功能路由只保留一个叶子 `dining.mcd_order`（点餐）。
- 一个 Workflow 用多节点 DAG 表达完整流程，由运行时按节点确定性推进。模型只负责两件事：把用户原话解析成结构化点餐意图；在官方菜单候选里做匹配排序。
- 信息缺失或有歧义时，用 `notify.ask_approval` 输入表单弹窗提问。回答后在**同一次执行**里继续，不重新路由，购物车和报价状态都保留。
- 未说明的信息使用确定的默认值，不追问：数量默认 1 份，取餐时间默认最早可取，优惠自动选最优方案，金额上限默认取账号的单笔限额。
- 流程内写购物车不逐次审批，付款审批是唯一的放行关口；清空原购物车仍需确认。
- 首版只开放已通过真实验证的取餐方式（目前为 `locker-in` 取餐柜）。
- 付款确认沿用现有的不可变审批（`mcd.purchase.commit`）。
- 每次点餐结束时，Workflow 自己确认本单状态并按状态处理；下单成功返回取餐码。

非目标：

- 不提供独立的“查上一单”功能。
- 不提供独立的“浏览菜单”或“查优惠”功能。
- 不新增支付渠道（仍只用 `ARCHCARD`）。
- 不修改 Mac 账本、授权摘要、报价交接、ISCP 操作或凭据流转。
- 不替换现有审批组件和连接设置页面，只按需调整文案。

## 3. 功能路由

| 项 | 重构前基线 | R4 源码实现 |
|---|---|---|
| 叶子 | 5 个 `dining.mcd_*` | 1 个 `dining.mcd_order`，`Operations: [draft]`，`RequireQuery: true` |
| 路由样例 | 每个叶子各有一组 | “帮我点一份麦辣鸡腿堡套餐”“在公司楼下那家麦当劳点两个巨无霸，12 点到店取”“用麦钱包买个早餐，30 块以内” |
| 硬负例 | 叶子之间互相排斥 | “麦当劳的历史”“麦当劳热量多少”“附近有什么快餐”“我上一单麦当劳付成功了吗”（交给通用回答或搜索，不进入点餐） |
| 不可用时 | 照常路由，模型自由回答 | 照常路由到本叶子，入口节点直接给出固定提示，不调用模型 |

不可用时保留路由，是为了让“帮我点麦当劳”得到明确提示，而不是被其他功能误接、编造答案。这与项目 UI 约定一致：入口保留，能力禁用。

开关：配置项 `enabled`、`cart_enabled`、`purchase_enabled` 保留，以兼容回滚，三项均默认关闭。点餐要求三项同时开启，且 ISCP 已协商并通过资格检查（现有 [execution_authorization.go](../../services/gateway/internal/gateway/execution_authorization.go) 的逻辑）。状态核对只需要 `enabled` 加 `mcd.operation.status` / `mcd.orders.query`，使用独立的 `AllowMCDStatus`，不依赖 `cart_enabled` 或 `purchase_enabled`。这样回滚关闭付款后，入口节点仍能先核对未决的原订单，再回复“暂不可用”。既有接入能力完整保留，继续受各自的资格门槛控制；单一点餐叶子只收拢用户侧编排，不删减适配器能力清单。

取餐方式：新增配置项 `mcd_selection.qualified_eat_types`，默认 `["locker-in"]`。只有列表里的取餐方式才会出现在候选和弹窗中。普通到店取餐（`take-in-store`）的报价交接通过真实验证后，再加入列表，代码不需要改动。

## 4. Workflow：`dining.mcd_order`

profile 实现 `workflowRuntimeStageProfile`，每个节点由 `RunStage` 直接执行，做法与药箱编辑相同（[medicine_profiles.go](../../services/gateway/internal/agent/medicine_profiles.go)，[medicine_edit.go](../../services/gateway/internal/agent/medicine_edit.go)）。麦当劳工具不再出现在模型可见的工具列表里，由阶段代码直接调用。Finalization 改为确定性模板。

```text
guard ──► intent ──► context ──► menu ──► offer ──► cart ──► quote ──► pay ──► settle
  │                     │          │                   │         │         │        │
  └─ 有未决订单：停止   └─ 弹窗 ───┘          (清空确认)┘  去券重报一次  付款审批  └─ 确认本单状态并处理
```

| 节点 | 执行方式 | 调用 | 产出 / 结束条件 |
|---|---|---|---|
| `guard` | 确定性 | `mcd.purchase.status`（恢复模式） | 安全闸门，不对用户暴露为功能。如果存在之前结果不明的原操作，先核对一次：已核验为 `PAID` 或 `CANCELLED` 就释放冻结，继续本次点餐，并在最终回复里附一行上一单的结果；仍不明确就停止，回复固定话术，**不进入新订单** |
| `intent` | 模型，结构化输出，无工具 | — | `OrderIntent`（见 4.1）。只记录用户原话里的信息，不得填写任何官方标识 |
| `context` | 确定性读取 + 表单 | `stores_favorites`、`cities_list`、`stores_search`、`pickup_methods`、`pickup_slots` | 唯一的门店、取餐方式、取餐时间。门店一律由用户在弹窗中确认，流程见第 4.4 节。取餐方式和取餐时间在用户原话与候选恰好唯一对应时自动采用，否则加入提问表单。取餐方式只在 `qualified_eat_types` 与门店支持方式的交集里选；第 4.4 节已保证确认的门店至少支持其中一种。取餐时间未说明时直接采用 `pickup_slots` 中距现在至少 3 分钟的最早时段，不提问。首次写购物车前，若这个默认时段已不足 3 分钟，就重新读取并替换；用户指定的时间已过时停止点餐 |
| `menu` | 确定性读取 + 模型排序 + 表单 | `menu_list`、`product_detail` | 每个意图条目绑定到唯一的 `product_code`，并补齐必选配置组。模型只能从给定候选里挑并排序，运行时校验结果属于候选集合。不唯一时提问。数量未说明时按 1 份 |
| `offer` | 确定性 | `coupons_list`、`coupon_products`、带 `coupon_ref` 的 `product_detail` | 按第 4.2 节，在写购物车之前为每一行选定用券或不用券，不提问 |
| `cart` | 确定性写入，不逐次审批 | `cart_snapshot`、`cart_clear`、`cart_add_simple` / `cart_add_configured`、`checkout_quote_pickup` | 按 `offer` 的结果写入，购物车与计划逐行一致。原购物车非空且与计划不同时，弹窗询问“清空后继续 / 取消”，这是流程内唯一与购物车写入有关的确认 |
| `quote` | 确定性 | `mcd.quote.prepare` | 完整报价交接到原 Mac，生成 `review`。按第 4.2 节校验优惠；总价超过金额上限时，在付款审批前停止 |
| `pay` | 现有不可变审批 | `mcd.purchase.commit`（参数由运行时绑定） | 审批弹窗展示门店、时间、方式、明细（含默认数量）、所用优惠、金额和 `ARCHCARD`。拒绝时撤销准备，不下单 |
| `settle` | 确定性 | `mcd.purchase.status`、按需 `mcd.orders.query` | 每次点餐结束都会执行，见第 4.3 节 |

所有提问都发生在 `cart` 之前（`cart` 内的清空确认除外）。

购物车写入不逐次审批。现有 `mcd.cart.write` 定义为需要审批（[mcd_cart.go](../../services/gateway/internal/toolhub/mcd_cart.go)），重构后由 `cart` 节点直接调用，不再走逐次审批：购物车可以撤销，不会产生订单或扣款，下单前的完整明细由付款审批统一确认。写入仍遵守现有的操作键、快照和结果不明时只核对不重试的规则。用户在提问弹窗里点拒绝，就是取消点餐：此前没有任何写操作，直接回复“已取消，未下单”。

执行约束沿用现有机制：整个流程在一次执行里完成。等待审批时执行不结束（[execution_workflow.go](../../services/gateway/internal/gateway/execution_workflow.go) 中的 `continueExecutionApprovals`，最多 32 轮，总预算 15 分钟）。报价的 120 秒有效期和付款审批后最多 2 次刷新的规则不变，内容变化必须重新审批。计划内的去券重报属于新的方案报价，不占用刷新次数。请求次数按第 4.5 节控制。

### 4.1 `OrderIntent` 结构化输出

```json
{
  "items": [{"text": "麦辣鸡腿堡套餐", "quantity": null, "notes": "可乐去冰"}],
  "store_text": "公司楼下",
  "pickup_method_text": "到店取",
  "pickup_time_text": "",
  "max_amount_text": "30 块以内"
}
```

使用严格的 JSON Schema，不接受任何门店编码、商品编码、券编码或金额数值。默认值由运行时填写，模型不填：

- `quantity` 为 `null` 时按 1 份。
- `pickup_time_text` 为空时取最早可取的时段。
- `max_amount_text` 由运行时解析成整数分，作为本单金额上限。为空时，取账号本地 Policy 的单笔限额 `max_order_cents`，因为上游报价必须带金额上限（`max_amount_cny`）。用户说的上限高于单笔限额时，以单笔限额为准。原话里写了上限却无法解析成金额时，提问确认。
- 每日预算和每日单数限制（上游默认每单 20 元、每天 20 元、每天 1 单）保持不变；本设计不放宽默认值，也不新增配置界面。超出这些限制时按“需要用户处理”回复。

模型调用失败时，按项目约定回复“模型暂时不可用”。

### 4.2 优惠选择

默认自动使用最优惠方案，不向用户提问。

约束：麦当劳的券是“券价商品”，以带 `coupon_ref` 的一行加入购物车；购物车只能整体清空，不能删除单独一行。另外，同一次执行里，报价一旦交接到 Mac，在撤销之前不能再次报价（[cart.go](../../services/gateway/internal/mcddining/cart.go) 的 `quoteLocked`）。因此不做多次报价比较，而是在写购物车之前定好方案，只报一次价，必要时去券重报一次。

1. **候选**：对每个意图条目，取 `coupons_list` 中当前可用、`coupon_products` 表明对应同一商品、且上游标记可直接加入购物车（`cart_configuration_supported`）的券价商品。需要额外加购才能满足条件的券、需要在官方 App 配置的券都不采用；不为凑券改变用户点的餐。
2. **逐行定方案**：用券价商品的展示价与 `menu_list` 的菜单价比较，两侧均计入已选组件和加料的额外费用，券价更低才用券。组件数量乘以其额外价格和内部加料费，再按餐品行数量计算完整价格；用券必须保留已选配置。同一张券同时可用于多行时，按节省金额从大到小分配，不超过券的剩余次数。展示价只用来挑方案，不是最终价格。
3. **报价校验**：`quote` 节点拿到完整报价后，检查以下几点：
   - 每一条计划用券的行，都在报价中以绑定了券（`coupon_fingerprint`）的同商品、同数量行出现，没有计划外的用券行，且 `discount_cents` 大于 0。`discount_names` 与券列表标题取自上游不同字段，只用于展示，不参与比对；
   - 总价低于全部按菜单价计算的价格；
   - 总价不超过金额上限。
4. **去券重报**：校验不通过时，Mac 撤销本次准备，然后清空购物车、去掉所有券重新写入，再报价一次。重报后仍超出上限就停止。每单最多两次报价。只有在这次去券重报仍在请求预算内时才会计划用券（第 4.5 节）。
5. **超出上限**：不用券的方案也超出上限时，在付款审批前停止，回复固定话术，不自动删减商品。

付款审批弹窗列出最终采用的优惠名称和减免金额。审批之后不再换券。

### 4.3 结束确认（`settle`）

每次点餐结束都由 `settle` 确认本次点餐的状态，用户不需要另外查询。

| 本单状态 | 处理 |
|---|---|
| 已核验 `PAID`，回执带有取餐码 | 回复取餐码 |
| 已核验 `PAID`，取餐码尚未生成 | 在剩余执行时限内最多查询 3 次（立即、3 秒后、8 秒后）；仍没有取餐码时，有订单号就回复订单号，并说明取餐码生成后可在麦当劳 App 查看。已核验的 `PAID` 不会被回复为未确认 |
| 已核验 `CANCELLED` | 回复“订单已取消，未扣款” |
| 结果不明（响应丢失、超时、助手中断） | 只核对原操作，在剩余预算内最多查询 3 次，不重试写入；仍不明确时回复固定话术，下次点餐时由 `guard` 自动再次核对 |
| 付款在发出前失败（报价过期且无法刷新、最后一次允许的审批后内容又变化、授权不匹配） | 撤销准备；只有两端账本都证明没有发出任何写入时，才回复未下单及原因，否则按结果不明核对 |
| 撤销或拒绝（用户拒绝付款审批、超出上限等） | 确认准备已撤销，没有遗留的写入声明，回复对应话术 |
| 官方要求用户处理（余额不足、需在 App 验证等） | 确认未发出付款，回复用户可处理的原因 |

### 4.4 门店确认

门店每次都要用户确认，不自动采用。门店确认是 `context` 的第一轮提问，取餐时段和菜单都依赖它。

1. **检测常用门店**：读取 `stores_favorites`，用户原话提到的门店排在前面。按此顺序最多预检 5 个门店的 `pickup_slots` 和 `pickup_methods`，并且只在之后一次优惠券探索和必需的点餐流程仍在请求预算内时才预检（第 4.5 节）。已预检且不支持 `qualified_eat_types` 的门店被去掉；其余门店照常列出，选中后再检查（第 5 步）。
2. **有常用门店：确认常用门店**。弹窗 `store` 列出剩余的常用门店；用户原话提到门店时，与原话匹配的排在第一。另外固定提供两个选项：“不用这些，选择其他门店”和“取消点餐”。只有一个常用门店时同样要确认。
3. **没有常用门店，或用户选择“选择其他门店”：打开门店选择**。按官方选店接口分两轮：
   - 第一轮：`city`（select，来自 `cities_list`）和 `store_keyword`（text，可选，最长 40 字，例如区域或路名）。关键词只作为 `stores_search` 的检索条件，与官方 App 选店时的搜索框相同，不会被当作门店标识。
   - 第二轮：`store`（select），按官方顺序列出 `stores_search` 的结果，最多 3 页、90 个，显示“门店名 · 地址 · 营业时间”。另外提供“重新搜索”（回到第一轮）和“取消点餐”。
4. **用户选中即为确认**：在常用门店或选店结果中选中一个门店，就是用户的确认，不再追加一轮确认。付款审批会再次展示门店。
5. **选中后校验**：从选店结果或未预检的常用门店中选中的门店，再查一次 `pickup_methods`。不支持已开放的取餐方式时，提示后回到同一列表并去掉该门店。
6. **上限**：门店选择最多重新搜索 3 次，超出后回复固定话术，不下单。这些读取都计入现有的请求预算。

### 4.5 请求预算

每次执行最多预留 128 次上游请求，即购物车会话原有的总额度，不作改动。每次调用在发出前按该调用的最大次数预留，用不完也不退回。按这些最大值计算，预检一个常用门店、只点一行的普通订单预留 57 次；用一张券多 14 次，可能的去券重报多 41 次，付款审批后的一次报价刷新需要 19 次。

- Workflow 从网关的连接记录读取本次执行剩余的预留额度（只读，不预留），并按同样的单次最大值计算必需的剩余开销：所选门店的检查、未完成的菜单读取、默认时段的重读、可能包含清空的购物车流程，以及计划用券时的去券重报。
- 在第一个门店问题之前，如果必需流程放不下，直接用固定话术结束，不做任何上游读取。
- 可选读取只在完成后仍能容纳必需剩余开销时执行：常用门店预检（同时为一次优惠券探索留出余量）、更多搜索页、整份菜单兜底和每一次优惠券读取。放不下优惠券时，按菜单价继续点餐。
- 首次写购物车前再检查一次必需剩余开销，因此不会在改动购物车之后才因额度不足停止。
- 付款审批后的报价刷新尽力而为：额度不够时撤销已过期的报价，并回复未下单。

## 5. 提问弹窗

提问复用 `notify.ask_approval` 和 `ApprovalInputForm`（[approval_inputs.go](../../services/gateway/internal/app/approval_inputs.go)；WebChat 端是 [approvalInputForm.tsx](../../apps/webchat/src/components/approvalInputForm.tsx)），不新增组件。

只有下表这些情形会弹窗提问，其余信息使用默认值：

| 疑问 | 字段 | 选项来源 | 触发条件 |
|---|---|---|---|
| 门店（常用） | `store`（select，含“选择其他门店”“取消点餐”） | 支持已开放取餐方式的常用门店 | 每次点餐、有常用门店时 |
| 门店选择第一轮 | `city`（select）、`store_keyword`（text，可选） | `cities_list` | 没有常用门店，或用户选择其他门店 |
| 门店选择第二轮 | `store`（select，含“重新搜索”“取消点餐”） | `stores_search`，最多 90 个 | 第一轮提交后 |
| 取餐方式 | `pickup_method`（select） | `pickup_methods` 与 `qualified_eat_types` 的交集 | 交集里不止一种，且未说明或不能唯一对应（首版只有 `locker-in`，不会弹出） |
| 取餐时间 | `pickup_time`（select，最早可取排第一） | `pickup_slots` | 说明了时间但不能唯一对应 |
| 商品 | `item_N.product`（select） | 菜单候选，前 20 个，附价格 | 不能唯一对应 |
| 套餐或配置 | `item_N.<group>`（select） | `product_detail` 中的必选配置组 | 原话没有指定该配置组 |
| 金额上限 | `max_amount`（number，单位元） | — | 原话提到上限但无法解析 |
| 清空购物车 | `clear_cart`（select：清空并继续 / 取消） | `cart_snapshot` | 原购物车非空且与计划不同 |

规则：

- 同一轮的疑问合并成一个表单，每个疑问一个 entry，尽量一次问完。下游选项依赖上游答案时（例如先定门店才能查时间段），按依赖顺序分轮提问。
- 选项值都是官方证据里的不透明标识，连同候选快照一起冻结在 `input_context` 中。提交后由现有 `ValidateApprovalInputs` 校验答案属于选项集合，模型不能生成选项值。
- 定制备注只有在完整文本唯一对应一个可用的官方选项时才自动映射。否定、多项或无法匹配的备注随官方配置表单展示，由用户明确确认；没有受支持表单可以解决时停止点餐。备注不静默丢弃，也不按子串猜测匹配。
- 没有合适候选时，提供“都不是，取消点餐”选项，不开放自由文本兜底。唯一的文本输入是门店选择第一轮可选的 `store_keyword`，只用作官方门店搜索的检索条件。
- `ApprovalInputForm` 已增加可选的 `submit_label`（纳入表单摘要），WebChat 优先使用它。标签最多 80 个 Unicode 字符，拒绝纯空白和控制字符。点餐表单使用“确认点餐信息”／“Confirm order details”；未提供时保留药箱文案“补全并写入 {count} 条”，原组件和交互不变。
- 不支持表单的通道（微信、纯文本执行）一律回复“请在 SparkX 客户端点餐”，不降级为文字问答。

## 7. 保留的安全不变量

- Mac 是唯一的会话和付款写入方；凭据不进入模型上下文、日志或回复。
- 付款参数由运行时绑定到完整的 `review`，审批内容不可变；金额、明细、优惠、门店、时间中任何一项变化都要重新审批。优惠选择和去券重报全部在付款审批之前完成，审批后不再换券。
- 购物车写入不逐次审批，但只有 `cart` 节点能按冻结的计划写入，模型不能直接调用写入工具。
- 只用 `ARCHCARD`，不切换支付渠道。
- 结果不明的写操作只做核对，不重试、不换新的操作键；只有核验为 `PAID` 或 `CANCELLED` 才释放冻结。
- 原账本、每日预算、成员锁和撤销记录保持不变。

付款前检查修复已实现：[purchase.py](../../tools/ezmcd-adapter/src/sparkclaw_mcd/purchase.py) 仅在原 attempt 和写入记录证明请求未发出时记录 `NOT_DISPATCHED`，无法证明的失败仍为 `UNKNOWN`。[recovery.py](../../tools/ezmcd-adapter/src/sparkclaw_mcd/recovery.py) 通过既有状态操作，对作用域完全对应且可证明未发出的准备记录持久化退休，并撤销未使用授权，全程不调用 provider。后端只有在受绑定的 `aborted_before_write` 回执落盘后才释放该准备；操作缺失或单独的 `NOT_DISPATCHED` 结果均不足以释放。原尝试、回执和预算保留；退休不宣称官方订单已取消或退款，也不重试写入。

## 9. 迁移与验收

迁移：三个开关在生产环境从未开启，不存在引用旧 Workflow ID 的持久化运行，可以直接删除旧 profile。旧 ID 只在注册表遗留测试里保留拒绝用例。账本、回执和撤销记录不需要迁移。

验收：

- 单元测试：
  - 每个节点的成功、提问、取消和失败路径；
  - 默认值：未说数量按 1 份，未说时间取最早可取；
  - 表单答案越界或被篡改时拒绝；`OrderIntent` 不接受官方标识；模型排序结果超出候选集时拒绝。
- 优惠测试：
  - 逐行选用更便宜的券价商品，券的剩余次数分配正确；
  - 需要加购的券、需要官方 App 配置的券都不采用；
  - 报价校验失败时撤销、去券重报一次，每单最多两次报价；
  - 不用券仍超出上限时停止；未说上限时使用单笔限额。
- 购物车测试：流程内写入不弹逐次审批；清空原购物车必须经过确认；模型不能直接调用写入工具。
- 取餐方式测试：只出现 `qualified_eat_types` 中的方式。
- 门店测试：
  - 有常用门店时每次都确认，只有一个也确认；原话匹配的门店排第一；不支持已开放取餐方式的常用门店被过滤；
  - 没有常用门店或选择其他门店时，进入城市加关键词、门店两轮选择；
  - 选中不支持的门店会回到重新选择；重新搜索超过 3 次时停止；
  - `store_keyword` 只传给 `stores_search`，不会成为门店标识。
- 结束确认测试：覆盖 `PAID`（有或没有取餐码）、`CANCELLED`、结果不明、拒绝和用户需处理等状态；结果不明时只做有限次查询，不写入；下一次点餐时 `guard` 能释放或阻止。
- 夹具端到端：“帮我点一份麦辣鸡腿堡套餐”经过常用门店确认、配置提问、自动选券、付款审批，最终返回取餐码；同时覆盖报价过期刷新、内容变化后重新审批、Mac 离线、开关关闭等场景。
- 路由评测：至少 30 条正例和负例，验证点餐请求进入 `dining.mcd_order`，查单和非点餐请求不进入。
- UI：现有审批组件能正确渲染点餐表单和付款审批，药箱表单的文案和行为不变。功能测试通过不能代替原界面的交互验收。
- 真实付款：仍需用户另行明确授权一笔具体订单，本设计不构成付款授权。

## 10. 已确认决策（2026-11-16）

1. 不提供“查上一单”功能。每次点餐结束时，由 `settle` 确认本单状态并按状态处理；之前未决的订单由下一次点餐的 `guard` 自动核对。
2. 未说明数量时默认 1 份。
3. 未说明取餐时间时默认最早可取。
4. 默认自动使用最优惠方案；实际不优惠，或会超出用户金额上限的券，不采用。
5. 下单成功返回取餐码。
6. 点餐流程内写购物车不逐次审批，付款审批是唯一的放行关口；清空原购物车仍需确认。
7. 优惠在写购物车之前逐行确定，只报一次价；报价校验失败时撤销、去券重报一次。
8. 用户没说金额上限时，用账号的单笔限额；每日预算和单数限制保持上游默认值。
9. 首版只开放 `locker-in` 取餐柜取餐，其他方式验证通过后再加入 `qualified_eat_types`。

10. 门店每次都由用户确认：有常用门店时确认常用门店；没有常用门店，或用户不用常用门店时，打开官方门店选择（城市加可选关键词，再选门店），选中即为确认。
