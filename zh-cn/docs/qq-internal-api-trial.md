# QQ 网页会话内部接口实测

> 语言：简体中文 | [English](../../docs/qq-internal-api-trial.md)

历史试验：2026-09-10。用户授权编写试验性油猴脚本并用真实 QQ 邮箱测速，同一份源码通过既有 CLI 测试通道在已登录 QQ 页面运行成功，但当时尚未验证油猴内持久安装。未放宽安全门禁。2026-09-17 已删除无生产调用的独立原型及其专属测试；本文保留历史证据，不再作为现行实现说明。正式实现是[受管 QQ Reader](../../tools/browser-userscripts/qq-mail-reader.user.js)，当前验收见[增量时间线设计](email-timeline-incremental-sync-design.md)。

## 已验证行为

脚本从页面实际发生的 `/list/maillist` 请求中取得仅在内存使用的会话参数，直接拉取当前普通文件夹第一页的 50 条列表记录，再通过 `/read/readmail?func=5&mailid=…` 获取单封 EML。该操作与 QQ 当前公开应用脚本中的原件导出调用相符。凭据留在页面会话中；测速报告不含 Cookie、SID、邮箱地址、主题或正文。原件只在页面内存保留，用户点击后才下载。本次未接入 Gateway、增加周期任务、上传邮件、发送邮件或执行邮箱管理操作。

面板提供“获取 3 封原件”“测速 3 轮”、下载报告、分别下载 EML、停止并清除。样本默认每封不超过 1 MiB，底层每次响应上限 25 MiB、15 秒。只发同源 GET，携带同源登录凭据，拒绝跳转，使用 `cache: no-store`；登录／错误响应或非 EML 返回会明确失败。当前范围不包含置顶及会话／群邮件记录，不宣称完整文件夹或历史覆盖。手动安装：在油猴中新建脚本，以链接中的源码替换模板并保存，再刷新已登录的 `wx.mail.qq.com` 文件夹页面。如果浏览器提示启用用户脚本，需在浏览器完成该设置后再检查面板。

## 测速结果

| 环节 | 实测耗时 |
| --- | --- |
| 50 封邮件列表，三轮 | 217.6 / 144.4 / 146.5 毫秒 |
| 接口直读三封原件，共九次 | 平均 152.3 毫秒；范围 118.5–203.0 毫秒 |
| 现有 `collectUnread` + 页面原件导出，三封 | 10,452.1 / 10,974.0 / 10,510.8 毫秒 |
| 三轮“列表 + 三封原件”直读 | 合计 1,881 毫秒 |

按单封平均值计算，观测到约 69.9 倍差异。这是实际链路对比：页面方式包含现有身份检查、Controller／CLI 往返和原生下载落盘，直读方式计时到内存取得字节并算出哈希为止；均从已登录、已加载的浏览器开始。它不等于服务器接口延迟对比，也不能推广为普遍吞吐量。`no-store` 不排除服务端缓存。本次仅测试三封小邮件（16,106／7,176／15,068 字节），大附件和持续同步未验收。

九次直读均与列表声明大小一致，同一邮件跨三轮 SHA-256 一致。对应的三个页面导出文件，均是在完全相同字节后额外加一个 CRLF（两字节），因此原始文件哈希不同；记录此差异，不宣称文件逐字节完全相同。

证据：[脚本直读](../../docs/evaluation/qq-internal-api/direct-script.json)、[页面基线](../../docs/evaluation/qq-internal-api/ui-baseline.json)、[字节对比](../../docs/evaluation/qq-internal-api/source-comparison.json)、[元数据与限制](../../docs/evaluation/qq-internal-api/metadata.json)。五项 Node 测试覆盖请求范围、报告不含凭据、缺少登录、错误／非原件拒绝及范围／清理行为，语法和双语链接检查通过。首次探测未登录，用户登录后才获得成功结果。前期页面测速失败尝试记录在元数据中，后续使用明确 QQ 导航重试，保留凭据输出保护。

测试开始时应用容器已停止，仅临时启动 PostgreSQL，让现有 Vault 测试通道读取浏览器控制凭据，结束后重新停止。保留浏览器登录状态，未启动正常自动收信。临时 Go／shell 测试入口和下载的实验 EML 已清理，保留报告只有计时与完整性元数据。

## 周二往来邮件补充验证 — 2026-09-10

用户指定周二的回复邮件验证完整往来。9 月 8 日的「测试／Re: 测试」实际包含 **两条独立的 RFC 回复链**，不能因为同名就合成同一事件：

| 往来链，本地时间（Asia/Shanghai） | 已收发原件 | 方向 |
| --- | --- | --- |
| 15:11:01–15:21:54 | 4 封 | 发出 → 收到 → 发出 → 收到 |
| 15:29:51–15:31:13 | 3 封 | 发出 → 收到 → 发出 |

依据 QQ 当前公开应用实现，验证了复用会话的 `/list/search` POST。将每页设为两条，实际请求八页，取得服务端声明的全部 16 条结果，无锁定结果、无重复 ID。其中七封是该确切主题的已收发原件，一封同主题未发送草稿和八封其他主题记录被排除。再次完整分页检索，核对七个目标 ID 相同，未发现其他文件夹中额外的同主题已收发记录。随后通过 `/read/readmail?func=5` 下载七封原件，全程无需打开单封详情页。

七份 EML 均与声明大小一致，总计 47,764 字节；MIME 解析无缺陷，Message-ID 各不相同，所有 In-Reply-To／References 引用均能对应到已获取原件。两条链均无缺失的已引用前文，且包含本人的已发送邮件。从已登录、已加载页面开始，分页检索加七封原件下载共 **2,490 毫秒**，其中八页检索耗时 1,456 毫秒。本例七封原件均无附件部分，因此不能据此验收附件采集。

本地私有交付文件 `data/qq-thread-trial/qq-tuesday-conversations.zip` 包含按两条链排序的七份 EML 及完整性记录。仓库仅保留去除凭据／地址／正文后的元数据：[采集结果](../../docs/evaluation/qq-internal-api/thread-sample/capture.json)、[引用关系图](../../docs/evaluation/qq-internal-api/thread-sample/integrity.json)、[范围与限制](../../docs/evaluation/qq-internal-api/thread-sample/metadata.json)。测试后 Browser Controller 返回空闲，临时启动用于 Vault 测试的 PostgreSQL 已恢复原先停止状态。

本次证明的是这组样本在已枚举搜索结果中的覆盖和前文引用闭合，不证明不存在已删除、不可访问或改过主题而未被检索到的后续回复。当前邮箱呈现独立邮件行；公开 QQ 源码中的 `/list/collo_maillist` 及原生聚合 ID 解析已定位，但未对聚合成员接口进行真机验收。本次是“搜索＋原件”的定向网络验证，用户脚本中的通用线程采集及油猴安装仍是后续工作。
